# 安全思维 · 深讲十问

> 脊梁：安全是一种看系统的视角——数据从"我控制的"变成"别人能影响的"那条线就是信任边界，所有漏洞都长在没被认出来的信任边界上。这正是 AI 写代码最系统性的盲区，也因此是"保证者"最该握紧的判断。

---

## 1 · 注入类漏洞为什么都是"数据当代码"同一个错

SQL 注入、命令注入、XSS、模板注入、LDAP 注入……这些名字听起来五花八门，**根上却是同一个错误的不同外衣：把不可信的"数据"，当成可信的"代码/结构"去解释了。** 学透这一句，你就一次看穿了一整类漏洞。

拿 SQL 注入举例。你这样拼 SQL：

```
query = "SELECT * FROM users WHERE name = '" + userInput + "'"
```

正常时 userInput 是个名字。但攻击者输入 `' OR '1'='1`，拼出来就成了 `... WHERE name = '' OR '1'='1'`——他输入的那些**引号和关键字，被数据库当成了 SQL 的结构（代码）来解析**，而不是当成一个普通的名字字符串（数据）。**数据越过了它的本分，篡夺了控制流。** 命令注入（用户输入被当 shell 命令）、XSS（用户输入被浏览器当 HTML/JS 执行）、模板注入（用户输入被模板引擎当模板指令）——全是同一个剧本：**数据与控制流（代码）混淆了，本该是惰性数据的东西被当成了活的指令。**

**而'参数化查询'能根治 SQL 注入、'转义/过滤'只能打补丁——这两者的差别是种类上的，不是程度上的，这个区分至关重要：**

- **转义/过滤（打补丁，治标）**：你试图把危险字符（引号、分号……）找出来、转义掉或拒绝。但这是一场**你必然会输的黑名单游戏**——总有你没想到的编码方式、没覆盖的边界情况、没考虑的上下文（同一个字符串在 HTML 属性里、JS 里、URL 里的危险字符还不一样）。你是在"混在一起的数据+代码流"里，事后努力把代码的部分洗干净——只要漏一个，就破。它降低的是**出事的概率**。
- **参数化查询 / 预处理语句（治本，根治）**：你把 SQL 的**结构（代码）和数据，从一开始就走两条物理隔离的通道**发给数据库——先发"SELECT * FROM users WHERE name = ?"（纯结构），再把 userInput 作为**绑定参数**单独送过去。数据库收到时，结构已经定死了，那个参数**无论内容是什么，都只会被当作一个 name 的值，永远没有机会被解析成 SQL 结构**。攻击者输入再多引号和 `OR '1'='1'`，也只是被当成一个（很奇怪的）名字去匹配，匹配不到、返回空，仅此而已。它消除的是**出事的可能性**——数据在物理上不可能变成代码。

**所以根治之道不是'把混在一起的流洗干净'，而是'从源头把数据和代码两个通道分开，让它们永远不混'。** 这个"分离通道"的思想，是所有注入防御的正解：XSS 的正解是**上下文相关的输出编码 + CSP**（或像 React 那样默认把所有插值当数据转义、不当 HTML），命令注入的正解是**用参数数组而非拼字符串调用子进程**（`exec("rm", userFile)` 而非 `exec("rm " + userFile)`）——本质都是"别拼字符串，把数据作为独立参数传，让它没机会变成结构"。

打个比方：你给秘书口述一封信，说到"句号（period）"——她怎么知道你是要她打一个标点，还是要写下"period"这个词？如果你俩约定"凡是我说的内容都是信的正文（数据），控制指令我用完全不同的方式给（比如按铃）"，混淆就不可能发生。拼字符串就像把正文和指令用同一种方式（说话）混着给，迟早出歧义；参数化就像把正文和指令分两个完全不同的通道给。

- **可验证**：起一个拼字符串的查询接口，用 `' OR '1'='1' --` 打穿它（能拖出全表）；改成参数化查询，看同样的输入怎么变成一个匹配不到的普通字符串。这是十分钟就能复现、且会让你终身记住"分离通道"的实验。

## 2 · "前端校验了"为什么等于没做

"我前端做了校验，金额不能为负、必须登录才能点这个按钮"——在安全意义上，**这等于什么都没做。** 因为安全的信任边界**永远在服务端**，而客户端的一切，都必须当作敌人能任意伪造的。

要理解这一点，先认清一个事实：**攻击者完全控制着客户端。** 你的前端 JS、你的表单校验、你那个 `disabled` 的按钮、你藏起来的字段——这一切都跑在**用户的浏览器/设备里**，而用户（攻击者）可以：

- 打开开发者工具，把 `disabled` 改掉、把隐藏字段显示出来、改任意值。
- **完全跳过你的前端**，用 curl / Postman / Burp 直接构造原始 HTTP 请求打你的后端接口——你的前端 JS 校验**根本没机会运行**。
- 篡改前端发出的任何数据——包括那个声称"我是管理员"的标记、那个"商品价格 = 100"的字段。

所以**前端发来的每一个字节，都必须假设是攻击者精心伪造的**。前端校验只有一个作用：**改善用户体验**（即时反馈"密码太短""邮箱格式不对"，省得用户提交了才知道错）——它是 UX 功能，**不是安全功能**。真正的校验、鉴权、业务规则，**必须在服务端重新做一遍**，因为服务端才是你能控制、攻击者改不了的地方，是真正的信任边界。

**这一条原则的威力在于，它能一句话判死一大类"看起来安全"的设计：**

- **靠隐藏按钮做权限控制**——"普通用户看不到删除按钮，所以删不了"。错：删除接口照样在那、照样可调，攻击者直接打接口。
- **前端计算价格/金额**——"前端算好总价传给后端"。错：攻击者传一个自己改过的价格（甚至负数），后端如果照单全收就被薅。
- **"前端检查了角色"**——攻击者跳过前端，后端没检查就放行。

凡是把"安全保证"建立在"用户会乖乖用我的前端"这个假设上的设计，都是纸糊的。**判断的落点：任何一个会改变数据、或需要权限的操作，问自己一句——如果攻击者绕过前端、直接打这个接口，服务端拦得住吗？拦不住，就是个洞。** 前端是敌占区，服务端才是你的城墙。

- **可验证**：拿你自己的一个"前端做了校验"的功能，用 curl 直接打它的后端接口、绕过所有前端校验，看后端是不是裸奔（接受了非法值、放行了越权操作）——大概率会让你冒汗，而这正是该补的服务端校验。

## 3 · 认证 vs 授权：严重越权多是"没做授权检查"

认证（authentication，你是谁）和授权（authorization，你能干什么）是两件**必须分开、又最常被混在一起做错**的事。把它们的区别刻进脑子，能让你避开 OWASP 榜首那一整类最严重的漏洞。

- **认证**：确认"你是谁"。登录、验密码、查 token——确认你确实是张三本人。
- **授权**：确认"你能干什么"。张三登录之后，他**能看李四的订单吗？能删别人的评论吗？能访问管理后台吗？**

**而绝大多数严重的越权漏洞，根本不是'认证被绕过'，而是'认证对了，但系统压根没做授权检查'。** 这个区分极其关键，却极其常被忽视。最经典的就是 **IDOR（不安全的直接对象引用）**：

```
GET /api/orders/12345     ← 张三登录后，请求订单 12345
```

系统验明了"你确实是张三"（认证通过 ✅），然后……**直接返回了订单 12345 的内容——却没有检查"订单 12345 到底是不是张三的"**。于是张三把 URL 里的 ID 改成 `12346`、`12347`……就能**遍历出所有人的订单**。攻击者全程是**合法登录的他自己**，没有绕过任何认证——漏洞在于系统认证了身份，却**忘了对每一个被访问的对象做"这个用户有权访问这个对象吗"的授权检查**。这就是水平越权（看同级别其他人的数据）；类似地，普通用户能调到管理员接口，是垂直越权。

**OWASP Top 10 长期把"失效的访问控制（Broken Access Control）"排在第一**，根源就是这个"认证做了、授权漏了"。它如此普遍，是因为认证有现成的框架/中间件（登录、JWT 校验，一次配好全局生效），而授权是**业务相关的、要在每一个数据访问点逐个判断**的——"这个用户能不能动这个具体对象/做这个具体操作"，没有一刀切的中间件能替你做完，于是极容易在某个接口漏掉。

**判断的落点**：每一次数据访问、每一个敏感操作，都要问两个**独立**的问题——①你是谁（认证）？②**你被允许访问这个具体对象 / 执行这个具体操作吗（授权）**？第二个问题必须针对**具体的资源**来问（"张三能看**这一张**订单吗"），而不能只停在"张三登录了所以放行"。把"已登录"当成"有权限"，是越权漏洞的头号成因。

打个比方：认证是进大楼时门口查你的身份证（确认你是张三本人）；授权是你拿着的票，是不是**这一场、这个座位**的票（确认你有权坐这个位置）。只查身份证就让你随便进任何包厢、坐任何座位，就是 IDOR——身份对了，但没人检查你这张票配不配这个座。

- **可验证**：拿你系统里任意一个"按 ID 查/改数据"的接口，用 A 用户的登录态去访问 B 用户的资源 ID，看后端是返回了 B 的数据（越权漏洞），还是正确地拒绝（"这不是你的"）——这是发现 IDOR 最快的自测。

## 4 · 密码为什么要慢哈希加盐，"慢"为何是特性

存用户密码，有一串"绝对不能"和"必须"：绝不能明文存、甚至**不能用普通哈希（MD5/SHA256）存**，而**必须用慢哈希（bcrypt / argon2 / scrypt）加盐**。这里"慢"反而是个**安全特性**——理解这个反直觉，能让你一眼识破大量错误的"密码加密"方案。

先厘清一个常被说错的词：**密码是"哈希（hash）"，不是"加密（encrypt）"。** 加密是**可逆**的（有密钥能解回明文）——密码绝不该可逆（否则密钥一泄、或内部人员，就能拿到所有明文密码）。哈希是**单向**的（算得过去、回不来），你存哈希值，用户登录时把他输入的密码哈希一遍、和存的比对。所以正确的说法是"密码哈希"，凡是说"我们把密码**加密**存起来"的，往往一开始方向就错了。

那为什么连 SHA256 这种正经哈希都不够、要用"慢"哈希？想象最坏情况：**你的数据库被拖走了，攻击者拿到了全部密码哈希。** 他要从哈希反推出原密码，办法是**离线暴力破解**——不停地猜密码、哈希、和你的库比对。而 SHA256 这类哈希是为"快"设计的，**攻击者用 GPU 每秒能算几十上百亿次**——常见密码、弱密码几秒就破了。

**慢哈希的破局，就是故意把每次哈希变得很慢。** bcrypt/argon2 带一个"工作因子（work factor）"，可以调到让**算一次哈希要花上几十到几百毫秒**。对正常登录，用户登录时多花 100 毫秒**毫无感觉**；但对攻击者，**每猜一个密码就要 100 毫秒**——他原来每秒几十亿次的暴力破解，现在每秒只能试几次，破解一个像样的密码要等到天荒地老。**所以"慢"是在和 GPU 暴力破解赛跑——你用每次哈希的高成本，把攻击者的暴力破解从"几秒"拖成"几百年"。** 这就是"慢即特性"：慢拖垮的是攻击者的批量尝试，而对单次合法登录无伤。（argon2 还故意吃大量内存，专门对抗 GPU/ASIC 的并行——同一个思路的升级。）

**那"加盐（salt）"又防什么？它防的是一类完全不同的攻击——预计算 / 批量破解。**

- **彩虹表**：攻击者**预先**算好海量"常见密码 → 哈希值"的对照表，拖到你的库后直接查表反推，连暴力破解都省了。**加盐**——给每个用户的密码混入一个**随机的、每人不同的盐值**再哈希——让预计算的彩虹表**彻底作废**（因为同一个密码 `123456`，张三加张三的盐、李四加李四的盐，哈希值完全不同，攻击者没法用一张通用表查）。
- **批量识别**：不加盐时，两个用户密码相同 → 哈希相同，攻击者一眼看出"这俩人密码一样"、破一个就破一片。加盐后，相同密码哈希也不同，**必须逐个、单独破解**，无法批量。

**所以慢哈希和加盐防的是两类不同的攻击**：慢哈希对抗"每次猜测的速度"（暴力破解），盐对抗"预计算和批量"（彩虹表/批量破解）。两者缺一不可，且必须配合。

**这个认知能让你瞬间识破一堆错误方案**：用 MD5/SHA 存（太快，能暴力破解）❌；不加盐（彩虹表能查）❌；说"我们加密存密码"（可逆，方向错）❌；自己设计一个"哈希两次 + 拼个固定字符串"的土方案（不是经过验证的慢哈希，且固定串不是随机盐）❌。正解就一句：**bcrypt / argon2 + 每用户随机盐（现代库通常把盐自动包含在输出里）**，别自创。

- **可验证**：用同一个工作因子的 bcrypt 哈希一个密码，计时看它要多少毫秒（几十到几百），再算"攻击者每秒能试几次"；对比 SHA256 每秒几十亿次——这个量级差，就是"慢"挡住的暴力破解。看 bcrypt 输出里自带的盐字段。

## 5 · 自己实现加密为什么人人喊打（常量时间比较）

"自己实现加密算法"是安全圈人人喊打的禁忌——**不是因为你写不出 AES**（算法是公开的，照着写出"功能正确"的版本不难），而是因为**密码学的安全性，藏在一堆你根本想不到要测试的地方**，一个"功能上完全正确"的实现，可以因为某个非功能的细节而**被彻底攻破**。这是整个仓库[元认知](../../)"能跑≠对"最锋利的一个例证。

那些"想不到"的地方包括：

- **时序侧信道**（下面细讲）。
- **随机数质量**：你用了个可预测的随机源生成密钥/IV/nonce → 攻击者能预测，加密形同虚设。
- **IV/nonce 复用**：某些加密模式下，同一个 IV 用两次就能让攻击者恢复明文——一个看起来无害的"复用"是灾难。
- **填充（padding）**：处理不当会引出"填充预言（padding oracle）"攻击，能逐字节解密。
- **密钥管理**：密钥怎么生成、存哪、怎么轮换——算法再对，密钥管理一塌糊涂也白搭。

**最能说明"功能正确 ≠ 安全"的，是那个比较 MAC/token 的经典翻车——常量时间比较。** 假设你要校验一个签名/token，写了最自然的比较：

```go
if userToken == realToken {  // 普通字符串比较
    // 放行
}
```

这段代码**功能上 100% 正确**——`==` 当且仅当两个 token 完全相等时返回 true，任何功能测试都挑不出毛病。但它有一个致命的**时序泄漏**：普通的字符串/字节比较是**逐字节比、遇到第一个不同就立刻返回**的。这意味着——**两个 token 的相同前缀越长，比较花的时间就越长**（要多比几个字节才发现不同）。攻击者据此可以：固定其他位、**逐字节地猜第一个字节**，哪个猜测让比较耗时**略长一点点**，说明那个字节猜对了（多比了一位）；定下第一字节，再用同样方法猜第二字节……**像撬保险箱一样，靠测量比较耗时，一个字节一个字节地把整个 token 试出来、伪造成功。** 这就是时序攻击。

修复是**常量时间比较（constant-time comparison）**：无论两个值在哪一位开始不同，**都把所有字节比完、花费完全一样的时间**，不泄漏任何"前缀对了多少"的信息（Go 里是 `hmac.Equal` / `subtle.ConstantTimeCompare`，别用 `==` 比 MAC/token）。

**为什么这是"能跑≠对"的极端案例？** 因为那段 `==` 比较，**通过了所有功能测试**（输入相等返回真、不等返回假，逻辑完美），却是一个严重漏洞——**因为"正确"在这里包含了一个没有任何功能测试会检查的非功能属性：时间。** 你写单测、跑 CI、覆盖率 100%，全绿——可它在密码学意义上是错的。**这恰恰是 AI 生成代码最容易栽、而一个脑子里有安全模型的人能一眼接住的地方**：AI 会自信地写出 `if token == expected`，功能完美、看起来对，而你知道这里必须是常量时间比较。这就是[AI 时代工程师](../../AI时代工程师/)那篇说的"保证者"价值的最锋利体现——**你无法验证你无法建模的东西，而这个时序模型，正是把"能跑"和"真对"分开的那道判断。**

**判断的落点**：用经过千锤百炼的成熟库（且正确地用——别拿 `==` 比 MAC），永远别自创密码学。"我自己实现的功能测试都过了"在密码学里是最危险的自信。

- **可验证**：搜一个时序攻击的演示（用普通 `==` 比较 token，通过统计比较耗时逐字节恢复 token）；对比 `subtle.ConstantTimeCompare` 怎么把耗时差抹平。亲眼看一次"功能正确的代码被时间出卖"，会重塑你对"正确"的定义。

## 6 · SSRF：访问用户给的 URL 怎么偷走云凭证

SSRF（服务端请求伪造，Server-Side Request Forgery）是个在**云时代杀伤力被极度放大**的漏洞。它的起点看起来人畜无害：**你的服务器，去访问一个用户提供的 URL。**

这种功能到处都是：webhook 回调、"从 URL 导入图片/头像"、网页链接预览、"从 URL 生成 PDF"、RSS 抓取……都是"用户给个 URL，服务器去拉取它"。问题在于：**这个请求是你的服务器发出的，所以它带着服务器的网络身份、能到达服务器能到达的地方——包括那些攻击者自己直接够不到的内网资源。** 攻击者于是不再让你去拉一个正常网址，而是让你的服务器去访问：

- `http://169.254.169.254/...`——**云厂商的元数据接口**。在 AWS/GCP/阿里云等环境里，这个特殊的链路本地地址返回**当前实例的 IAM 凭证 / 临时密钥**。攻击者诱使你的服务器去请求它、把返回内容回显出来，就**偷到了这台机器的云凭证**——进而能用这套凭证操作整个云账号（读 S3、改配置、横向移动）。2019 年的 **Capital One 大泄露**就是这么发生的：一个 SSRF 拿到了元数据接口的凭证，撬走了上亿条客户数据。
- 内网的其他服务、数据库、管理接口（`http://10.0.0.x/admin`）——本来只在内网、没暴露公网，但你的服务器在内网，攻击者借你的手去访问。

**而"校验一下 URL 不是内网地址不就行了"——这种黑名单防御几乎总被花式绕过**，原因和[网络](../../网络/)主题相通：

- **DNS rebinding**：攻击者控制一个域名，让它在你**校验**那一刻解析到一个正常的公网 IP（校验通过），等你**真正去请求**那一刻，DNS 已经改成解析到 `169.254.169.254`（校验和使用之间的时间差被钻了空子——又是一种 TOCTOU 竞态）。
- **重定向**：你校验的 URL 是正常的，但它返回一个 302 跳转到内网地址，你的 HTTP 客户端**乖乖跟着跳**过去。
- **奇异的 IP 表示法**：`169.254.169.254` 可以写成十进制 `2852039166`、八进制、十六进制、IPv6 映射、`0.0.0.0`、`@` 绕过……朴素的"字符串里查内网 IP"根本拦不全。

**健壮的防御不是黑名单，而是：白名单（只允许访问明确许可的目的地）、在网络层屏蔽内网/链路本地段（让服务器根本到不了 169.254 和内网）、禁止或重新校验重定向、走专门的出口代理。** 核心思想还是信任边界——**用户给的 URL 是不可信数据，"让服务器拿它去发请求"就是把这个不可信数据放到了一个能触及内网的高权限位置**，必须严格限制它能去哪。

打个比方：你雇了个跑腿的（服务器），客人（用户）递给他一张纸条说"去这个地址取个东西"。客人完全可以在纸条上写**你家保险柜的地址**——跑腿的拿着你的钥匙、进了你家、把保险柜里的东西取出来交给了客人。SSRF 就是这样：你以为让服务器"去取个用户指定的东西"很无害，却忘了服务器能进的"家"（内网、元数据接口）里，放着要命的东西。

- **可验证**：在一个测试环境起一个"按用户给的 URL 拉取内容"的接口，试着让它请求 `http://169.254.169.254/latest/meta-data/`（云环境下）看能不能拉到元数据；试 DNS rebinding / 重定向绕过你的"内网校验"——体会黑名单为什么防不住，白名单 + 网络层隔离为什么才靠谱。

## 7 · CSRF 和 XSS 为什么本质相反

CSRF 和 XSS 名字像、常被一起提，**本质却恰好相反**——一个是"网站信任了用户给的内容"，一个是"网站信任了浏览器自动带上的凭证"。看清这个"相反"，两个漏洞和它们的防御就都通了。

- **XSS（跨站脚本）：网站信任了用户输入的内容，把它当脚本执行了。** 这是第 1 问"数据当代码"在浏览器里的形态——用户提交的内容（评论、昵称、URL 参数）被网站**原样渲染进页面**，里面藏的 `<script>` 就在**受害者的浏览器里、以这个网站的身份**运行了：能偷 cookie、能冒充用户操作、能改页面。**罪在网站信任了'注入进来的脚本'**（信任了内容）。
- **CSRF（跨站请求伪造）：网站信任了浏览器自动附带的凭证。** 机制完全不同——攻击者在**自己的恶意网站**上放一个会向**你的网站**发请求的东西（一个自动提交的表单、一个 `<img src="你的网站/transfer?to=攻击者&amount=1000">`）。当登录着你网站的受害者访问了这个恶意页面，**他的浏览器会自动带上他在你网站的 cookie** 去发这个请求——于是**你的网站收到一个带着合法登录态的请求，以为是用户本人自愿发起的**，就执行了（转账、改密码）。**罪在网站信任了'浏览器自动捎带的那个凭证（cookie）'**，而没确认这个请求是不是用户**有意**发起的。

**所以两者的'信任'方向相反：XSS 是信任了进来的内容（content），CSRF 是信任了自动随请求而来的环境凭证（ambient credential）。** 一个的输入是攻击者的脚本，一个的"输入"是受害者浏览器忠实捎带的 cookie。

**SameSite cookie 的出现，几乎改变了 CSRF 的攻防格局。** CSRF 的命根子是"浏览器会在跨站请求里自动带上你的 cookie"。而 `SameSite=Lax`（现代浏览器默认）/`Strict` 属性告诉浏览器：**跨站发起的请求，别自动带这个 cookie。** 命根子一断，CSRF 最核心的机制（盗用自动捎带的凭证）就基本失效了——这是浏览器层面对一整类漏洞的釜底抽薪。（传统的 CSRF token——每个表单藏一个服务器才知道的随机值、提交时校验——仍是显式防御，和 SameSite 配合用。）

**而"用 GET 请求做有副作用的操作"是个双重错误**：

- **违反 REST/HTTP 语义**：GET 按规范应该是**安全的、幂等的、只读的**（[分布式系统](../../分布式系统/)幂等、API 契约的精神）——浏览器、爬虫、预取器会随意重复 GET，你拿 GET 去转账/删除，可能被无意触发。
- **大开 CSRF 之门**：GET 请求**极其容易被跨站触发**——一个 `<img src="...">`、一个链接就能让受害者浏览器发出 GET。把有副作用的操作放在 GET 上，等于把它摆在最容易被 CSRF 利用的位置。所以有副作用的操作必须用 POST/PUT/DELETE，并配合 CSRF 防护。

- **可验证**：做个最小 demo——一个用 cookie 鉴权、用 GET 做"转账"的接口，再做一个含 `<img src="该接口?...">` 的"恶意页面"，登录后访问恶意页，看转账怎么被自动触发（CSRF）；给接口加 SameSite cookie 或 CSRF token，看它怎么被挡住；再做个把用户输入直接 innerHTML 进页面的 XSS demo，对比两者机制的相反。

## 8 · 最小权限与 assume breach

最小权限原则（principle of least privilege）是纵深防御的地基：**每个组件、每个账号、每个凭证，只拥有它完成工作所必需的最小权限，多一点都不给。** 它对抗的，是"一次小突破被放大成全面沦陷"的杠杆。

先看那些**放大杠杆**长什么样——它们平时figure省事，出事时要命：

- **"这个服务用 root 跑"**：服务本身只是处理图片，却以 root 权限运行。一旦它被攻破（比如一个 RCE 漏洞），攻击者**直接拿到整台机器的最高权限**——本来只该泄露几张图片，变成了整机沦陷。
- **"这个数据库账号有所有权限"**：一个只需要读某张表的服务，却用了能读写删所有库、还能 DROP TABLE 的账号。这个账号的凭证一旦泄露（日志里、代码里、SSRF 偷走），攻击者**拥有了你整个数据库**。
- **"这个 token 永不过期"**：一个泄露了也无所谓的短期 token，被设成永久——于是它一旦泄露，攻击者**永久持有**。

**最小权限就是拆掉这些杠杆**：服务用专属低权限账号跑（被攻破也只能干它本来能干的）、数据库账号只授它需要的那几张表的那几种操作、token 短期有效且按需授权。这样**一次突破的"爆炸半径（blast radius）"被牢牢圈住**——攻破了图片服务，攻击者也只能动图片服务那一亩三分地，蔓延不开。

**而比"最小权限"更进一层的成熟思维，叫 assume breach（假设已被攻破）。** 传统安全思维只问"我怎么**防止**被攻破"——但第 5 问已经告诉你，完美防御不存在（你总会有 bug、有未知漏洞、有被钓鱼的员工）。所以更成熟的问法是：**"假设攻击者已经攻破了我的某一个组件、已经在里面了——他能横向移动多远？能拿到什么？"** 然后据此设计：网络分段（被攻破的服务够不到核心数据库）、每个服务独立凭证（偷到一个不等于偷到全部）、短期凭证（偷到了也很快失效）、零信任（内部调用也要鉴权，不因为"在内网"就互相无条件信任）。

**"假设已被攻破、限制损害"这个思维，和[可靠性工程](../../可靠性工程/)的舱壁隔离（第 5 问）是同一个灵魂**——可靠性里你假设"某个零件一定会坏"，于是用舱壁把故障圈在一个隔舱里、别淹了全船；安全里你假设"某个组件一定会被攻破"，于是用最小权限和分段把入侵圈在一个区域、别沦陷全局。**两者都是从"防止坏事发生"升级到"接受坏事必然发生、把损害控制住"——这是成熟工程思维的共同标志**（也会在第 10 问和可靠性的错误预算再次汇合）。

- **可验证**：盘一下你系统里的服务和账号——有几个在用 root / 用万能数据库账号 / 用永不过期的凭证？给其中一个降权到"刚好够用"，确认功能不受影响——这一步就是在拆一个放大杠杆。画一张"假设这个服务被攻破，攻击者能横向够到哪些东西"的图，往往会发现一堆该隔离没隔离的路径。

## 9 · 供应链：最软的腹部

现代软件安全有个最软的腹部：**你自己的代码可能固若金汤，但你 `npm install` / `go get` / `pip install` 进来的成百上千个依赖里，任何一个被投毒，整条防线就破了。** 攻击者不必攻击你——他去攻击一个**你信任、并自动拉进项目里运行**的库。

理解它的可怕，先理解现代依赖的**传递性**：你直接依赖 20 个库，这 20 个又各自依赖几十个……最终你的项目里**跑着成百上千个你从没审过、甚至没听过的第三方代码**（尤其 npm 生态，一个普通前端项目轻松上千个依赖）。这些代码和你自己的代码**有同等的执行权限**——它能读你的环境变量（密钥！）、能发网络请求、能在 `install` 时执行任意脚本。**这上千个依赖，每一个都是你延伸出去的一份信任，而信任链上任何一环被攻破，攻击者就进来了。**

这不是假想，是反复发生的真实攻击：

- **event-stream（2018）**：一个每周下载千万次的流行 npm 库，原作者把维护权转给了一个"热心"的陌生人，对方在一次更新里植入了**窃取比特币钱包**的后门。无数项目自动拉到了带后门的版本。
- **xz backdoor（2024）**：一场潜伏**数年**的社工攻击——攻击者长期伪装成热心贡献者，逐步获得一个核心压缩库（被 SSH 间接依赖）的维护权，然后植入一个极其隐蔽的后门，差点波及几乎所有 Linux 服务器。是被一个工程师偶然发现性能异常才揭露的。
- **left-pad（2016）**：一个十几行的小库被作者删除，瞬间让无数依赖它的项目构建失败——展示了"一个看似人畜无害的小工具库"对整个生态的牵动。

**所以 lockfile、依赖审计、最小依赖，不是洁癖，是必需：**

- **lockfile（package-lock.json / go.sum 等）锁定每个依赖的确切版本和哈希**：这样攻击者**重新发布**一个同版本号但被篡改的恶意包时，哈希对不上，**不会被你静默拉进来**。`go.sum` 里那些哈希就是干这个的——它在防"你以为拉的还是那个包，其实内容被换了"。
- **依赖审计（npm audit / Dependabot / SCA 工具）**：扫描你的依赖树里有没有已知漏洞的版本，及时升级。
- **最小依赖原则**：每加一个依赖，就是多延伸一份信任、多一块攻击面。能不引入的就不引入（为了一个 `isOdd` 这种函数引入一个库，是在用攻击面换几行代码）——依赖越少，腹部越小。

**这直接连到作者 git-workflow 里那条纪律——"动 lock 文件（npm install / go mod tidy / cargo update）要单条确认"。** 现在你懂了那条纪律的安全分量：**改 lockfile 这个动作，可能在静默地把一个被投毒的依赖、或一个引入了恶意传递依赖的新包拉进来**。lockfile 的每一次变动，都是信任边界的一次移动，值得停下来看一眼"这次到底拉进来了什么、为什么"——这不是流程洁癖，是供应链攻击时代的自我保护。

- **可验证**：对你的项目跑一次 `npm audit` / `govulncheck`，看依赖树里有多少已知漏洞；数一下你的传递依赖总数（往往多到吓人）；看一次 `go.sum`，理解那些哈希在防什么；故意把 lockfile 删了重装，对比哈希校验怎么保证你拉到的是同一份字节。

## 10 · 安全是权衡，威胁建模怎么把空话逼成判断

最后一问，把安全从"技巧清单"拉回到"判断力"——也收口整个仓库反复出现的那条元规则。

第一个要破除的天真，是"我们要做到安全"这种**把安全当绝对**的想法。**安全和可用性、性能常常直接对立**：每多一道校验就慢一点、每多一层加密就费一点资源、最小权限让运维更麻烦、多因素认证让用户更烦。**追求"绝对安全"，和[可靠性工程](../../可靠性工程/)第 6 问追求"100% 可用"一样天真**——成本无穷（你能无限加固，回报却越来越小），而且你**根本无法穷举所有威胁**（总有你没想到的攻击面）。所以——

> **没有"安全"，只有"针对某些威胁、足够安全"。承认"安全是个权衡而非绝对"，反而是专业的标志。**

那怎么把"我们要安全"这句空话，逼成可执行的工程判断？靠**威胁建模（threat modeling）**——它强迫你回答一组具体的问题，把模糊的"要安全"拆成明确的决策：

- **防谁？**（who）——你的对手是谁？是无聊的脚本小子（自动化扫描），是想薅羊毛的黑产，是有内部权限的员工，还是有国家级资源的 APT？**防御等级取决于对手等级**——防脚本小子和防国家队，投入和手段天差地别，分不清就会么过度防御、要么防错方向。
- **护什么？**（what）——你最该保护的资产是什么？用户密码、支付信息、核心数据、还是可用性本身？**资源要押在最值钱的资产上**，不是平均撒。
- **不防什么？**（accepted risk）——明确**接受**哪些风险。"我们不防有物理机房权限的攻击者""我们接受这个内部工具的低安全等级"——主动声明"这些风险我们认了"，才能把精力集中。
- **防到什么程度？**（degree）——每个威胁防到什么水位算够，对应付出多少成本。

**威胁建模的本质，是把'安全'从一个无法达成的绝对目标，变成一组'防谁、防什么、不防什么、防到什么程度'的显式工程取舍。** 这正是[可靠性工程](../../可靠性工程/)的错误预算（主动定义"可接受的失败"）、[性能工程](../../性能工程/)第 10 问的"够快了"（用 SLO 而非"还能更快"定义终点）在安全领域的同一个身影——

> **工程成熟度的共同标志，是主动定义并接受一个非零的、有理有据的风险/失败/成本水平，把资源花在刀刃上；反义词，是"我全都要、且要绝对"的天真。**

可靠性主动接受"非零的失败"（错误预算），性能主动接受"非无限的快"（SLO），安全主动接受"非绝对的安全"（威胁模型里的 accepted risk）——**三个主题在这里汇成同一条判断力**。这也正是这整个仓库、乃至[AI 时代工程师](../../AI时代工程师/)那篇追求的东西：**真正的工程判断，不是追求某个绝对的理想值，而是在真实约束下，清醒地选择"够好"的那个点，并说得清为什么是这个点。**

- **可验证**：给你负责的一个系统做一次简化版威胁建模——画出数据流和信任边界，列出"防谁、护什么、不防什么、防到什么程度"，对照现状看哪里防过头了（浪费）、哪里该防没防（漏洞）。用 STRIDE 或攻击树辅助。你会发现，一旦写下"不防什么"，"安全"这件事第一次变得可决策、可收口，而不再是一句永远做不完的空话。
