# 网络 · 深讲十问

> 脊梁：网络上不存在"连接"这个实体，只有两端各自维护的状态，靠交换小纸条维持"还连着"的共识。可靠，是端上模拟出来的。

---

## 1 · IP 只承诺尽力而为，TCP 凭什么造出可靠有序的流

IP 层把话说得明明白白："我**尽力而为**。包可能丢、可能乱序到达、可能重复、可能延迟任意久——我不保证任何一条。" 这是一块极不靠谱的地基。可你天天用的 TCP，却给你一条**可靠、有序、不重不丢**的字节流。它凭什么在流沙上盖起高楼？

答案是：它**没有改造网络**，而是在两个端点上，用几样机制把 IP 的每一种不可靠分别补上：

- **怕丢、怕乱序、怕重复 → 序列号**：TCP 给字节流里**每一个字节**编号。接收方据此能发现"32 号到 47 号之间断了一段"（丢包）、"先到的是 48 号、32 号还没来"（乱序）、"这段我已经收过了"（重复）。一个编号，同时解决了三种病。
- **怕发出去石沉大海 → 确认（ACK）**：接收方不断告诉发送方"我已经连续收到第几号了"。发送方因此知道哪些到了、哪些还悬着。
- **怕丢了没人补 → 重传**：发送方把"已发出但还没被确认"的数据**留在重传缓冲里**，超时没等到 ACK（或收到重复 ACK），就重发。
- **怕乱序交付给应用 → 接收端重排缓冲**：乱序到达的段先在接收方缓冲里排好队，**按序**才交给上层应用。所以应用看到的永远是整齐的流，看不到底下的乱象。
- **怕数据损坏 → 校验和**：每段带校验和，坏了就当丢包处理。

把这五样拼起来，不可靠的 IP 之上就"长出"了可靠的 TCP。

**这里有个比五个机制更重要的观念，叫端到端原则（end-to-end principle）：可靠性不在网络里，是在端上模拟出来的。** 网络（路由器、交换机）被刻意保持"笨"——只管尽力转发，不管可靠；所有的聪明（重传、排序、纠错）都放在两个端点。为什么这么设计？因为只有端点才真正知道"这次通信要什么样的可靠"——有的要绝对可靠有序（TCP，传文件），有的宁可丢也不要等（UDP，实时语音，丢一帧无所谓、卡一下要命）。把可靠性硬塞进网络中间，既做不周全，又剥夺了端点的选择权。**这个"把保证放在端点、让中间保持笨"的思想，是整个互联网能做大的根基之一**，也呼应了[分布式系统](../../分布式系统/)的味道：可靠从来不是某一层免费给的，是有人在某个位置主动盖上去的。

打个比方：你要把一本书页页拆开、通过一个会丢件、会送错顺序、偶尔重复投递的烂邮政系统寄给朋友。你的办法是：给每页编号（序列号），让朋友收到后告诉你"我连续收到第几页了"（ACK），缺的页你重寄（重传），朋友按编号把书重新装订（重排）。邮政还是那个烂邮政，但你俩在两头的约定，让"可靠送达一本完整的书"成为可能。

- **可验证**：`tcpdump` 抓一段 TCP，观察序列号、ACK 号怎么递进；制造丢包（`tc qdisc ... loss 10%`）看重传怎么触发。读 Saltzer/Reed/Clark 的 *End-to-End Arguments in System Design*——这篇是互联网设计哲学的源头之一。

## 2 · 握手为什么三次、挥手为什么四次

"TCP 三次握手"几乎人人背得出，但为什么是**三**次、不是两次？为什么关闭却要**四**次？背后藏着 TCP 连接的本质——连接是两端各自维护的状态，建立它就是让两端的"序列号"对齐，且要防住一个幽灵。

**建立为什么要三次。** 连接的核心状态是序列号（第 1 问），而 TCP 是双向的，所以**两个方向各有一套序列号要协商**。三次握手干的就是这件事，外加防一个幽灵：

1. 客户端发 SYN，带上自己的初始序列号 x（"我从 x 开始编号"）。
2. 服务端发 SYN+ACK，带上自己的初始序列号 y，并确认收到了 x（"我从 y 开始，且我知道你从 x 开始"）。
3. 客户端发 ACK，确认收到了 y（"我知道你从 y 开始了"）。

走完三步，**两个方向的序列号都被对方确认过了**，双向通道就绪。少一次行不行？**两次握手扛不住一个幽灵：旧连接的迷途 SYN。** 设想客户端早先发过一个 SYN，但它在网络里堵了很久没到，客户端超时重发、正常通信完早关了。结果那个迟到的旧 SYN 这会儿才晃悠到服务端——若只要两次握手，服务端一收到 SYN 就 SYN+ACK 然后**直接认为连接建立、开始分配资源、甚至准备收数据**，可客户端根本没想建这个连接（它是个幽灵请求）。有了第三次——服务端要等客户端的 ACK 才真正建立——客户端收到这个针对幽灵 SYN 的 SYN+ACK 时会一脸懵、回个 RST 拒绝，连接就建不起来。**第三次握手，是用来确认"客户端此刻真的还想连"，堵死旧迷途 SYN 制造的假连接。**

**关闭为什么要四次。** 因为 TCP 是**全双工**的——A→B 和 B→A 是两条独立的通道，**各自独立关闭**。所以：

1. A 发 FIN（"我没有数据要发了"）。
2. B 回 ACK（"知道了"）。但**此刻 B 可能还有数据要发给 A**（A 只是不发了，没说不收）——这叫半关闭（half-close）。B 把剩下的数据发完……
3. B 发 FIN（"我也发完了"）。
4. A 回 ACK（"知道了"）。

四次的根源就是中间这段：B 的"我收到你不发了"（第 2 步 ACK）和"我也不发了"（第 3 步 FIN）**通常不能合并**，因为两者之间 B 可能还要发数据。而握手时不存在这个问题（双方都是从零开始、没有"还没发完的存货"），所以能把 SYN 和 ACK 合成一步，三次搞定。当 B 确实没有任何数据要发时，第 2、3 步偶尔也会合并成一个 FIN+ACK，退化成"三次挥手"——所以"四次"是上限不是铁律，本质是"两个方向各关一次"。

- **可验证**：`tcpdump` 抓一次完整连接的建立与关闭，对照 SYN/SYN-ACK/ACK 和 FIN/ACK/FIN/ACK 的标志位与序列号；用 `netstat`/`ss` 看连接在 `SYN_SENT`、`ESTABLISHED`、`FIN_WAIT`、`TIME_WAIT` 之间的状态迁移——状态机是理解 TCP 的钥匙。

## 3 · TIME_WAIT 为什么要傻等 2×MSL

主动关闭连接的那一方（发出最后一个 ACK 的一方），关完不会立刻消失，而是进入一个 **TIME_WAIT** 状态，**傻等 2×MSL**（MSL = 报文最大生存时间，典型 30 秒～2 分钟，所以这一等可能是 1～4 分钟）才彻底释放。明明都关完了，为什么要白白占着资源等这么久？这个"浪费"防的是两件事：

**其一，保证最后那个 ACK 真的到了对端。** 回顾四次挥手：主动关闭方发出最后的 ACK 后，如果这个 ACK 在路上丢了，对端（被动关闭方）会以为自己的 FIN 没被收到，于是**重发 FIN**。这时主动关闭方必须**还活着**，才能再补一个 ACK 让对端安心关闭。如果主动方关完立刻消失，对端重发的 FIN 就没人理，对端会一直卡在等待、最后异常关闭。TIME_WAIT 留出的时间，正好覆盖"对端可能重发 FIN"的窗口。

**其二，也是更深的一层——让本连接的迷途报文彻底死绝，免得污染下一个复用同一"四元组"的新连接。** 一个 TCP 连接由四元组（源 IP、源端口、目的 IP、目的端口）唯一标识。假设这个连接刚关，马上有个新连接复用了完全相同的四元组。而上一个连接可能还有几个延迟报文在网络里游荡——它们带着旧的序列号，如果这时冒出来到达新连接，就可能被**误当成新连接的数据**收下，造成数据错乱。2×MSL 这个时长，恰好保证"上一个连接的任何迷途报文都已超过最大生存期、必然已被网络丢弃"，新连接才安全。**TIME_WAIT 是在为"端口复用的安全"站岗。**

**这带来一个真实的工程痛点**：高并发**短连接**的服务器（比如每个请求建一个连接、用完就关，且由服务器主动关闭），会**积累海量 TIME_WAIT**——成千上万个连接都卡在那等 2×MSL，耗尽本地端口、吃掉内存。怎么办？

- **正确的方向**：减少短连接本身——用**长连接 / 连接池**复用（第 7 问），从源头不产生那么多关闭；或让**客户端而非服务器**主动关闭（TIME_WAIT 就堆在客户端、分散到千万台客户机上，而不是堆在一台服务器上）。
- **危险的歧途**：`net.ipv4.tcp_tw_recycle` 这个开关曾被当成"快速回收 TIME_WAIT"的灵丹——但它基于时间戳做激进回收，**在 NAT 后面会出致命问题**（NAT 后面多个客户端共用一个出口 IP，时间戳不单调，会导致合法连接被莫名拒绝），所以 **Linux 4.12 起已被彻底删除**。把它当解药是经典的"治标致命"。相对安全的是 `tcp_tw_reuse`（仅用于主动发起的新连接，配合时间戳）。

打个比方：挂电话后，你没立刻走开，而是在电话旁多守一会儿——一来怕对方说"刚没听清"再打回来（重发 FIN，你得能再应一声）；二来怕有条留给你的旧留言迟迟才到、被下一个用这条线路的人误收（迷途报文污染新连接）。守这一会儿看着浪费，其实是在保下一通电话的清白。

- **可验证**：`ss -tan state time-wait | wc -l` 数一台服务器上的 TIME_WAIT；压测一个短连接服务看它怎么飙升；查 `tcp_tw_recycle` 在你内核版本是否已不存在（4.12+ 就没了）——这本身就是一条"别照抄老博客危险参数"的活教材。

## 4 · 拥塞控制是为谁服务的，BBR 为什么换信号

很多人以为拥塞控制是"让我这条连接尽量快"。**恰恰相反——它的首要使命是让大家共享的网络别崩，必要时还会主动让你慢下来。** 理解这个"利他"的本质，是看懂它的钥匙。

历史上真出过事：1986 年，早期互联网（NSFNet）发生过**拥塞崩溃（congestion collapse）**——网络一堵，大家的包开始超时，于是大家**一起重传**，重传又加重了堵塞，于是更多超时、更多重传……正反馈把网络的有效吞吐打到接近零。从此 Van Jacobson 给 TCP 加上了拥塞控制：**慢启动**（新连接试探着从慢到快加速，别一上来就猛灌）、**拥塞避免**（接近上限时谨慎地线性增长）、**快重传/快恢复**（丢一个包别全速重来）。它管的是"所有连接如何礼貌地共享有限的网络带宽，不把彼此和网络一起拖垮"——是个**全局公地治理**问题，不是你一条连接的私事。

那 TCP 怎么知道"网络堵了、该让一让"？经典 TCP 的信号是：**丢包 = 拥塞**。逻辑是——路由器队列满了才会丢包，所以丢包意味着某处堵了，于是 TCP 一丢包就大幅降速（把拥塞窗口砍半甚至重来）。

**这个假设藏着一个致命的场景错配：在无线/高丢包链路上，丢包常常不是因为堵，而是因为信号干扰。** wifi、4G 信号一抖，丢个包是家常便饭，跟网络拥堵毫无关系。可经典 TCP 一根筋地把这种"无线噪声丢包"也解读成"网络堵了"，于是**无端降速**——结果你信号明明没满、带宽明明有余，下载速度却上不去，因为 TCP 被噪声吓得一退再退。**一个在有线时代完全正确的假设（丢包=拥塞），在无线时代成了性能杀手。**

**BBR（Google，2016）的破局，就是换掉那个信号。** 它不再问"丢包了吗"，而是**直接测量两个物理量**：瓶颈链路的**实际带宽**（我发出去的数据，对端到底以多快的速率在确认？）和**最小 RTT**（链路空载时的往返时间）。有了这两个，BBR 直接算出"这条路最多能容纳多少在途数据"，按这个来发——**随机的、非拥塞的丢包不再能吓退它**，因为它看的是"路实际有多宽、空走要多久"，而不是"丢没丢"。在高丢包链路上，BBR 往往能比经典 TCP 快出一截。代价也要诚实说：BBR 在某些混跑场景里对基于丢包的传统流不够"谦让"（可能抢占更多带宽），公平性是它持续被讨论和迭代（BBRv2/v3）的点。

打个比方：经典 TCP 像个一摔碗就以为厨房失火、立刻减速的服务员——可碗摔了原因多了去了（地滑、手抖、不止是失火）。BBR 像个先去测"这条路实际多快能走、空着走要多久"再据此匀速配速的司机——偶尔颠一下（丢个包）不影响它对路况的判断。

- **可验证**：`sysctl net.ipv4.tcp_congestion_control` 看你机器用的算法；在一条人为加了随机丢包的链路上（`tc ... loss 2%`）对比 cubic 和 bbr 的吞吐——能直观看到"丢包=拥塞"假设在有损链路上吃的亏。

## 5 · 队头阻塞的三个层次，QUIC 为什么搬到 UDP

"队头阻塞（head-of-line blocking）"是个会在三个不同层次反复出现的幽灵，名字一样、长相却不同。把三层看穿，你才懂为什么 HTTP/2 "解决"了它却又"制造"了它，以及 QUIC 为什么非得搬到 UDP 上重起炉灶。

**第一层，TCP 自己的队头阻塞。** TCP 承诺**按序交付**（第 1 问）：应用必须按字节顺序拿到数据。于是如果第 32 号段丢了，哪怕第 33、34、35 号段**早已到达**接收方缓冲，TCP 也**不能**把它们交给应用——必须死等 32 号重传补上、把窟窿填了，才能按序往上交。**一个丢包，卡住它后面所有已经到了的数据。** 这是 TCP 有序性的内在代价。

**第二层，HTTP/1.1 的队头阻塞。** HTTP/1.1 一条连接同一时刻只处理一个请求-响应。于是你在一条连接上排了请求 A、B、C，**A 的响应很慢（比如查库卡住），B 和 C 就只能干等**——哪怕它们本来秒回。这是请求层面的队头阻塞。（浏览器的缓解办法是开多条并行连接，但连接数有限。）

**第三层，HTTP/2 解决了第二层，却把第一层放大了。** HTTP/2 的杀手锏是**多路复用**：在**一条** TCP 连接上，把多个请求/响应切成帧、交错传输，逻辑上并行——A 慢不再挡住 B、C，请求层面的队头阻塞解决了。但魔鬼在于：**所有这些逻辑上并行的流，仍然挤在同一条 TCP 连接上**。而 TCP 还是那个"一个段丢了就卡住后面全部"的 TCP（第一层）。于是只要这条 TCP 连接**丢一个段**，**所有**复用在上面的流**全部**被卡住——因为 TCP 不知道这些字节属于不同的逻辑流，它只看到一条字节流断了一截，于是把所有后续数据一起扣住。**HTTP/2 把请求层的队头阻塞消了，却让 TCP 层的队头阻塞从"影响一个请求"升级成了"一丢包全员卡住"。** 队头阻塞没消失，被**下沉**到了传输层。

**这就是 QUIC 为什么非搬到 UDP 上不可。** 要根治，必须让"丢一个包只卡住它所属的那一个流、别的流照常跑"。可这要求传输层**理解流的边界**——而 TCP 骨子里就是一条不分流的字节流，改不动（它在内核、在全世界的中间设备里固化了几十年）。于是 QUIC 干脆绕开 TCP，在 **UDP**（无连接、不保证有序，等于一张白纸）之上，用**用户态**重新实现一套"传输层"：自己的序列号、确认、重传、拥塞控制——但关键是**按流独立**地做可靠和排序。某个流的包丢了，只阻塞那个流，其他流的数据继续交付。**为了把队头阻塞做成"按流"而非"按连接"，QUIC 重造了一个跑在 UDP 上的"TCP"。** 顺带它还把 TLS 握手揉进了连接建立（更少往返、支持 0-RTT），并用"连接 ID"而非四元组标识连接（所以手机从 wifi 切到 4G、IP 变了，连接还能续上）。HTTP/3 就是 HTTP over QUIC。

- **可验证**：在一条人为丢包的链路上对比 HTTP/2 和 HTTP/3 加载一个含很多小资源的页面，看丢包时 H2 的"集体卡顿" vs H3 的"个别卡顿"；读 QUIC 的 RFC 9000 里关于 stream 独立性的设计动机。

## 6 · Nagle + 延迟 ACK：两个优化撞出 40ms

有一类延迟故障最让人崩溃：代码没问题、网络没堵、机器没满，可某些小请求就是莫名其妙慢了**整整约 40 毫秒**，规律得可疑。十有八九，是 TCP 的两个"优化"——**Nagle 算法**和**延迟 ACK**——各自正确、撞在一起却合谋出了 bug。这是"两个对的局部优化组合出全局错误"的网络版教科书案例，和[并发原理](../../并发原理/)里"两个对的局部重排组合出错"是同一类陷阱。

先看两个优化各自的好意：

- **Nagle 算法**：为了避免网络被大量"只装一个字节"的小包淹没（每个 TCP 包有 40 字节头，发一字节太浪费），Nagle 规定：**如果还有数据没被对端确认，就先攒着小数据别发，等到要么攒够一个整段、要么之前发的都被 ACK 了，再发。** 好意是"合并小包，省带宽"。
- **延迟 ACK**：为了避免每收一个数据就单独回一个空 ACK（同样浪费），接收方规定：**收到数据后别急着 ACK，稍等一下（最多约 40～200ms），看看能不能搭顺风车**——要么和自己马上要回的响应数据捎带一个 ACK，要么攒到第二个包一起 ACK。好意是"合并 ACK，省带宽"。

各自都对。可在"请求-响应、且消息很小"的场景里，它俩**互相把对方按住了**：

1. 客户端用 Nagle，发了个小请求。
2. 服务端收到，用延迟 ACK——它想"等我把响应算出来，捎带着 ACK 一起发，省一个包"，于是**暂时不 ACK**。
3. 但客户端这边，如果它还想接着发下一小段数据，Nagle 说"上一段还没被 ACK 呢，先攒着别发"——于是**客户端在等服务端的 ACK**。
4. 而服务端在**等自己有响应数据好捎带 ACK**（或等延迟 ACK 定时器超时）。

**两边互相等：客户端等 ACK 才肯发，服务端攒着 ACK 等数据捎带——谁也不动，直到延迟 ACK 的定时器超时（约 40ms）强制发出那个 ACK，僵局才打破。** 凭空多出来的那约 40ms，就是这么来的。两个为省带宽设计的优化，在小消息往返场景下，组合成了一个延迟 bug。

**怎么破？** 对延迟敏感、又是小消息往返的协议（很多 RPC、数据库驱动、交互式协议），关掉 Nagle：设置 `TCP_NODELAY`，让小包立刻发，不再"攒着等 ACK"。这就是为什么几乎所有正经的 RPC 框架、数据库客户端默认都开 `TCP_NODELAY`。

**判断的落点**（也是和并发主题共享的元教训）：**两个在各自局部都正确的优化/重排，组合起来可能产生谁也没预料的全局错误。** 这类 bug 最难查，因为单独审查每一个组件都"没问题"。看穿它们，靠的是理解组件**交互时的时序**，而不是孤立地看每个组件——这正是系统思维的硬功夫。

- **可验证**：写个一来一回发小消息的 TCP echo，不设 `TCP_NODELAY`，`tcpdump` 抓包看那个约 40ms 的延迟 ACK 间隙；设上 `TCP_NODELAY` 再抓，间隙消失。这是少数能让你"亲眼看见两个优化打架"的实验。

## 7 · 长连接的新难题：怎么知道对端还活着

"短连接每次握手太费，我改用长连接（keep-alive）复用，性能就上去了"——对，但长连接换来了一个短连接根本不必面对的难题：**连接一直开着，可你怎么知道对端还活着？**

短连接里这不是问题：用完就关，下次重建，每次都是新鲜的。长连接里，一个连接可能开着几分钟几小时，期间对端可能**悄无声息地没了**：进程崩了、机器重启了、中间的网络断了。诡异的是——**这些情况通常不会给你发 FIN**（崩溃的进程来不及优雅挥手，断掉的网络更不会通知谁）。于是你这端的 TCP 状态机**还停留在 ESTABLISHED，以为连接好好的**，这叫**半开连接（half-open）**：一端已死，另一端却毫不知情，直到它真的往里发数据、石沉大海、最后超时报错，才发现"原来早断了"。

TCP 不是自带 keepalive 探测吗？有，但它**默认要空闲约 2 小时才发第一个探测包**——这个间隔是为"清理僵死连接"设计的，对应用级的"我现在就想知道对端还在不在"来说，**慢得毫无用处**。（而且改这个系统级参数会影响整机所有连接，很少这么干。）

**于是几乎每个应用层协议都被逼着自己造心跳：** Redis 的 `PING`/`PONG`、gRPC 的 keepalive ping、MySQL 的 ping、WebSocket 的 ping/pong 帧、各种 RPC 框架的心跳。机制都一样——**定期发个小包，对端按时回，几次收不到回应就主动判定连接死了、关掉重建。** 这本质上就是[分布式系统](../../分布式系统/)第 2 问那个故障检测器：用超时把"对端没回应"裁决成"对端死了"，同样躲不开"误判活人 vs 漏判死人"的两难——心跳间隔设短了灵敏但费流量、易误杀，设长了省事但发现得慢。

**长连接最经典的故障源，是连接池里的"陈旧连接（stale connection）"。** 你用连接池复用连接，但池子里某条连接，可能早被对端关了、或被中间的**负载均衡器/NAT/防火墙因为空闲超时悄悄掐了映射**（很多 LB 默认几分钟空闲就回收）——而你的池子不知道，下次有请求借到这条"看起来还在、其实已死"的连接，一发就报错或卡住。这是生产里极常见、又极难一眼看穿的坑。

**怎么治？** 一套组合拳：池子里设**最大空闲时间 / 最大存活时间**（连接太老就主动淘汰重建，别等它被中间设备掐）；**借出前校验（test-on-borrow）**或定期心跳保活；让应用层心跳间隔**小于**链路上最短的那个空闲超时（比 LB 的空闲回收更勤地发包，连接就不会被判空闲）。

打个比方：长连接像一条始终不挂断的电话线。对面的人可能早离开了房间，而你这头听筒还贴着耳朵、以为对话还在——直到你开口说话，迎来一片死寂，才知道对方走了半天了。心跳，就是每隔一会儿"喂一声"确认对面还在。

- **可验证**：起一个长连接服务，中途用 `iptables` 把对端流量 DROP 掉（模拟网络静默断开，不发 FIN），看你这端多久才发现连接已死（不开应用心跳的话，可能要等到下次写超时）；给连接池配上 maxIdleTime 和 test-on-borrow，复现并修掉一次 stale connection 报错。

## 8 · PMTU 黑洞：小请求正常、大请求莫名卡死

有一类故障的现象诡异到能让人怀疑人生：**小请求一切正常，一发大请求（或返回大响应）就莫名其妙卡死、超时**，而且 ping 得通、小接口都好使。十有八九，你撞上了 **PMTU 黑洞**。

先理解 MTU。每段链路有个**最大传输单元（MTU）**——一个 IP 包最大能多大，以太网典型是 1500 字节。一个包如果比沿途某段链路的 MTU 大，就得**分片（fragmentation）**拆成几个小包传。而分片是性能与可靠性的隐形杀手：任何**一个分片丢了，整个原始包就废了**（要全部重传）；重组要耗资源；更糟的是不少防火墙/设备**直接丢弃分片**。

为了**避免**分片，现代 TCP 用 **路径 MTU 发现（PMTUD）**：发包时打上"不许分片（DF）"标志，万一某个路由器发现"这包太大、又不让分片"，它会**回一个 ICMP 报文**告诉发送方："需要分片但被禁止了，请把包改小到 XXX。" 发送方收到这个 ICMP，就老实把包调小。机制很优雅——**前提是那个 ICMP 报文能回得到发送方**。

**黑洞就出在这个前提被破坏：很多防火墙/网络管理员，出于"安全"一刀切地把 ICMP 全部拦掉。** 于是：路由器丢弃了那个过大的包、也回了"请改小"的 ICMP——但 ICMP 被防火墙吞了，**发送方永远收不到这个反馈**。发送方蒙在鼓里，继续乐此不疲地发那个过大的包，每个都在中途被**静默丢弃**，没有任何错误提示。结果就是：

- **小请求/小响应**：包不超过 MTU，不触发这个机制，**一切正常**——这正是它最迷惑人的地方。
- **大请求/大响应**：包超过 MTU、被静默丢、又收不到 ICMP 反馈，于是**反复重传、反复被丢，最终超时卡死**。

这就是"PMTU 黑洞"。它难查到令人发指，因为最常用的诊断手段（ping 小包、curl 小接口）全是绿的，唯独"大数据量"这一类请求中招，而日志里往往只有一个干巴巴的超时，毫无线索。

**怎么破？**

- 别一刀切拦 ICMP——至少放行"需要分片（Type 3 Code 4）"这一类，PMTUD 才能工作。
- **MSS 钳制（MSS clamping）**：在网络边界（如 VPN、隧道入口）主动把 TCP 的 MSS 改小到安全值，让两端从一开始就不发超标的包。这是 VPN/PPPoE 环境的标准做法。
- **PLPMTUD（RFC 4821）**：一种**不依赖 ICMP** 的路径 MTU 发现——靠传输层自己探测（发不同大小的包看哪个能通），绕开"ICMP 被拦"的死穴。

打个比方：一辆超高的卡车要过一座限高桥，桥头本该有个"限高 3 米，请绕行"的牌子（ICMP 反馈），司机看到就换小车。可有人把牌子拆了（防火墙拦 ICMP），于是卡车一次次开到桥下被拦下、掉头、再来、再被拦——而小轿车（小请求）畅通无阻。你在起点看，只觉得"怎么大车老是到不了"，却怎么也想不到是那块被拆掉的牌子。

- **可验证**：`ping -M do -s 1472 <host>`（不许分片、发 1472+28=1500 字节）测路径能不能过整 MTU；逐步加大 `-s` 找到黑洞点；`tracepath` 直接探测 path MTU。亲手制造：在中间加一段小 MTU 链路并拦掉 ICMP，看大包怎么"人间蒸发"。

## 9 · TLS 防的三件事，前向保密靠什么

"上了 HTTPS/TLS 就安全了"——但安全到底指什么？TLS 其实在防**三件完全不同的事**，用的是**三套完全不同的手段**。把它们拆开，你才不会犯"以为加了密就万事大吉"的错。

- **防窃听（别人偷看我传的内容）→ 对称加密。** 握手之后，双方协商出一个只有彼此知道的**会话密钥**，用它把后续数据加密。中间人抓到的是密文，看不懂。这一项，加密算法（AES 等）就够了。
- **防篡改（别人偷偷改我传的内容）→ 消息认证（MAC / AEAD）。** 光加密不够——攻击者就算看不懂，也可能瞎改密文、或重放。所以每条消息附带一个用密钥算出的认证标签，接收方一验就知道有没有被动过。现代 TLS 用 AEAD（认证加密一体）把"加密 + 防篡改"合在一个算法里做。
- **防冒充（我连的真的是这个域名，而不是中间人假冒的）→ 证书链 / PKI。** 这是**最容易被忽略、却最关键**的一项。你和谁协商了会话密钥、加了密、防了篡改——可万一**对面那个"谁"本身就是中间人**呢？你可能建立了一条加密得无懈可击的通道，**直通攻击者**。所以必须有办法确认"对面真的是 example.com，不是冒充的"：服务器出示一张**证书**，这张证书由一个你信任的**证书颁发机构（CA）**签名，证明"这个公钥确实属于 example.com"。你的浏览器内置了一批受信 CA，验证这条签名链，才敢相信对面身份。

**这里是全问的关键观念：加密只解决了"窃听"，它根本不解决"对面是不是真身"。** "内容没被偷看"和"我连对了人"是两个正交的问题，由两套机制管。一个只加密不验身份的连接，是可以被中间人完美劫持的——这就是为什么自签证书、证书校验被关掉，是比"不加密"更危险的伪安全（你以为安全，其实门户大开）。

**前向保密（PFS）又是什么、靠什么做到？** 它要的保证很苛刻：**就算服务器的长期私钥将来某天泄露了，攻击者拿着它也解不开他过去抓的、存下来的流量。** 怎么可能？靠**临时密钥交换（ECDHE，椭圆曲线迪菲-赫尔曼）**：每次会话，双方各生成一对**用完即弃的临时密钥**，用它们当场推导出会话密钥，会话一结束就把临时密钥销毁。而那个长期私钥，**只用来"签名"证明身份（防冒充），从不直接用来加密会话密钥**。于是——长期私钥泄露，攻击者能冒充你（伪造未来的身份），但**推不出任何一次过去会话的密钥**（那些临时密钥早销毁了、且没参与签名），过去抓的密文依然是天书。没有 PFS 的老式做法（用长期公钥直接加密会话密钥）则相反：私钥一泄，**历史流量全部被追溯解密**。这就是为什么现代 TLS 默认强制 ECDHE——它把"身份"和"保密"解耦，让密钥泄露的伤害不能向过去蔓延。

打个比方：对称加密是你俩约定的暗语（防偷听）；MAC 是每句话后面附一个防伪封印（防篡改）；证书是对方亮出的、由你信得过的机构盖章的身份证（防冒充）。而前向保密，是你俩每次见面都**临时**约一套当天用完就忘的暗语——就算哪天你家那把"证明身份的总钥匙"被偷了，小偷也复原不出你们过去任何一天聊了什么。

- **可验证**：`openssl s_client -connect example.com:443` 看证书链和协商出的密码套件（带 ECDHE 的就是前向保密）；故意连一个证书过期/自签的站，看浏览器怎么因"身份不可信"而拦截——那一刻，被拦的不是"加密"，是"冒充"那一关。

## 10 · DNS 为什么是全球最大的最终一致缓存

DNS 看起来只是个"域名换 IP"的查号台，朴素到没什么可讲。但换个视角，它其实是**全世界最大的最终一致分布式缓存系统**——把它当缓存看，你会发现它的每个特性都在重复[缓存](../../缓存/)和[分布式系统](../../分布式系统/)主题的核心权衡。

为什么说它是个巨型缓存？因为**没有谁真的每次都去问权威服务器**。你查 `example.com`，请求会层层经过缓存：浏览器自己的 DNS 缓存 → 操作系统缓存 → 你配的递归解析器（如 8.8.8.8 或运营商的）→ 一路向上直到权威服务器。而每一层都会**按 TTL 把结果缓存起来**——TTL（生存时间）就是这条记录"可以放心用多久"，到期才重新去问。这套机制让全球天量的 DNS 查询绝大多数命中各级缓存、根本不惊动权威服务器，DNS 才扛得住整个互联网的规模。这正是缓存的本质（第 [缓存] 主题）：**用"可能过期的副本"换取速度和可扩展性。**

于是缓存的经典权衡，在 DNS 里一个不落：

- **TTL = 新鲜度 vs 负载的旋钮**：TTL 短，改动生效快、但查询频繁、负载高；TTL 长，省查询、但改动要很久才传开。和缓存主题第 5 问一模一样。
- **递归 vs 迭代查询**：谁替谁跑完整条查询链——是责任和缓存位置的分配。
- **负缓存（negative caching）**：连"这个域名不存在（NXDOMAIN）"也会被缓存一段时间，免得对不存在的域名反复追问。

而你日常遇到的两个"DNS 怪事"，本质是同一套缓存信任模型的两面：

- **"改了 DNS 解析，半天不生效"**：这就是**缓存失效难题**（缓存主题的"两大难事"之一）。你改了权威记录，但全球各级解析器、操作系统、浏览器里**还缓存着旧记录，要等各自的 TTL 到期才更新**——你根本无法强制全世界立刻刷新。所以上线切流量前要**提前把 TTL 调低**（让缓存活得短、改动传得快），这是运维的标准操作。
- **"DNS 劫持 / 投毒"**：攻击者往这套"靠缓存信任"的体系里**注入伪造的记录**——比如污染某个解析器的缓存，让它把 `bank.com` 解析到攻击者的 IP。它利用的正是"DNS 默认信任收到的应答、并缓存起来"这一点。防御靠 **DNSSEC**（给 DNS 记录加密码学签名，让伪造的应答验不过签）——本质是给这个"无脑信任缓存"的系统补上"防冒充"那一关（呼应第 9 问 TLS 的证书思路：又是"加密/校验身份"在另一处的重演）。

**所以 DNS 不是个孤立的查号台，它是缓存与最终一致性思想在互联网基础设施上的一次大规模实践。** 看懂这一点，你对"为什么改 DNS 要等""为什么切流量要提前降 TTL""为什么 DNS 会被劫持"这些运维常识，就不再是死记，而是从"它是个最终一致的巨型缓存"这一个原理推得出来——这正是本主题、乃至整个仓库追求的"底层是连通的"。

- **可验证**：`dig example.com` 看返回记录的 TTL 怎么随时间递减（缓存剩余寿命）；`dig +trace` 看一次完整的迭代查询从根服务器一路问下来；改一条自己域名的记录、用不同地区的公共 DNS 查，亲眼看"生效"怎么随 TTL 参差地传播开。
