# E · 范式之争——是性能选择，还是世界观选择

## 一个让人犯晕的矛盾

Go 最有名的箴言是："**Don't communicate by sharing memory; share memory by communicating**"——不要用共享内存来通信，要用通信来共享内存。它把 channel 捧成头号公民。

可上一面墙的实测明明白白：**channel 比锁还慢**，因为它底下就是一把锁加一套挂起唤醒。而这面墙开头这组配置读取的数字，更是把另一个反差摆到了脸上：

```
配置读路径            1核         8核
RWMutex            14.47 ns    134.2 ns    ← 核越多越慢
atomic.Pointer      6.59 ns      1.22 ns    ← 核越多越快
```

8 核时相差 **110 倍**，两条曲线还朝着相反方向跑。

于是矛盾来了：如果 channel 更慢，凭什么"用通信"是被推荐的默认写法？如果配置读取该用 atomic.Pointer，那 RWMutex 和 channel 又算什么？这箴言是性能上的谎言吗？

不是。**它压根不是一句关于性能的话，是一句关于"所有权"的话。** 这是看懂整个范式之争的钥匙。

## "用通信来共享"的真正含义：所有权，不是速度

把那句箴言翻成大白话：**在任何时刻，一块数据只被一个 goroutine 拥有、只有它能碰；想让别人碰，就把数据通过 channel 交出去——所有权随着消息一起转移。**

它的威力不在快，而在于**让"被多方共享的可变状态"压根不存在**。竞态条件的前提，是"多个执行流同时碰同一块可变数据"；当数据在任意时刻只有一个主人，这个前提就被釜底抽薪。**bug 不是被锁住了，是被设计掉了。**

这和最开头那面墙讲的 Rust 是同一个洞察的两种实现：Rust 用所有权系统在**编译期**强制"同一块可变数据只能有一个主人"；Go 用 channel 哲学，请你在**写法上自觉**做到同一件事。两者攻击的是同一个病根——别名的可变状态。区别只在于，Rust 用编译器把门焊死，Go 把钥匙交给你、附一句"建议这么用"。

## 四条路，同一个敌人

协调并发，本质都是在回答同一个问题：**怎么防止两个执行流同时碰同一块可变数据？** 人类想出的答案，分成几条不同的哲学：

- **共享内存 + 锁**：让它们排队碰。最直接灵活的默认路线，Mutex / RWMutex / atomic。代价是要你自己保证"所有访问者都守同一把锁"——只要有一方不守约（比如只写加锁、读不加锁），整个保护就失效。
- **CSP / channel**（Go，源自 Hoare 的理论）：不让它们共享，数据通过 channel 转交所有权。意图清晰、整类 bug 被消灭；代价是每次转交都要走那套锁加挂起唤醒，不便宜。
- **Actor**（Erlang/Elixir、Akka）：更彻底，每个 actor 只拥有自己的状态，对外只能往信箱发异步消息，**根本不存在共享内存**。用极致的隔离换来惊人的容错——一个 actor 崩溃不会污染别人。
- **不可变 + COW**（函数式、配置热加载）：把数据冻成只读，要改就造一份全新的整体替换。读者永远读一个不会变的快照，**连"协调"这一步都不需要**。

四条路，面对的是同一个敌人，只是把它消灭在不同的环节。

## 配置热加载：最优解既不是锁，也不是 channel

回到一个最常见的场景——配置热加载怎么保证并发安全。直觉往往在 RWMutex 和 atomic.Pointer 两个方案之间二选一。但站在范式的高度看，真正的洞察是：

**最优解不是在"锁还是 channel"里挑一个，而是先认出这是个读多写少的场景，进而把协调问题整个移除掉——用不可变 + 原子换指针（COW）。**

上面那 110 倍就是铁证，而它的成因，恰恰是缓存一致性那面墙：

- **RWMutex 读路径**：每次 `RLock` 都要原子地给 `readerCount` 加一——这是一个**共享写**。于是 8 个核疯抢这条缓存行，乒乓，134ns，核越多越慢。
- **atomic.Pointer 读路径**：所有核 `Load` 的是**同一个指针值**，它在各核缓存里都处于只读的 Shared 态——**多个读者和平共处，零写入、零争用**，于是 1.22ns，核越多越快，是真正的并行。

同一个问题、三种范式，而胜出的那个的精髓是一句话：**别让数据可变，竞争就不存在。** 这把内存模型（换指针靠原子操作建立可见性）、缓存一致性（readerCount 是个 cache 热点）、范式（移除协调而非挑选原语）三面墙，在同一个场景上同时点亮。

## channel 当对象池：这才是 channel 的主场

千万别因为上一面墙说"channel 慢"，就以为它没用。用带缓冲 channel 做对象池，恰恰是 channel 的**甜点区**：缓冲容量天然就是池容量，取对象就是 `recv`，还对象就是 `send`，并发安全由 channel 自带，一行锁都不用写。

为什么这里用 channel 是对的？因为**这件事的本质就是"资源的所有权在借用方和池之间来回转移"**——这正是 CSP 的拿手好戏。你要的是它的语义（池空时阻塞等待、池满时不收、所有权清晰），而不是它的裸速度。这跟"用 channel 做高频计数器"形成完美对照：**同一个工具，用在所有权转移上是神来之笔，用在简单状态的高频同步上是反模式。** 判断标准从来不是"channel 快不快"，而是"这件事是不是关于数据流和所有权"。

（顺带一个延伸：对象池为什么不能用 `sync.Pool`？因为 GC 会清空它——这是上一面墙运行时知识的直接推论。数据库连接这种"昂贵、需限量、要常驻"的资源，必须用 channel 池自己掌控生命周期，不能交给一个随时会被 GC 清空的缓存。）

## 成熟工程师的选择框架

把整面墙收成一张能直接用的判断表：

- 这件事是**数据流 / 所有权转移 / 信号通知**吗？→ 用 **channel**。
- 这件事是**高频地保护一个简单共享状态**吗？→ 用 **Mutex / atomic**。
- 这块数据**读多写少、而且能做成不可变**吗？→ 用 **COW / atomic.Pointer**，把协调问题直接移除。

Go 把这几把工具全摆在标准库里，那句著名箴言是**默认建议，不是法律**。Go 团队自己还有一句更平衡的话——*"channels orchestrate, mutexes serialize"*：channel 用来编排协作流程，mutex 用来串行化对状态的访问，各司其职。

## 三个值得想透的延伸

**COW 这么神，代价在哪？** 它只在"读多写少 + 数据可冻结 + 拷贝得起 + 读快照可接受"这几个条件同时成立时才赢。一旦写变频繁，每次写都要整体复制一份新对象，GC 压力陡增、写吞吐崩塌；一旦对象巨大，整体拷贝本身就贵（可以用结构共享的持久化数据结构缓解，但复杂度高）；更微妙的是，COW 给你的是"**某一个快照**"，不保证是"**最新**"——一个攥着旧指针的读者会一直读旧配置，如果你的业务要求"必须基于最新值动作"，COW 就不够，得上更强的协调。所以 COW 不是银弹，是一把专为"读多、可冻结、容忍快照"打造的钥匙。

**Go 为什么不学 Erlang 做纯 actor？** 因为 Go 选了务实而非纯粹。纯 actor（Erlang）用 share-nothing 换来无与伦比的容错和监督树，但代价是一切都得异步消息、连本可以一把 atomic 搞定的简单共享状态也要绕一圈，而且整个 BEAM 虚拟机是围着它造的。Go 选择"既给 channel 也给锁"，信任工程师按意图挑——代价是 **Go 不像 Rust/Erlang 那样从根上杜绝数据竞争**，你照样能写出 race，靠的是 `-race` 检测器这张"运行时安全网"，而不是编译器这道"编译期铁闸"。这又是一次世界观的取舍：灵活与性能，换掉了一部分保证。

**async/await 算这四条路的一种吗？** 它其实是另一根轴。async/await 主要回答的是"**怎么在等待 I/O 时不白占一个线程**"——这是调度问题，更该和 goroutine + 运行时调度器放在一起比，而不是和"如何安全共享"放在一起。在 Rust 里，async/await 管"如何高效地等"，所有权 + `Send`/`Sync` 管"如何安全地共享"，是两条独立的轴；在 JS 里，async/await 配单线程事件循环，靠"压根没有真并行"绕开了共享可变状态的竞态。而 **Go 干脆没有 async/await**——因为上一面墙讲的"goroutine 挂起极便宜"让它可以让你写**同步风格**的阻塞代码，由运行时在背后调度，于是 Go 优雅地躲过了 async/sync 把函数染成两种颜色的"函数染色"难题。这本身就是 D 那面墙省下的红利。

## 收口：五面墙，一条主线

到这里，这个主题的五面墙合龙了。回到最开始那个直觉——"各语言并发原理是不是通用的，只是上层包装不同"——现在可以给出完整回答：

- **A 内存模型 / B 原子性 / C 缓存一致性 / D 阻塞调度**，讲的是**机制**：底层那套硅——缓存一致性、原子指令、硬件乱序、park/wake——全世界通用，越往下越不分语言。
- **E 范式**，讲的是**意图**：共享内存加锁、CSP、actor、不可变、Rust 的编译期所有权、JS 的单线程事件循环——这些就是你最初说的"上层包装"，每一种都是对"如何防止别名的可变状态被并发触碰"这个**同一个敌人**的不同哲学回应。

而最关键的一句：**每一种上层范式，最终都编译到同一套五面墙的机制上**——channel = 锁 + park/wake；COW = atomic.Pointer + happens-before；actor 信箱 = 队列 + 锁；乐观事务 = CAS 自旋重试。你现在不只是知道有哪些包装，而是能一眼看穿每一种包装底下顶着的，是哪几面墙。

一句话带走整个主题：

> **并发安全 = 原子性 + 可见性；多核世界里争抢的基本单位是一条 cache line；所有同步原语的本职都是建立 happens-before；而你选哪种范式，是在表达意图，底下的机器永远是同一套。**
