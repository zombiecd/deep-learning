# 编译器与运行时 · 深讲十问

> 脊梁：源码只是给优化器的"意图说明书"，不是执行脚本。机械同理心的核心，是看穿"源码 → 实际执行"这层映射。

## 1 · 逃逸分析：你 new 的对象真在堆上吗

写 Go 时你以为自己掌控着对象在栈还是堆——其实**编译器在背后替你做了这个决定**，依据是一项叫"逃逸分析（escape analysis）"的静态分析。看穿它，能直接改变你写出 GC 友好代码的判断。

先理解栈和堆的天壤之别。**栈**上分配近乎免费——函数一返回，整个栈帧"啪"地一下全部回收，不需要 GC 操心。**堆**上分配要向内存分配器申请、用完还得等 GC 来回收，每一个堆对象都是 GC 的负担。所以"能放栈上就别放堆上"是性能的常识。

那一个对象到底放哪？关键问题是：**它会不会"逃逸"出当前函数的生命周期？** 如果一个局部变量的指针，在函数返回后还能被外界够到——被 return 出去了、被存进了全局变量、被一个比函数活得久的 goroutine 捕获了——那它就**必须**放堆上（否则函数返回、栈帧销毁，那个指针就指向了被回收的内存）。反之，如果它的一切使用都困在函数内部、函数一返回就再没人引用，它就能安安稳稳待在**栈**上。编译器通过逃逸分析推断每个变量的命运，自动决定栈还是堆。

**这里有个跨语言的精彩对照，能让你瞬间理解逃逸分析的价值：**

```go
func newThing() *Thing {
    t := Thing{}     // 局部变量
    return &t        // 返回它的指针
}
```

同样的代码模式，**在 C 里是悬垂指针灾难**——返回一个局部变量的地址，函数返回后栈帧没了，调用方拿到的是一个指向已销毁内存的野指针，未定义行为。**而在 Go 里完全安全**——因为逃逸分析发现 `t` 的指针被 return 出去（逃逸了），于是**自动把它分配到堆上**，函数返回后它依然有效，由 GC 负责回收。**编译器替你做了"该放堆上"的决定，把 C 里的一个经典 bug，变成了 Go 里的一个自动正确。**

反直觉的地方在于：**对象在栈还是堆，常常和你"看起来"的不一样。** 你 `new(Thing)`（看起来像在堆上）的对象，如果没逃逸，编译器照样把它放栈上；你一个普通局部变量（看起来在栈上），一旦被塞进 interface、被闭包捕获、被存进一个会逃逸的 slice，它就悄悄逃到了堆上。**所以"在堆还是栈"不取决于你怎么写分配，取决于这个值会不会逃逸。**

**判断的落点**：想写 GC 友好的高性能代码，核心动作是**减少不必要的逃逸**——少让局部对象逃到堆上（避免无谓地返回指针、避免把小对象塞进 interface、复用缓冲区而非每次新建）。逃逸少 → 堆分配少 → GC 压力小（直接接第 3 问）。而你不能靠猜，要靠工具看编译器到底怎么判的。

- **可验证**：`go build -gcflags='-m'`（甚至 `-m -m` 更详细）会逐行打印逃逸分析结果——"escapes to heap" / "does not escape" / "moved to heap"。拿你自己的热点函数跑一遍，常会发现一些意外逃逸（呼应作者并发 lab 的反汇编经验，这是同一种"看穿编译器"的功夫）。

## 2 · 内联为什么是"优化之母"

内联（inlining）就是把一次函数调用，直接替换成那个函数的函数体——调用 `f()` 处，直接展开成 `f` 里的代码。很多人对它的理解停在"省掉了一次函数调用的开销"（压参、跳转、返回）。这个理解**太浅，错过了内联真正的威力**。

内联真正的价值，是它**打开了后续一连串优化的大门**——所以被称作"优化之母"。把一个函数调用展开成函数体之后，编译器突然能"看穿"原本被调用边界挡住的东西，于是一串优化接连被激活：

- **常量传播**：如果你 `f(5)`，内联后编译器看到函数体里的参数就是常量 5，能顺着把一连串依赖它的计算在编译期算出来。
- **死代码消除**：内联后发现某个分支在这个调用点永远不会走（比如那个 `if param == nil` 在 param 是常量非 nil 时恒假），整段砍掉。
- **逃逸分析增强**（接第 1 问）：一个参数在被调函数里"看起来逃逸"，但内联到调用点后，编译器看清了它其实没逃逸，于是能把它留在栈上。
- **边界检查消除**（接第 5 问）：内联后能证明某个索引安全，删掉检查。

**所以内联省的那一次调用开销只是零头，它真正的回报是'让编译器能跨越函数边界做全局优化'。** 一个被内联的小函数，常常被后续优化吃得连影子都不剩。

这也解释了一个反直觉的性能悬崖：**"函数太大就不内联"**。编译器有个内联预算（cost threshold）——函数体超过一定复杂度/大小就**不予内联**（展开太大的函数会让代码膨胀、得不偿失）。于是一个热点函数，一旦因为加了几行逻辑**越过这个阈值、从"可内联"掉到"不可内联"**，它和它的调用方就**同时失去了那一连串内联带来的优化**——性能可能**断崖式下跌**，而你只是"加了几行无关紧要的代码"。

更反直觉的推论：**有时候手动把一个大函数拆成"小而热的核心 + 大而冷的边角"，反而更快**——因为那个被拆出来的小核心重新落进了内联预算，又能被内联、又能享受那串优化了（这正是第 9 问"冷热分离"在函数粒度的体现）。

- **可验证**：`go build -gcflags='-m'` 会打印 "can inline f" 或 "cannot inline f: function too complex"（还会给出 cost 分值）；把一个临界大小的函数加几行、再删几行，看它在"可内联/不可内联"之间翻转，并 benchmark 性能的悬崖。

## 3 · GC 偷走你的延迟，写屏障是内存屏障的亲戚吗

垃圾回收（GC）让你不用手动管内存，但它会在你看不见的地方**偷走 CPU 和延迟**——理解它什么时候偷、为什么偷，是写出延迟稳定的 Go 服务的前提。

先看 GC 怎么偷。最原始的 GC 要"停止整个世界（STW，Stop-The-World）"——暂停所有业务线程，扫描整个堆、标记存活对象、清理垃圾，扫完再放业务跑。堆一大，这一停就是几十上百毫秒，对延迟敏感服务是灾难。Go 的 GC 是**并发三色标记 + 写屏障**，目标是**让大部分标记工作和业务并发进行，只留极短的 STW**（现代 Go 的 STW 通常在亚毫秒级）。

那"写屏障"是干嘛的、为什么必须有？问题出在"并发标记"——GC 在标记存活对象的**同时**，业务代码还在跑、还在改指针。三色标记把对象分黑（已扫描，存活）、灰（待扫描）、白（还没碰，可能是垃圾）。危险场景：GC 已经把对象 A 标黑（认为它扫完了），这时业务代码让 A 新指向一个**白色**对象 B，同时又抹掉了别处对 B 的引用——如果 GC 不知道这次指针修改，它会以为 B 没人引用（还是白的），**把还活着的 B 当垃圾回收了**，灾难。**写屏障就是编译器在每个指针写操作旁边插入的一小段代码**，在 GC 期间记录下这些指针修改、通知 GC"这里有变动，别漏了 B"，从而维持三色标记的正确性（不变量）。

**那它和[并发原理](../../并发原理/)主题里的内存屏障是亲戚吗？** 要诚实地辨析——**它们共享"屏障"这个名字和"在写操作处插入额外动作"的形式，是概念上的表亲，但管的不是一回事**：

- **GC 写屏障**：管的是**可达性/回收的正确性**——别把还活着的对象当垃圾。
- **硬件内存屏障**：管的是**多核间的顺序与可见性**——别让一个核的写以错误顺序被另一个核看到。

两者都是"naive 代码会破坏某个不变量，于是在写操作处插桩来维持它"——这个**形式上的同构**是真的、也很有启发（看，不同层次的系统都在用"写处插桩维持不变量"这一招）；但说它们是同一个东西就过头了。看穿"形似而神不同"，本身就是一种判断力。

**判断的落点**：GC 调优的第一性原理是**"别产生垃圾"，而不是"更快地收垃圾"**。很多人一上来调 `GOGC`（控制 GC 触发频率）——但那只是让 GC 跑得更勤或更懒，治标。真正治本的是**减少堆分配**（接第 1 问逃逸分析）：对象池复用、避免无谓逃逸、减少小对象——分配少了，GC 要扫的、要回收的就少，停顿和 CPU 占用自然降。**少产生垃圾，胜过更快地收垃圾。**

- **可验证**：`GODEBUG=gctrace=1` 跑你的程序，看每次 GC 的耗时、堆大小、触发频率；用 `-gcflags=-m` 找出热点路径的堆分配并消除它们，再看 gctrace 里 GC 频率和停顿怎么下降。反汇编一个含指针写的函数，能看到 GC 期间写屏障插入的代码。

## 4 · interface 的隐藏堆分配与去虚化

"面向接口编程"是优雅的设计，但在热点路径上，interface 是有**性能价格**的——而且价格藏在你看不见的地方。看清它，你才知道这个优雅什么时候该付钱、什么时候不该。

**价格一：interface 赋值可能偷偷触发一次堆分配（装箱）。** 一个 Go interface 变量在底层是两个指针：一个指向类型信息（itab），一个指向实际数据。当你把一个具体值赋给 interface 时，如果那个值不是"已经在某处可寻址"的，运行时就得**把它拷到堆上**、让 interface 的数据指针指过去——这就是装箱（boxing），一次隐藏的堆分配。最经典的例子：把一个 `int` 塞进 `interface{}`（或 `any`），常常就触发一次堆分配（因为要给这个 int 在堆上找个地方让指针指）。一段"看起来只是赋个值"的代码，背后是一次 GC 负担。

**价格二：interface 方法调用比直接调用慢，且无法内联。** 调用一个具体类型的方法，编译器静态就知道调的是哪个函数，能直接调、还能内联（第 2 问）。但调用一个 interface 的方法，编译器**不知道运行时它装的是哪个具体类型**，必须**动态派发**——运行时通过 itab 查到真正的方法地址再跳过去。动态派发本身有开销，但**更致命的是它无法内联**——而无法内联，就意味着第 2 问那一连串"内联带动的优化"全都享受不到。所以热路径上密集的 interface 调用，损失的远不止那一次查表。

**那编译器的"去虚化（devirtualization）"是来救场的：当编译器能在某个调用点静态证明出 interface 实际装的具体类型时**，它就能把动态派发**还原成直接调用**（进而又能内联）。比如某个 interface 变量在小范围内刚被赋成一个确定的具体类型、紧接着就调用它的方法，编译器有机会看穿、去虚化。但去虚化只在编译器能证明类型时才生效，很多场景它证明不了，就只能老实动态派发。

**判断的落点**：interface 的优雅（解耦、可测试、可替换）是真有价值的，绝不是"别用 interface"。要点是**分清场景**——在**冷路径、模块边界、需要灵活性的地方**，interface 的开销可以忽略，优雅值这个价；但在**每秒被调用千万次的热点内循环**里，密集的 interface 装箱和动态派发会实实在在拖慢你，这时该考虑用具体类型、泛型（第 8 问）来避免。这正是作者延伸阅读里 ["What Color is Your Function"](https://journal.stuffwithstuff.com/2015/02/01/what-color-is-your-function/) 那个主题的精神——**抽象的代价不会凭空消失，只会换个地方出现**，你的判断力体现在知道这个代价在哪、什么时候付得起。

- **可验证**：`go build -gcflags='-m'` 看 interface 转换处有没有 "escapes to heap"（装箱）；写个 benchmark 对比"直接调用具体类型方法"和"通过 interface 调用"，看差距；观察去虚化能在哪些写法下把差距抹掉。

## 5 · 边界检查消除：写循环的方式怎么影响它

Go 和 Rust 是内存安全的——每次 `a[i]` 访问，编译器都在背后插了一道**边界检查**：如果 `i` 越界，就 panic（Go）/ abort（Rust），绝不让你读写到数组之外的内存。这是它们没有 C 那种缓冲区溢出漏洞的根基。但问题来了：**每次数组访问都多一道检查，为什么它们没有比 C 慢一大截？**

答案是**边界检查消除（Bounds-Check Elimination, BCE）**：编译器会**尽力证明"这个索引不可能越界"，证明得了就把那道检查删掉**。绝大多数规规矩矩的数组访问，编译器都能证明安全、删掉检查，于是运行时和 C 几乎一样快——你白拿了安全，却没怎么付速度。只有在编译器**证明不了**的地方，检查才保留。

**而最实用、也最反直觉的一点是：你写循环的方式，会直接影响编译器能不能完成这个证明、从而能不能删掉检查。** 看两段都"正确"的代码：

```go
// 写法 A：range 自己
for i := range a {
    sum += a[i]        // 编译器知道 i 一定在 a 的范围内 → 检查可消除
}

// 写法 B：用另一个长度去索引
for i := 0; i < len(b); i++ {
    a[i] = b[i]        // 编译器无法确定 a 至少和 b 一样长 → a[i] 的检查保留！
}
```

写法 B 里，编译器看着 `a[i]`，它知道 `i < len(b)`，但**它不知道 `len(a) >= len(b)`**——万一 a 比 b 短呢？所以它**不敢删 `a[i]` 的边界检查**，每次循环都老实检查一遍，热循环里这是实打实的开销。一个常见的优化技巧是给编译器"喂一个证明"：

```go
// 写法 C：先建立 a 足够长的事实
b = b[:len(a)]         // 或 _ = a[len(b)-1] 之类，给编译器一个 hint
for i := 0; i < len(a); i++ {
    a[i] = b[i]
}
```

通过让索引和被索引的 slice 在编译器眼里"长度可证明匹配"，BCE 就能生效、把检查删掉。**这就是"看穿源码→实际执行"在循环上的直接变现：两段逻辑等价的循环，因为写法不同，一个被插满了边界检查、一个干干净净，热路径上性能可以差出可观的一截。**

**判断的落点**：你不需要为每个循环都抠 BCE（绝大多数代码不在热路径，可读性优先）。但在**最热的内循环**里，知道"循环写法影响 BCE、可以通过给编译器喂可证明的长度关系来消掉检查"，是榨性能的一招——而前提是你得能**看见**哪些检查还在。

- **可验证**：`go build -gcflags="-d=ssa/check_bce/debug=1"` 会逐行报告"Found IsInBounds"（还保留着的边界检查）；或直接反汇编（`go tool objdump`）找循环里的 `CMP`/`JMP`（越界跳转）——对照写法 A/B/C，亲眼看检查怎么被消掉或保留（这正是作者并发 lab 反汇编功夫的延伸）。

## 6 · 分支预测：排序数组为什么快几倍

有一道著名的 StackOverflow 神题（史上点赞最高的问题之一）：**"为什么处理一个已排序的数组，比处理未排序的数组快好几倍？"** 代码完全一样——一个循环，里面一个 `if (data[i] >= 128) sum += data[i]`——唯一区别是数组排没排序。指令一模一样，速度却差几倍。这道题是理解现代 CPU "源码 ≠ 实际执行" 的最佳入口。

答案是 **CPU 的分支预测（branch prediction）**。现代 CPU 是**流水线**的——它不是执行完一条指令再取下一条，而是像流水线一样同时处理几十条指令的不同阶段（取指、译码、执行……）。可遇到一个 `if` 分支，CPU 在条件算出来之前，**就得决定继续取哪条路的指令**填进流水线——它只能**猜**（预测这个分支会走哪边），猜对了流水线满速前进，猜错了就得**把已经填进流水线的、走错路的指令全部清空、重来**——这一清空（流水线冲刷）要浪费**几十个时钟周期**。

现在看排序的影响：

- **已排序数组**：数据是有序的（先一堆小于 128 的，然后一堆大于等于 128 的），那个 `if (data[i] >= 128)` 的结果是**高度可预测**的——连续一长串 false，然后连续一长串 true。CPU 的分支预测器几下就摸清规律、几乎**每次都猜对**，流水线畅通无阻。
- **未排序数组**：数据是随机的，`if` 的结果**像抛硬币一样随机**——预测器约有 50% 猜错，**每两次就有一次流水线冲刷**，几十周期几十周期地浪费。于是慢出几倍。

**数据的顺序，在指令完全相同的情况下，决定了性能**——因为它决定了分支好不好预测。这彻底打破了"看代码就能估性能"的幻觉：同一段代码，喂不同分布的数据，快慢天差地别。

**这对你写热点判断逻辑意味着几条实招：**

- **把大概率的分支放前面**——让常走的路成为预测器容易学会的默认。
- **在热循环里用"无分支（branchless）"技巧消掉难预测的分支**——比如用位运算、条件移动（CMOV）、查表，把一个"猜不准的 if"换成"没有分支的算术"。那道 SO 题的高赞回答就给了用位运算消掉分支后、排序与否不再有差别的版本。
- **有时让数据更可预测（如预先排序、分组）本身就是优化**——虽然排序有成本，但若后续要在热循环里反复判断，可能整体更快。

- **可验证**：把那道 SO 题的代码跑一遍（排序 vs 不排序的条件求和），亲眼看几倍差距；再换成无分支写法，看差距消失。这是十分钟就能复现的、最震撼的"机械同理心"实验，强烈建议作者亲手跑一次。

## 7 · 内存布局：字段顺序怎么改变缓存表现

两个 struct，字段**完全相同**，只是**顺序不同**——它们会占用**不同的内存大小**、有**不同的缓存表现**。这件事很多人不知道，却是高性能数据结构的基本功。根源是**内存对齐（alignment）**和它带来的**填充（padding）**。

CPU 访问内存要求"对齐"：一个 8 字节的字段，地址最好落在 8 的倍数上（未对齐访问要么更慢、要么某些架构直接禁止）。为了满足对齐，编译器会在字段之间**插入填充字节（padding）**。而填充多少，取决于字段排列顺序：

```go
type Bad struct {
    a bool   // 1 字节
    b int64  // 8 字节 —— 但要对齐到 8 的倍数，所以 a 后面要填 7 字节！
    c bool   // 1 字节 —— 后面再填 7 字节凑整
}                // 总共 24 字节（一堆浪费在 padding）

type Good struct {
    b int64  // 8 字节
    a bool   // 1 字节
    c bool   // 1 字节 —— a、c 挤在一起，后面填 6 字节
}                // 总共 16 字节
```

同样三个字段，`Bad` 占 24 字节、`Good` 占 16 字节——**仅仅因为字段顺序。** 把大的、对齐要求高的字段放前面，小字段挤在一起，能显著减少 padding 浪费。这不只是省内存：struct 越小，**一个 CPU 缓存行（通常 64 字节）能装下越多个**，遍历一个 struct 数组时缓存命中率越高、越快（接[性能工程](../../性能工程/)主题的 memory wall）。

更进一步是**冷热分离（hot/cold splitting）**：把**频繁访问的字段（热）放在一起**，让它们挤进同一个缓存行（访问时一次加载就都在了）；把**很少访问的字段（冷）分出去**（甚至拆成单独的 struct 用指针引用）。这样热字段的访问缓存效率最高，不会被夹在中间的冷字段"撑开"、害得一个缓存行装不下几个热字段。

**那这和[并发原理](../../并发原理/)主题里的伪共享（false sharing）是同一层考量吗？是同一层物理（缓存行），但开的是相反的药方——这个对照特别能体现"看场景下判断"：**

- **单线程下，你想要"挤"**：把字段挤紧、让更多数据进一个缓存行，减少缓存行加载次数（本问的 packing）。
- **多线程下，你有时想要"分"**：如果两个核**各自频繁写两个不同的变量**，而这俩变量**恰好挤在同一个缓存行**里，就会发生伪共享——那个缓存行在两个核之间反复"乒乓"（MESI 协议来回失效），性能暴跌。这时的解药恰恰**相反**：用 padding 把这两个变量**撑到不同的缓存行**去（Go 里常见 `_ [64]byte` 填充，或 `sync` 包里的 cache-line padding）。

**同一个缓存行物理，单线程要"挤进一行"（packing），多线程要"撑开两行"（避免伪共享）——开相反的药，取决于访问模式是'一个执行流密集读' 还是 '多个执行流分别写'。** 看穿这一点（同一物理、相反处方），就是真正理解了缓存行这层。（并发主题 C 面墙讲的就是伪共享，这里是它的单线程镜像。）

- **可验证**：`unsafe.Sizeof()` 量一下重排字段前后的 struct 大小，看 padding 的差别；写个 benchmark：两个 goroutine 分别狂写一个共享 struct 的两个相邻字段，对比"相邻"和"用 padding 撑到不同缓存行"两种布局的吞吐——亲手制造并消除一次伪共享。

## 8 · "零成本抽象"为什么要打星号

"零成本抽象（zero-cost abstraction）"是 C++ 和 Rust 的招牌口号：**用了高级抽象，不该比你手写底层代码慢**——你不为没用到的东西付费，用到的也和手写一样高效。这句话**既是真的，又是个需要打星号的承诺**。看清星号在哪，是理解抽象代价的关键。

**哪些抽象真能做到零（运行时）成本？** 靠的是编译期把抽象"碾平"：

- **泛型的单态化（monomorphization）**：C++/Rust 的泛型，编译器为**每一个具体类型**生成一份专门的代码。`Vec<int>` 和 `Vec<string>` 各自编译成独立的、针对该类型优化到底的机器码——**没有运行时的类型判断、没有动态派发**，和你手写一个 int 专用版本一样快。
- **迭代器、RAII**：编译器能把它们彻底展开/内联成等价的底层循环和确定性析构，运行时不留痕迹。

**哪些抽象注定有运行时成本（星号所在）？**

- **虚函数 / dyn Trait / interface**：要运行时查表派发（第 4 问），有开销、无法内联——这是为"运行时多态"付的、抹不掉的钱。
- **动态类型、GC、反射**：都是运行时的活，编译期碾不平。

**而最能体现'零成本要打星号'的，是 Go 泛型的选择——它走了一条和 C++ 全单态化不同的路。** C++ 的全单态化虽快，但有代价：**代码膨胀**（每个类型一份代码，二进制体积爆炸、编译变慢）。Go 的泛型选了 **"GC shape stenciling"——字典 + 部分单态化的混合**：把**底层内存布局相同（同一 GC shape）的一组类型共用一份代码**，再通过传一个**字典（dictionary）**告诉这份代码具体的类型信息。

这个取舍换来了什么、失去了什么，要诚实说：

- **换来**：避免了 C++ 那种代码爆炸——二进制更小、编译更快。
- **失去**：那个字典带来了**一层间接**（运行时要查字典拿类型信息），所以 Go 泛型**不总是和"全单态化的手写代码"一样快**，某些场景比 C++ 的零成本泛型慢一点、可预测性差一点。

**所以"零成本"永远要打星号**：它可能是"零**运行时**成本，但有编译期/二进制体积成本"，也可能是"只对**能被单态化的那部分**零成本，动态派发的部分照样收费"。Go 用一点运行时速度和可预测性，换了更小的二进制和更快的编译——这是个**清醒的工程取舍**，不是"Go 泛型不行"。能说清"这个抽象到底零的是什么成本、不零的又是什么"，就是把这个口号真正学透了。

- **可验证**：拿一个泛型函数，对比 Go 和 Rust（或 C++）编译出的二进制大小、以及对不同类型实例化时的性能；读 Go 团队关于泛型实现选择 "dictionaries and GC shape stenciling" 的设计文档，看他们怎么权衡代码体积和运行速度。

## 9 · 编译器往你代码里塞了什么（栈扩容/抢占/写屏障）

你写的 Go 函数，编译出来的机器码里**藏着一堆你没写的东西**。看不见它们，你就解释不了 Go 的很多性能行为。主要有四样：**栈扩容检查、抢占点、GC 写屏障、race 插桩。**

**栈扩容检查（morestack），最普遍、最该懂。** Go 的杀手锏之一是 **goroutine 的栈能动态增长**——它起步只有约 2KB（所以你能轻松开几十万个 goroutine，每个栈都很小），需要更多时再自动长大。可"自动长大"是怎么做到的？**编译器在几乎每个函数的入口，插入一段检查代码（栈序言/prologue）："当前栈空间还够这个函数用吗？不够，就调用 `runtime.morestack` 去分配一个更大的栈、把数据搬过去。"** 这就是为什么 Go 函数有一点固定的入口开销（这段检查），也是为什么"goroutine 栈很小又能按需长大"这个特性，是用"每次函数调用都检查一下"换来的。理解了 morestack，你就懂了 goroutine 廉价的代价藏在哪。

**抢占点（preemption）。** Go 的调度器要能**抢占**一个跑太久的 goroutine（否则一个死循环的 goroutine 会霸占 CPU、饿死别人）。早期 Go 用**协作式抢占**——只在函数调用这种"安全点"才能被抢占。这埋了个著名的坑：一个**没有任何函数调用的纯计算死循环**（比如 `for { x++ }`），因为没有安全点，**永远无法被抢占**，能把整个调度器卡住、饿死其他 goroutine（甚至卡住 GC）。Go 1.14 起加入了**基于信号的异步抢占**才根治。理解"抢占需要安全点"，你就懂了为什么老版本 Go 里某些紧凑循环会神秘地拖垮整个程序。

**GC 写屏障**（第 3 问）：GC 期间，编译器在指针写操作旁插入的、维护三色标记正确性的代码。

**race 插桩**：用 `-race` 编译时，编译器在**每一个内存访问**旁插入监控代码，记录访问的 happens-before 关系来检测竞态（[并发原理](../../并发原理/)主题）——这也是为什么 `-race` 会让程序慢 5-10 倍、内存涨好几倍（它往你每个内存访问旁都塞了东西），所以只用于测试不用于生产。

**判断的落点**：**"运行时往你代码里塞了什么"是判断 Go 性能行为的前提。** 为什么函数调用密集的代码有固定开销（morestack 序言）？为什么纯计算循环在老 Go 里会卡死调度（无抢占安全点）？为什么 `-race` 这么慢（每个内存访问都被插桩）？这些"灵异现象"，一旦你知道编译器和运行时在背后塞了什么，全都变成了可推理的因果。这就是机械同理心——你工作的那一层之下，没有一个你完全无法推理的黑箱。

- **可验证**：`go tool objdump` 反汇编一个简单 Go 函数，在开头能看到栈检查序言（比较 SP、条件跳转到 `runtime.morestack`）；用老版本（<1.14）跑一个无函数调用的死循环 goroutine + 别的 goroutine，看它怎么饿死后者（新版本已修）；对比 `-race` 编译前后的二进制大小和运行速度。

## 10 · JIT vs AOT：运行时才编译为什么可能更快

Go、Rust、C++ 是 **AOT（提前编译，Ahead-Of-Time）**——源码在你发布前就编译成机器码。JVM、V8（JavaScript）是 **JIT（即时编译，Just-In-Time）**——程序**运行的时候**才把热点代码编译成机器码。直觉上"提前编译好"应该更快，可现实是 **JIT 跑起来可能比 AOT 更快**。这个反直觉，藏着一个深刻的取舍。

**为什么"运行时才编译"反而可能更快？因为 JIT 能看到 AOT 永远看不到的东西——真实的运行时 profile。** AOT 编译时，编译器对"程序实际会怎么跑"一无所知，只能做**保守**的优化（它不知道哪个分支热、不知道某个 interface 实际装的总是同一个类型）。而 JIT 编译器是在程序**已经跑了一阵、积累了真实运行数据之后**才编译热点的，于是它能做**激进的、基于实测的投机优化**：

- 看到某个分支 99% 走某条路 → 把那条路优化到极致，另一条留个慢速兜底。
- 看到某个多态调用点**实际上**总是同一个具体类型 → **去虚化 + 内联**（第 4 问），哪怕代码写的是多态。
- 一旦运行时发现"咦，假设破了"（出现了没料到的类型/分支）→ **去优化（deoptimize）**，退回安全的慢速版本。

这种"基于实际运行情况下注、赌错了能反悔"的能力，是 AOT 的静态视角天生给不了的。所以一个长期运行、热点稳定的 JVM 服务，跑久了之后的机器码可能比 AOT 编译的还优。

**但 JIT 的代价同样鲜明：**

- **启动慢、有预热期（warm-up）**：程序刚启动时，代码还在用解释执行或未优化版本跑（JIT 还没出手），**头一批请求很慢**，要等热点被识别、被编译之后才进入高速状态。
- **不可预测的延迟尖峰**：JIT 编译本身发生在运行时，会偶尔占用 CPU；去优化（deopt）也会造成突然的性能回退——这些制造了**延迟抖动**，对延迟敏感的系统不友好。
- **运行时开销**：JIT 编译器、profile 收集本身要占内存和 CPU。

**这个取舍干净地解释了语言的适用场景：**

- **JVM（JIT）适合长跑服务**：服务一开就是几天几周，**预热期的慢被几天的运行摊薄到可忽略**，而 profile-guided 的激进优化能持续受益——划算。
- **Go/Rust（AOT）适合 CLI 工具和冷启动敏感场景**（命令行程序、Serverless 函数）：这些场景**启动速度就是一切**，跑完就退、根本没机会预热——JIT 的预热期是纯亏，AOT 的"启动即满速、延迟可预测"才是对的。这就是为什么你不会想用 JVM 写一个频繁冷启动的 Lambda，也是 Go 在云原生 CLI/Serverless 里流行的底层原因之一。

**要诚实补一句**：这条界限正在被模糊——AOT 也能搞 **PGO（Profile-Guided Optimization，用一次采集的 profile 来指导 AOT 编译）**，Go 1.21 起就支持 PGO，等于让 AOT 也吃上了一部分"基于真实 profile 优化"的红利（只是 profile 是离线采的、不是运行时动态的）；JVM 也有 AOT 编译（GraalVM Native Image）来改善启动。所以"JIT vs AOT"不是非黑即白，而是一条"编译时机 vs 运行信息"的连续光谱——但理解两端的本质取舍，仍是判断"这个场景该用什么语言/运行时"的钥匙。

- **可验证**：测一个 JVM 服务的预热曲线——头几百个请求的延迟 vs 跑热之后的延迟，看那条下降曲线（预热期）；对比一个 Go 程序的启动到满速时间（几乎瞬间）。用 Go 的 PGO（采集 profile 再编译）跑一次，看它能不能逼近"JIT 式"的 profile 优化收益。
