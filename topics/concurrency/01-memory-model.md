# A · 内存模型：你写的顺序，凭什么不算数

## 一段"绝对没问题"的代码

```go
data = 42      // (1)
ready = true   // (2)
```

另一个 goroutine 在等：

```go
for !ready {}   // (3) 等 ready 变 true
print(data)     // (4)
```

任何人第一眼都会说：(4) 必然打印 42——`ready` 都 true 了，(1) 当然早跑完了。

可这段代码**允许打印 0，甚至允许 (3) 永远死循环**。注意用词是"允许"：这不是哪里写错了，是 Go（以及 C++、Java、几乎所有语言）的规则明文准许的合法行为。要理解为什么，得先承认一件反直觉的事——**你写下的语句顺序，到了机器那里不一定算数。**

## 三个捣乱者，和一条让你一直没察觉的铁律

`data = 42` 和 `ready = true` 这两行之间没有数据依赖：谁先谁后，对它们自己的结果毫无影响。于是有三个独立的角色，都有权动它们的执行顺序：

- **编译器**。它做指令调度时，看这两行互不相干，可能为了寄存器分配或流水线效率，把 `ready = true` 排到前面去。
- **CPU 的乱序执行**。现代处理器从不老实地一条接一条执行，谁的操作数先就绪就先发射哪条，完成顺序和程序顺序可以完全不同。
- **store buffer 与缓存**。`data = 42` 写出去的值可能还堵在本核的写缓冲里没刷进主存，而 `ready = true` 的值却先一步被别的核看见。

三个角色各自为政，却共同遵守一条铁律——**as-if-serial**：无论怎么重排，**只要你单线程去看，结果必须跟没重排过一模一样**。

这条铁律解释了那个最大的疑问：你单线程写了一辈子代码，为什么从没撞见过乱序？因为乱序对你这一条执行流是"隐身"的——它承诺只骗别人、不骗你自己。可一旦第二个 goroutine 站到旁边来观察，这条承诺就不再覆盖它了。它看到的，是被三个角色重排过的、赤裸裸的真实顺序。

打个比方：三个排版编辑可以随意调换你文章的段落顺序，只要**你本人**重读时感觉文意没变就行。问题是，另一个读者并没有这条保护——他读到的是被打乱的版本。并发 bug 的全部阴险都在这里：**它不是"错"，是"没保证"**。测试里跑一万次都对，生产环境某个深夜就翻车，因为乱序是概率性的，取决于当时的缓存状态、调度时机、甚至 CPU 型号。

## 这不是黑板上的理论——你的机器此刻就在为它插栅栏

要证明乱序是真的，不用读规范，反汇编一下就行。把同一个 `atomic.StoreInt64` 分别编译到 x86 和 ARM：

| 操作 | amd64（x86） | arm64（Apple M 系列） |
|---|---|---|
| `atomic.Store` | `XCHGQ`（自带全屏障） | `STLR`（store-release **屏障**） |
| `atomic.Load` | 裸 `MOVQ` | `LDAR`（load-acquire **屏障**） |

盯着 arm64 那一列问一句：**Go 凭什么要在这里插 `STLR`、`LDAR` 这两条带屏障的指令？** 因为 ARM 是弱序架构，硬件真的会把读写乱序刷出去；这两条屏障的唯一职责，就是摁住硬件"这之前的写必须先落地，别给我重排"。而 x86 是强序架构（TSO，总存储序），它本来就不允许 store-store、load-load 这类重排，所以裸指令就够用，不必额外插屏障。

反过来推就是铁证：**如果乱序不存在，编译器何苦多花这两条指令？** 屏障的存在本身，就是硬件会重排的证明。

这里还藏着一个对工程师的提醒：同一行 Go 代码 `x.Store(v)`，在你的 M 系列 Mac 上比在 x86 服务器上**多生成了屏障指令**。语言给你的"顺序一致"承诺没变，但兑现它的硬件代价随 ISA 浮动，而这层代价对你完全透明——这正是"上层包装"在替你干的脏活。

## happens-before：把"没保证"翻译成"有保证"

那么前面那段会打印 0 的代码，正确的修法是什么？不是含糊地"加把锁"，而是精确地**在两个 goroutine 之间建立一条 happens-before 关系**：

```go
var ready atomic.Bool

data = 42
ready.Store(true)      // 原子写。在 arm64 上，这就是那条 STLR

// ……另一个 goroutine
for !ready.Load() {}   // 原子读。arm64 上是 LDAR
print(data)            // 现在保证打印 42
```

happens-before 是内存模型定义的一条**偏序关系**，它的含义精确到冷酷：

> 若操作 A happens-before 操作 B，则 A 之前的所有写，**保证**对 B 之后可见。反之，两个操作之间若没有这层关系，可见性**没有任何保证**。

请把"没有任何保证"读三遍。它不是"大概率看不到"，是 undefined——编译器和 CPU 有权做任何事，包括让你永远看不到那次更新（于是 `for !ready {}` 真的死循环）。

`ready.Store(true)` 与 `ready.Load()` 之间建立了这条关系，于是 `Store` 之前写的 `data = 42` 被"一起拖过去"，对 `Load` 成功之后的代码保证可见。可见性不是原子操作额外送的赠品，它就是 happens-before 这条关系的直接结果。

记住这句话，整个并发世界就清爽了：**Mutex、channel、WaitGroup、Once、atomic——所有同步原语真正的本职工作，都是建立 happens-before。** 互斥、阻塞、唤醒都只是手段；建立这条关系、从而同时给出原子性和可见性，才是目的。

## 它怎么悄悄撑着你天天写的代码

这条抽象关系一旦握在手里，很多"我以为我懂"的写法会露出真正的骨架。

**配置热加载里的 `atomic.Pointer`。** 流行的说法是："读配置几乎零成本，就是原子地 load 一个指针。"这话只说对了一半，而且漏掉的那一半才是关键。它真正安全，不是因为"读指针这个动作是原子的"，而是因为 `Store`/`Load` 建立了 happens-before：你在 `Store` 新配置指针之前，构造好的那张 map、填进去的那些字段，靠这条关系才保证对"`Load` 到新指针"的读者可见。设想换成裸指针赋值（非原子），指针的值也许读对了，但它指向的对象内部可能还是半初始化的——读者拿到新地址，却读到旧的、甚至写了一半的内容。**"读指针是原子的"是表象，"建立了 happens-before"才是它不崩的根。**

**singleflight 里那个不起眼的 WaitGroup。** 多个并发请求合并成一个，只有第一个真正执行，其余等待并共享结果。等待者直接读共享变量 `c.val`，全程没有再加锁保护它——凭什么不出事？凭 `WaitGroup.Done()` happens-before `Wait()` 返回这一条关系。第一个 goroutine 对 `c.val` 的写，happens-before 它的 `Done()`，进而 happens-before 每个等待者的 `Wait()` 返回，于是等待者读 `c.val` 必然看到写入后的值。不是"碰巧没事"，是这条关系在背后兜底。

**连最朴素的 Mutex 也是这套。** "第 n 次 `Unlock` happens-before 第 n+1 次 `Lock` 返回"——所以上一个持锁者在临界区里写的东西，下一个拿到锁的人保证看得见。锁保护的从来不只是"同一时刻一个人进",还有"前一个人的修改对后一个人可见"。

## 各语言在这里分道扬镳——这正是"上层包装"的真义

最深的一层在这里。硅层是统一的：缓存一致性、原子指令、硬件乱序，全世界的 CPU 都这套。但**每个语言选择把这套乱序自由暴露给你多少**，截然不同——而这个选择，不是语法糖，是语言的世界观。

- **C++** 把全套刀都递给你：`relaxed`、`acquire`、`release`、`acq_rel`、`seq_cst`、`consume` 六档内存序，任你按性能榨到极限。代价是，你得自己保证别割到手。
- **Rust** 照搬了 C++ 的内存序，却用所有权系统让你**用错就编译不过**——safe Rust 里数据竞争在编译期就不可能，因为不可能存在"别名的可变引用"。同样把全套刀给你，但物理上拦着你割手。这就是它"无畏并发"的底气。
- **Java** 走的是演化路线：`volatile` 给你近似顺序一致的保证，多年后又用 VarHandle 补上了 acquire/release 这些更细的档位，是个不断长出旋钮的中间态。
- **Go** 最克制：**只给"顺序一致"一个档**，连 acquire/release 都不向你暴露。它的内存模型文档甚至直接撂了态度："If you must read the rest of this document to understand the behavior of your program, you are being too clever. Don't be clever."（要靠读懂这份文档才敢写并发，说明你太自作聪明了——别耍聪明。）

所以那个常见的直觉——"各语言并发原理差不多，只是包装不同"——对了一半，也错了一半。对的是：硅层确实统一。错的是：把差异看成糖。真相是，**"暴露多少乱序自由"这一个选择，就浓缩了语言的性格**：Go 的极简与"别耍聪明"，Rust 的"给你全部却不让你犯错"，C++ 的"全权交给你、后果自负"。你甚至能从这一个点，反推出整个语言的价值取向。

## 一句话收口

并发安全 = 原子性 + 可见性，二者缺一不可；而可见性的全部根基，是 happens-before。所有同步原语都在干同一件事——在执行流之间建立这条关系。理解了它，你就站在了讲原理的人那一侧，而不是背 API 的人那一侧。下一面墙（B）会往下钻：一条机器指令，到底凭什么是"原子"的。
