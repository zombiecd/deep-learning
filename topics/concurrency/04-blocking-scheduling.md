# D · 抢不到锁之后——傻等，还是躺下睡觉

## 三种"计数 +1"，先把代价摆出来

还是那台 8 核 Apple M 系列，让它用三种方式给一个计数器加一，量出每次操作的纳秒：

```
计数 +1 的代价          无竞争(1核)    满竞争(8核抢同一个点)
atomic.Add               7.24 ns        56.44 ns
Mutex  加锁 ++ 解锁      14.14 ns        98.38 ns
channel 发送(actor)      25.62 ns        73.11 ns
────────────────────────────────────────────────────
分片 atomic（对照）       7.25 ns         2.69 ns   ← 唯一随核数变快的
```

两个故事埋在里面。其一：**无竞争时，原语越"重"越贵**——atomic 7ns，Mutex 翻倍到 14ns，channel 再翻到 26ns。其二：**满竞争时三种单点写法全崩**，而把竞争分散掉的分片版反手把它们甩开二三十倍。这两个故事，正是这面墙要讲的两件事——锁的代价从哪来，以及代价失控时该怎么办。

## 锁的本质，还差一半没讲

锁的本质常被总结成一句漂亮的话：**锁 = 原子操作（CAS 抢标志）+ 阻塞唤醒机制**。前半句，上一面墙已经钻到底了——CAS 怎么抢标志、为什么一条指令能原子。但后半句"阻塞唤醒"，往往只用四个字带过。**抢不到的那一刻，到底发生了什么？** 这才是这面墙的正题，也是把"会背"和"懂"分开的地方。

抢不到锁，世界上只有两条路可走：

- **自旋（spin）**：赖在 CPU 上，反复重试，赌持锁者马上就放手。代价是白白烧着一个核空转；好处是如果对方几百纳秒内就释放，你立刻抢到，省掉了一切切换的开销。
- **挂起（park）**：把自己的执行状态存好，让出 CPU 给别人用，等锁空了再被唤醒。代价是"存档—调度—唤醒—恢复"这一整趟来回；好处是这段时间 CPU 能去干正经活。

选哪条，本质是一道算术题：**预计要等的时间，和 park/wake 的成本，谁大谁小。** 等待远比挂起成本短，就自旋；远比它长，就躺下。

这里藏着一个决定性的、很多人没想透的判据：**自旋只在"持锁者此刻正运行在另一个核上"时才划算。** 如果持锁者本身已经被调度走了（根本没在跑），你再怎么自旋也等不到它执行 `Unlock`——你不仅白烧 CPU，还占着核让它更难被调度回来。所以任何聪明的锁都不会无脑自旋，它得先判断"对方在不在跑"。

## Go 的 Mutex 是一部"代价递增的楼梯"

把上面的取舍落到代码，就是 Go Mutex 的加锁流程——一部踩一级贵一级的楼梯：

1. **快路径**：一次 CAS，把状态字 `state` 从 0 改成"已锁"。无竞争？到此为止。这正是"锁在无竞争时就是一次 CAS"的出处。（但记住 B 的提醒：这条 CAS 即便无竞争也不免费，它内含一道屏障——上面 Mutex 的 14ns 比 atomic 的 7ns 翻倍，一半就花在加锁解锁这两次带屏障的原子操作上。）
2. **自适应自旋**：CAS 失败说明有人在抢。先自旋几次。但自旋有严格条件——只在多核、自旋次数没超上限（约 4 次）、并且运行时判断"持锁者很可能正在跑"时才自旋；任一条件不满足，立刻放弃自旋。这就是上面那个判据的代码化身。
3. **挂起**：自旋几下还抢不到，就通过运行时信号量把自己挂起，进等待队列。
4. **唤醒**：持锁者 `Unlock` 时，从信号量里唤醒一个等待者。

楼梯之外还有一个公平性的旋钮——**正常模式 vs 饥饿模式**：

- **正常模式**：新来的 goroutine 和刚被唤醒的一起抢锁。新来的还热乎在 CPU 上、手里有时间片，往往抢赢——吞吐高，但代价是队列里的老等待者可能被反复插队，饿死。
- **饥饿模式**：一旦某个等待者等超过 **1 毫秒**，锁切到饥饿模式，直接把锁交给队首，严格先到先得。保证不饿死，代价是吞吐下降。

能讲出"Go 的 Mutex 在吞吐和公平之间会动态切换模式"，就比"它就是一把锁"高了一整个层级。

## 真正的魔法：Go 让 goroutine 睡，而不是让线程睡

到了这面墙最值钱、也最常被讲错的地方——**第 3 步那个"挂起"，挂的究竟是谁？**

流行的误解是："Go 的 Mutex 挂起时调用了操作系统的 futex，让 OS 线程睡了。"这是错的。Go 挂起的是 **goroutine，不是它底下的 OS 线程（运行时里叫 M）**。当一个 goroutine 阻塞在锁上，运行时把这个 **G** 摘下来、挂进等待队列，而那个 **M（连同它绑的 P）转身就去跑别的就绪 goroutine**。底层那个线程一刻都没闲着，更没有陷入内核去睡。

这就是 Go"睡觉"便宜到离谱的原因：

- **挂起一个 goroutine**：纯用户态的几百纳秒记账——改个状态位、挂进 `runtime` 那张按地址索引的等待表、调度器再换一个 G 上来跑。全程不进内核。
- **挂起一个 OS 线程**（比如 C/Java 里 pthread mutex 真的阻塞）：要陷入内核、走内核调度器，一两微秒起步；而且线程本身是重资源，MB 级的栈、数量上限只有几千。

Go 运行时的信号量是个**用户态结构**，不是直接的 OS futex。只有当整个 M 实在没有任何 G 可跑、要连线程一起睡时，最底层才借助操作系统原语。所以这条要刻进脑子：**Go 的锁阻塞，阻塞的是 goroutine、走的是运行时调度器，OS 线程会继续去忙别的。** 正是这一条，撑起了"随手开十万个 goroutine"的底气——睡一个 goroutine 几乎不要钱。

也顺手回答一个自然的反问：既然挂起这么便宜，干嘛还先自旋、不直接挂起？因为"便宜"是相对 OS 线程而言；几百纳秒的挂起开销，对一个只锁了几十纳秒的极短临界区来说仍然偏贵。自旋赌的就是"对方马上放手"，赌赢了连这几百纳秒都省了。所以是先自旋几下、赌一把短的，赌不中再躺下——两手都要，按情况切换。

## 横向一看：这一层各语言又分了家（绿色线程的死与复活）

把主题 README 那张三层图的第 3 层摊开，会看到一段很有意思的历史：

- **OS 线程**（Java 早期的 platform thread、pthread）：阻塞 = 内核挂起，重、贵、上限几千。
- **Go goroutine**：M:N 模型（M 个 OS 线程上跑 N 个 goroutine），阻塞 = 用户态挂起，轻、便宜、上百万。
- **Java 21 虚拟线程（Project Loom）**：**绕回了 Go 这条路**——虚拟线程阻塞时，从它的载体线程上"卸下来"，载体线程转去跑别的虚拟线程。几乎就是 goroutine 的翻版。

Java 在这件事上走了个回字形：它**早期有过绿色线程**（M:1，所有绿色线程共用一个 OS 线程），后来**死掉**了、换成原生 platform thread；二十年后又以虚拟线程的形式**复活**成 M:N。绿色线程当年为什么死？因为 M:1 有两个硬伤——**一个阻塞系统调用就能卡死全部绿色线程**（底下只有一个线程），而且**根本用不上多核**。Go 和 Loom 的 M:N 正好治好这两病：多个载体线程能铺满多核，运行时遇到阻塞系统调用时，把 P / 载体线程交给别的线程接管，不让一个阻塞拖垮全场。**同一个"让执行单元睡得便宜"的目标，被 M:1、纯 OS 线程、M:N 三种实现轮番试了一遍，最后收敛到 M:N。** 这是"底层原理通用、上层各自取舍"在调度层最生动的一例。

## channel 底层也是一把锁

很多人以为 channel 是某种"无锁"结构，其实不然——这面墙正好给它补上机理。`hchan` 结构体里明明白白躺着一把 `lock`——每一次 `ch <- x` 和 `<-ch`，运行时都先抢这把锁，操作环形缓冲区和等待队列，再解锁。当一个 goroutine 在 channel 上阻塞，它被挂进 `sendq` / `recvq`，由对手方唤醒——**和 Mutex 用的是同一套挂起唤醒机器**。所以 channel = 一把锁 + 一个环形队列 + 我们刚拆的那套 park/wake，外面包一层"通信 / 所有权转移"的漂亮语义。

回头看最上面那组数字：无竞争时 channel 发送 25.62ns，是 atomic 7.24ns 的 **3.5 倍**，还白搭了一个 owner goroutine。**所以"用 channel 做高频计数器"是典型的性能反模式**——优雅不等于无锁，更不等于快。channel 的价值在于表达数据流和所有权转移，让代码意图清晰；不在于给一个简单共享状态做高频同步。各司其职：传数据、转交所有权用 channel，护一个共享状态用 Mutex 或 atomic。

这里还有个值得停一下的反直觉：满竞争那列，channel（73ns）竟然比 Mutex（98ns）还快一点。原因是这个 channel 带了 1024 的缓冲，发送方多数时候只是把值塞进缓冲就走、并不真的挂起；而 Mutex 满竞争时在疯狂地 park/wake。但别被带偏——**它俩都被分片版的 2.69ns 暴打了二三十倍**。这说明一件事：当性能崩了，"选 Mutex 还是 channel"是次要的，**那个被所有核争抢的单点本身才是原罪**（这正是 C 那面墙的结论）。先消灭单点，再谈用什么原语。

## 锁粒度：为什么"慢操作绝不持锁"

限流器（令牌桶、滑动窗口）这类组件，表面在拼算法，**真正吃紧的是锁粒度**——而"锁粒度为什么要紧"，答案就在这面墙。

看最上面满竞争那一列，Mutex 已经冲到 98ns，而这还只是临界区里一个 `n++`。**设想你在持锁期间干了慢活**——查一次数据库、读一次文件、发一次 RPC——那么所有别的 goroutine 要么自旋空烧、要么走那条相对昂贵的 park/wake；临界区拖多长，这笔账就乘多大。这就是那条铁律"**执行慢操作时绝不持锁**"的硬核理由：持锁时间是要被竞争者数量放大的。

令牌桶常用的"惰性补算"之所以高明，正是把临界区压到最小：锁里只剩几步算术（按时间差补令牌、够则扣减），既不开后台 ticker，也绝不碰 I/O。锁一进一出快如闪电，自然没人需要被挂起。写好这类组件的真正功夫，不在算法本身，而在**你能不能把临界区缩到只剩"非碰共享状态不可"的那几行**。

## 收口

"锁的本质"现在能给出完整版了：**锁 = 用 CAS 抢标志（B 那面墙）+ 抢不到时在"自旋还是挂起"之间做决策（这面墙）+ 在吞吐与公平之间动态权衡（正常 / 饥饿模式）。** 而 Go 真正的杀手锏，是把"挂起"做进了用户态调度器——睡的是 goroutine 不是 OS 线程，这才撑得起海量并发，也是它和 Java 21 虚拟线程殊途同归的地方。

最后一面墙 E 顺着 channel 这个话题继续往上走：既然 channel 底下也是锁，那"用通信代替共享内存"到底是一个**范式选择**还是一个**性能选择**？共享内存加锁、CSP、actor、async/await 这几条路各自买到了什么、又付出了什么？

## 附：复现用的基准测试
```go
// go test -bench='Counter$' -benchtime=300ms -cpu=1,8
var an int64
func BenchmarkAtomicCounter(b *testing.B) {
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() { atomic.AddInt64(&an, 1) }
    })
}

var mu sync.Mutex; var mn int64
func BenchmarkMutexCounter(b *testing.B) {
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() { mu.Lock(); mn++; mu.Unlock() }
    })
}

func BenchmarkChannelCounter(b *testing.B) {
    ch := make(chan int, 1024); done := make(chan int64)
    go func() { var n int64; for range ch { n++ }; done <- n }()
    b.ResetTimer()
    b.RunParallel(func(pb *testing.PB) { for pb.Next() { ch <- 1 } })
    b.StopTimer(); close(ch); <-done
}
```
