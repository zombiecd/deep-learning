# B · 原子性：一条指令凭什么"不可打断"

## 从一个人人会背的事实，到一个没人追问的疑点

`counter++` 不是原子的——这句话面试人人会说。理由也都背得出：它在 CPU 眼里是三步，**读出来、加一、写回去**。两个核同时执行，可能都读到 5，各自算成 6，各自写回 6，凭空少了一次。

标准答案接着说："所以要用 `atomic.AddInt64`，它是一条指令，所以原子。"

就在这里，藏着一个几乎没人追问、却是整面墙地基的疑点：**"一条指令"凭什么就原子了？**

把 `atomic.Add` 编译出来，x86 上是一条 `XADD`。可这条 `XADD` 在 CPU 内部**照样是读-改-写**，照样要跨好几个时钟周期、拆成好几个微操作来跑。如果"一条指令"天生就不可打断，那它内部这几步之间，凭什么别的核插不进来？

答案很扎心：**插得进来。** x86 上一条**不带 `LOCK` 前缀**的 `XADD [mem], reg`，在多核下**根本不是**原子的——另一个核可以大大方方在它"读"和"写回"中间，把那块内存改掉。

所以原子性的来源，从来不是"它是一条指令"。是那个躲在指令前面、平时你根本不会注意的一字节前缀：**`LOCK`**。

## 先划清一条边界：什么不需要 LOCK

这里要插一句，免得矫枉过正。**不是所有内存访问都需要 LOCK 才安全。** 一次**对齐的**单纯读、或单纯写——比如读一个 8 字节对齐的 `int64`——本身就是原子的，CPU 用一次总线事务就完成，不会被劈成两半，不需要 `LOCK`。这正是为什么 `atomic.LoadInt64` 在 x86 上编译出来是裸 `MOVQ`，连 `LOCK` 都没有。

需要 `LOCK` 的，是**读-改-写（RMW）**这种复合动作：读出旧值、基于它算新值、写回去。麻烦不在"读"或"写"单独哪一步，在于这三步之间会被别人插队。`LOCK` 要保护的，就是这个"中间不许有人动手"的窗口。

记住这个区分：**单次对齐读写靠硬件天然原子；复合 RMW 才需要 LOCK 把窗口焊死。**

## `LOCK` 到底锁了什么——总线，还是缓存

这是最该抠、却最常被一句"锁住总线/缓存"糊过去的地方。其实那是两个时代的两回事：

**老 CPU，或现代 CPU 没办法时的回退**：拉高 `#LOCK` 信号，**锁整条内存总线**。在这条 RMW 指令执行期间，所有其他核**碰不了任何内存**。它对，但它暴力——你做一个加法，全机器的内存访问陪你一起堵。

**现代 CPU 的绝大多数情况**：**只锁一条 cache line，不动总线**。靠的是缓存一致性协议（MESI）：CPU 把目标数据所在那条缓存行，攥在"我独占"的状态（Exclusive/Modified），在整个 RMW 期间不让任何别的核拿走它。其他核访问**别的**地址完全照常，只有同样想抢这条线的核才会被挡一下。

所以"`LOCK` 锁了什么"的精确答案是：**现代 CPU 锁的是一条缓存行，不是总线。** 只有当被操作的数据**跨了两条 cache line**、或者落在不可缓存的内存上时，才退化回那个暴力的总线锁。

把这句话刻下来，因为它是下一面墙的火种：既然"加锁"在硬件上等于"独占一条 cache line"，那当很多核同时抢同一条线时会发生什么——就是 C 题"核越多反而越慢"的全部根源。

## `LOCK` 不免费，哪怕没人跟你抢

顺带破一个常见错觉。很多人以为"无人竞争时原子操作零成本"。不对。一条 `LOCK` 指令即使在完全没有竞争时，也比普通指令慢一个数量级（普通 `ADD` ~1 周期，`LOCK XADD` 往往几十周期）。因为它不只要做加法，还得**保证全局可见顺序**——通常要把本核的 store buffer 排空、充当一道全屏障。

这正好和 A 那面墙接上了：A 里我们看到 Go 在 ARM 上为原子操作插 `STLR/LDAR` 屏障；这里看到 x86 的 `LOCK` 本身就内含屏障语义。原子操作"轻"是相对锁的重竞争而言，**它从来不是免费的**——它的成本恰恰是它能提供顺序保证的代价。

## ARM 没有 `LOCK`——它换了一整套哲学

x86 是 CISC：给你一条复杂的"自带锁的 RMW"指令，一锤子买卖。ARM 是 RISC，骨子里不喜欢这种又重又复杂的指令，于是把"原子 RMW"拆成两步，叫 **LL/SC（Load-Linked / Store-Conditional）**：

- `LDXR`（load-exclusive）：读一个地址，同时在硬件里给它**挂一个监视器**。
- `STXR`（store-exclusive）：写回去，但**只有这期间没人碰过那个地址才成功**；被碰过就失败、返回一个标志，由你**跳回去重试**。

这恰好是把同一段 Go 代码编译到 arm64 时，看到的回退路径：

```
LDAXR (R1), R2      // load-exclusive，挂上监视器
ADD   R0, R2, R2    // 加一
STLXR R2, (R1), R27 // store-conditional，可能失败
CBNZ  R27, -3(PC)   // 失败就跳回去重来  ← 这才是真正的"自旋"
```

而较新的 ARM（ARMv8.1 起的 LSE 扩展，比如苹果 M 系列芯片）补上了真正的单指令原子，像 `LDADD`、`CAS`、`SWP`。所以 Go 在 arm64 上其实生成了**两条路**外加一个运行时探测：芯片支持 LSE 就走单条 `LDADD`、跳过整个循环；不支持才落到上面那个 LL/SC 自旋。

这个细节顺手纠正一个流行说法——"`atomic.Add` 是个 CAS 自旋循环"。它**只**在老 ARM 无 LSE 的回退路径上才长成那样；在 x86 是单条 `LOCK XADD`，在你手边的 M 系列 Mac 上是单条 `LDADD`，都不自旋。把一个随硬件变形的抽象，钉死成它最少见的那个形态，正是"背 API"和"懂原理"的分水岭。

## CAS：无锁世界的地基，也是"乐观锁"的硅层本体

在所有原子原语里，**CAS（Compare-And-Swap）**是最关键的一条——x86 是 `LOCK CMPXCHG`，ARM 用 LL/SC 或 LSE 的 `CAS` 实现。它接收三个参数：**地址、期望的旧值、要写的新值**，语义是：

> "如果这个地址现在还等于我给的旧值，就把它改成新值、返回成功；如果不等（被别人改过了），什么都别做、返回失败。"

几乎所有无锁（lock-free）数据结构——无锁队列、无锁栈、引用计数——底层都是一个 `for` 循环套着 CAS："读出当前值 → 算出新值 → CAS 试着提交 → 失败就拿着最新值重算重试"。

而这里有一个很漂亮的收束，把"乐观锁 vs 悲观锁"这个看似很上层的概念，一直拉到硅层：

- **CAS 就是乐观锁的硬件本体。** "假设没人跟我抢，直接试着提交；真撞上了就重来。"乐观不是一种编程技巧或设计模式，它就是 `CMPXCHG` 这条指令的语义本身。
- **Mutex 是悲观锁。** "先把门锁上，再安心动手。"

ARM 那个监视器，更是把"乐观"直接做进了电路——store-conditional 失败，就是硬件在对你说："你乐观地赌了一把，但赌输了，重来。"所以乐观/悲观不是两种写法，是两种世界观，而且它在硬件层就已经分好了阵营。

## 两套哲学，连 ABA 都分了胜负

x86 的 CAS 有个经典坑——**ABA 问题**：它只比"值等不等于旧值"，不知道这中间有没有被人从 A 改成 B、又改回 A。值兜了一圈回到 A，CAS 一看"还是 A"，就以为风平浪静，其实世界已经变过了（比如那个指针被释放又复用，指向了完全不同的对象）。

有意思的是：**ARM 的 LL/SC 天生免疫 ABA。** 因为它的监视器盯的根本不是"值变没变",而是"这个地址被写过没有"——A→B→A 中间的那两次写，会直接打掉监视器，让 store-conditional 失败。同一个"原子 RMW"的目标，x86 选了会踩 ABA 的 CAS，ARM 选了不踩 ABA 的 LL/SC，这是两套硬件世界观的又一次分道。

那 x86 为什么不干脆抄 LL/SC？因为各有代价。LL/SC 更灵活（你能在 LL 和 SC 之间塞任意计算），还免疫 ABA；但它有**虚假失败（spurious failure）**——一次上下文切换、一个中断、甚至监视器粒度（常是一整条 cache line）上的伪共享，都能让 SC 无辜失败、逼你重试。而 CAS 没有虚假失败，行为更好预测、对编译器更友好，代价就是得自己提防 ABA（常见解法是给值加一个版本号，值和版本号一起 CAS）。没有谁绝对更好，是 CISC 与 RISC 两条路各自的自洽选择。

## 一个 Go 工程师真会踩的坑：对齐

原子操作要求地址**自然对齐**。x86 上一个没对齐的原子操作会退化成那个暴力的总线锁，ARM 上则直接 fault。Go 因此有一个著名的历史陷阱：在 32 位平台（32 位 ARM、386）上，对 `int64` 做原子操作要求它 **8 字节对齐**，而结构体的字段排布会影响对齐——如果你把一个 `int64` 放在结构体中间、前面垫了个 `int32`，它就可能不是 8 字节对齐，运行时直接 panic。老代码里那条"把 64 位原子字段放结构体第一个"的玄学惯例，根源就在这。Go 1.19 之后提供了 `atomic.Int64` 这类带对齐保证的类型，这个坑才算被语言层正式堵上——又一次印证 A 的主题：**上层包装替你把硅层的脏活默默干了。**

## 收口

原子性不来自"一条指令"，来自一套"让 RMW 中途不可被打断"的硬件机制：x86 用 `LOCK`（现代锁一条 cache line，而非总线），ARM 用 LL/SC（挂监视器 + 条件写 + 重试），新 ARM 又补了单指令的 LSE。CAS 是这套机制最有用的形态，也是乐观锁的硅层本体；x86 与 ARM 在"如何实现原子"上选了两套自洽的哲学，连要不要为 ABA 操心都因此不同。而无论哪一套，"独占一条 cache line"这件事都绕不开——这正是下一面墙 C 的火种：当很多核同时来抢同一条线，原子操作会以一种最反直觉的方式崩掉——**核越多，越慢。**
