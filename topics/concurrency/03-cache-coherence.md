# C · 核越多反而越慢——瓶颈根本不在 CPU

## 一个数字摆出来，直觉就崩了

下面是同一个 `atomic.AddInt64`，在一台 8 核（6 性能核 + 2 能效核）的 Apple M 系列上跑的基准测试，唯一变化的变量是**参与的核数**：

```
                     1核        2核        4核        8核
共享单计数器      7.23 ns   22.50 ns   45.52 ns   60.63 ns
分片计数器        7.22 ns    6.92 ns    3.81 ns    2.34 ns
```

第一行：所有核抢同一个计数器，**核越多越慢**，8 核比 1 核慢了 8 倍。第二行：换一种写法，**核越多越快**，8 核比 1 核快了 3 倍——这才是并行该有的样子。8 核时两者相差 **26 倍**。

同一条 CPU 指令、同样的加法，差别只在一件事：**大家抢不抢同一个变量。** 要讲清这 26 倍从哪来，得钻进 CPU 的缓存里看一场你平时完全看不见的争夺战。

## 先排除一个错误答案

最容易脱口而出的解释是"高竞争下原子操作在自旋空转，浪费 CPU"。但这是错的。在这台机器上，`atomic.Add` 编译成单条 `LDADD` 指令，**它根本不自旋**（这一点在上一面墙已经反汇编验证过）。它每次只老老实实做一次加法，没有任何重试循环。

所以慢，不是因为 CPU 在空转。CPU 其实闲得很。慢在一个 CPU 之外、你看不见的地方——**那条存着计数器的缓存行，在核与核之间被反复抢夺。**

## MESI：一条缓存行的"独占权"争夺

每个 CPU 核都有自己的私有缓存（L1/L2）。当多个核都缓存了同一块内存，谁也不能各改各的，否则就乱套了。协调它们的，是缓存一致性协议 **MESI**。一条缓存行（cache line，通常 64 字节）在每个核的缓存里，时刻处于四种状态之一：

- **M**odified——我改过它，我手上这份是全世界最新的，别人都没有。
- **E**xclusive——只有我缓存了它，但我还没改。
- **S**hared——好几个核都缓存了它，大家只读、值一致。
- **I**nvalid——我这份已经作废，要用得重新去拉。

整个故事的关键只有一条规则：**一个核想写一条缓存行，必须先独占它（拿到 M 或 E 态）；而独占的代价，是把其他所有核手里的那一份全部作废（打成 I）。**

现在把这条规则套到 8 个核都在 `atomic.Add(&shared, 1)` 上：

1. 核 1 要写，先广播一条"读独占"请求，把核 2~8 缓存里的那份计数器全打成 I，自己进入 M 态，然后写。
2. 轮到核 2 写。它一看自己那份是 I（刚被核 1 作废了），得先**把整条缓存行从核 1 那里拉过来**，再广播独占、把核 1 和其余核打成 I，才能写。
3. 核 3 要写，重复上面一整套……

于是这条缓存行就在 8 个核的缓存之间被**踢来踢去**，每一次 `Add` 背后都拖着一轮跨核的一致性事务，要走片上互联总线。这就是 **缓存行乒乓（cache line ping-pong）**。参与的核越多，抢同一条行的人越多，乒乓越疯狂——所以核越多越慢。慢的从来不是那个加法，是这条行的"所有权"在反复交接。

把上一面墙那句话拎回来就全通了：**"加锁"在硬件上等价于"独占一条缓存行"。** 一个被多核高频写的共享原子变量，本质上就是一个永远在被争夺独占权的点，它必然成为一个串行化的咽喉。瓶颈不在指令快慢，在这条行本身。

## 伪共享：你明明没共享，硬件替你共享了

第二组数字更阴险。两个 goroutine，一个**只**写变量 `a`，一个**只**写变量 `b`，从头到尾谁也不碰对方：

```
a、b 紧挨着定义（同一条缓存行）   43.24 ns/op
a、b 之间塞 padding 推到两条行    13.79 ns/op   ← 快 3 倍
```

逻辑上这俩操作零冲突，凭什么慢 3 倍？因为**硬件一致性的最小单位是缓存行，不是变量**。`a` 和 `b` 恰好落在同一条 64 字节的行里，于是核 1 写 `a`，按上面的规则，要独占这条行——顺手就把核 2 缓存里那条（同时装着 `b` 的）行打成了 I；核 2 写 `b` 时又得把行抢回来，再把核 1 的打作废。两个毫不相干的变量，因为"住在同一间 64 字节的屋子里"，被迫替对方反复作废缓存。

这就是**伪共享（False Sharing）**：你以为没共享任何数据，但硬件以缓存行为粒度，擅自把它们当成了一个整体。它格外难抓，因为代码读起来完全正确、毫无竞争痕迹，性能却莫名其妙地差。

## 解法只有一个核心：别让大家抢同一条行

既然病根是"多核抢同一条缓存行"，药方就一句话——**分散竞争**，落地两招，刚好对应上面两组数字：

**分片（Sharding）**：把一个共享计数器拆成一组，每个核去加自己那一片，读取时再把所有片加起来。竞争被打散到 N 条不同的行上，冲突概率降到 1/N。

**填充（Padding）**：给每个热点变量补足字节，让它独占一整条缓存行，连伪共享都掐掉。

上面那个跑出 2.34 ns 极速的分片计数器，就是两招叠加：

```go
const shards = 256

type paddedCell struct {
    v int64
    _ [56]byte // 8 + 56 = 64：占满整条缓存行，谁也别想跟我同住
}

var cells [shards]paddedCell
```

但要立刻补一句平衡的话，否则就把"分片 + padding"念成了万能咒：**它不免费，所以不要无脑用。** 256 个 cell 各垫 56 字节，光这个计数器就吃掉约 16KB；而且分片后想读"总数"得把所有片加一遍（`Sum()` 是 O(分片数)）。在低竞争下，单个原子变量那 7ns 完全够用，分片只是徒增内存和复杂度。**正确的顺序永远是：先测出某条行真的是热点，再对它分片或 padding——而不是预防性地给每个变量都套上。** 那个 8 倍的差距，只在真有 8 个核往死里抢一个变量时才出现。

顺带回答一个会冒出来的疑问：分片版在 8 核（2.34ns）反而比 1 核（7.22ns）更快，这是 benchmark 假象吗？不是，这是**真并行**——8 个 worker 各写各的缓存行、互不作废，吞吐量真的叠加上去了，所以每次操作的墙钟时间被摊薄。这恰恰是"没有竞争时多核应该带来的线性加速"的样子，和第一行那条越加越堵的曲线形成残酷对照。

## 三道面试题在这里同时被点亮

C 这面墙一立，材料里三道原本孤立的题，瞬间连成一条因果链：

**主问 3 下半（高竞争下的原子操作怎么办）。** 材料给的归因是"自旋空转 + cache 乒乓"。经过 B、C 的校正，前半截要划掉——现代硬件上 `atomic.Add` 不自旋——真正且唯一的瓶颈，就是 cache 乒乓。而它开的药方"分片 + padding"是对的，上面的 benchmark 就是铁证：从 60.63ns 砍到 2.34ns。

**延伸题 1（RWMutex 什么时候反而比 Mutex 慢）。** 谜底正在这。`RWMutex` 内部维护一个 `readerCount`，**每一次 `RLock`/`RUnlock` 都要原子地加减它**。也就是说，所有读者其实都在争抢同一个共享计数器——正是我们刚眼看着崩掉的那个东西。临界区一短、核一多，这个 `readerCount` 缓存行的乒乓开销，就盖过了"允许多个读者并发"省下来的那点收益。所以在多核、短临界区的场景，RWMutex 会输给普通 Mutex，甚至输给直接用 atomic。它慢，慢在**记账用的那个计数器本身就是个 cache 热点**。

**延伸题 3（sync.Pool 的 per-P 设计）。** 这道题是**解法本身**的化身。给每个 P 一个本地池，就是"分片"——让每个核优先操作自己那一份，不去抢全局那条行。为什么绑定到 P 而不是 goroutine？因为 P 的数量固定（等于 GOMAXPROCS），而且同一时刻一个 P 上只跑一个 G，本地访问天然没有并发、连原子操作都省了。它和上面那个分片计数器，是一模一样的思想。

## 这是最不挑语言的一面墙

A 和 B 还能看出 Go、C++、Rust 各自的世界观；到了 C，**几乎没有语言差异——因为 MESI 是 CPU 的协议，不属于任何语言。** 最好的证据是：各语言的解法长得几乎一字不差。

- Java 的 `LongAdder`，就是分片计数器——一个 `base` 加一组 `Cell`，每个 `Cell` 还用 `@Contended` 注解自动 padding。
- C++ 要你手动 `alignas(64)` 或塞填充字节。
- Go 就是上面那个 `[56]byte`。

这恰恰是"底层原理是否通用、各语言是否只是上层包装"这个问题最强的证据：到了缓存一致性这一层，所有语言面对的是同一块硅、同一个乒乓难题，连药方都相同。**越往硬件走，差异越小，通用性越强。** 上层的锁、channel、原子封装千姿百态，底下顶着的是同一面墙。

## 收口：多核世界里，竞争的单位是缓存行

把 A、B、C 串起来，会浮出一个能重塑直觉的心智模型：**在多核上谈并发性能，争抢的基本单位不是变量、不是锁，是一条 64 字节的缓存行。** 一把锁、一个原子计数器、一个引用计数，甚至两个恰好同住一条行的无关变量——任何被多核高频写入的"点"，都是一个会随核数增多而越来越堵的串行咽喉。

所以优化并发的第一问，从来不是"这个操作本身多快"，而是"有多少个核在抢同一条缓存行"。下一面墙换个角度逼近同一组问题：当你**抢不到**的时候，到底该原地傻等（自旋），还是干脆躺下睡觉（挂起让出 CPU）——以及 Go 凭什么能让一个 goroutine 睡得比一个操作系统线程便宜得多。

## 附：复现用的基准测试
```go
// go test -bench='SharedCounter|ShardedCounter' -benchtime=300ms -cpu=1,2,4,8
var shared int64
func BenchmarkSharedCounter(b *testing.B) {
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() { atomic.AddInt64(&shared, 1) }
    })
}

const shards = 256
type paddedCell struct{ v int64; _ [56]byte }
var cells [shards]paddedCell
var idx int64
func BenchmarkShardedCounter(b *testing.B) {
    b.RunParallel(func(pb *testing.PB) {
        i := atomic.AddInt64(&idx, 1) % shards
        for pb.Next() { atomic.AddInt64(&cells[i].v, 1) }
    })
}
```
