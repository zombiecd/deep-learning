# 存储引擎的物理学 · 深讲十问

> 脊梁："写进数据库了"是一句要拆开好几层的话。持久化工程的全部，就是和每一层的"善意谎言"与重排序作斗争——这和并发的内存可见性是同一道数学题。

## 1 · `write()` 成功 = 落盘了吗？连 fsync 也撒谎

你调了 `write()`，它返回成功。数据安全了吗？**没有。** 它大概率只是从你的进程内存，被拷进了**内核的 page cache**——一块内核管理的"待写"内存。`write()` 返回的意思仅仅是"内核收下了"，不是"盘上有了"。此刻断电，这数据就跟没写过一样。

那 `fsync()` 呢？`fsync` 才是那句"求你真的写到盘上去"的命令，它会阻塞到内核把这个文件的脏页刷给存储设备。理论上 fsync 返回 = 落盘了。**但 fsync 也会撒谎，而且撒谎的地方不止一处：**

- **硬件那一层**：很多消费级硬盘自带一块易失的写缓存。fsync 把数据交给磁盘，磁盘把数据收进自己的缓存、立刻回一句"好了"，然后才慢悠悠真正写到盘片——这中间断电，数据照样飞。要堵这个洞，得靠带掉电保护（断电时用电容/电池把缓存刷完）的企业级盘，或确认 FLUSH 命令真被尊重。
- **文件系统/内核那一层**：2018 年著名的 "fsyncgate"——PostgreSQL 团队发现，某些内核下 fsync 遇到回写错误后，**会把错误"吞掉"**：第一次 fsync 报错，第二次 fsync 却返回成功（因为脏页标记已被清掉），让上层误以为落盘成功，实则数据已丢。这一个内核行为，逼得好几个数据库改了崩溃恢复逻辑。
- **目录项那一层**：你 fsync 了文件内容，却没 fsync 它所在的**目录**——崩溃后文件内容在盘上，但"这个文件叫什么、在哪"这条目录信息没落盘，文件可能**找不回来**。新建文件后要既 fsync 文件、又 fsync 父目录，才算数。
- **虚拟化/网络存储那一层**：跑在云上、容器里、网络盘上，你的 fsync 可能还要穿过 hypervisor、穿过网络协议，每一层都可能再缓存一道。

**所以"持久化"这个词，到底在哪一层兑现？** 答案是：**只有当从你的进程一路到稳定介质的每一层，都老实尊重了写屏障，它才兑现。** 这就是开篇说的"和并发是同一道题"——内存模型里，一个写要对另一个线程可见，必须有 happens-before 屏障逼着缓存刷出去；存储里，一个写要对"未来的崩溃"可见，必须有 fsync 这道屏障逼着数据一层层落到稳定介质。**fsync 就是持久化世界的内存屏障。** 少一道，下层就有权把你的写攥在手里、断电时若无其事地扔掉。

打个比方：`write()` 是把信投进公司内部收发室（"收到了"），fsync 是要求邮局真的把信送达。但邮局可能把信扔进自己的待发筐就回执"已寄出"（硬件缓存），可能弄丢了还谎报送达（fsyncgate），可能送到了楼下却没人知道这信是给谁的（没 fsync 目录）。"寄到了"是一条信任链，断一环就不算数。

- **可验证**：读 PostgreSQL 的 fsyncgate 邮件线程和后续的 "PostgreSQL's fsync() surprise" 文章；用 `fio` 带 `--fsync=1` 对比有无 fsync 的写吞吐，亲身感受 fsync 有多贵（也就明白了为什么数据库要想方设法少 fsync——下一问）。

## 2 · WAL：为什么写两次反而更安全、更快

几乎每个正经数据库的命根子都是 **WAL（Write-Ahead Logging，预写日志）**，规矩只有一句：**改任何数据之前，先把"我要做的这个改动"追加写进一个日志文件、并 fsync 它；之后才慢慢去改真正的数据页。** 听起来很怪——同一份改动写了两遍（先写日志、迟早还要写数据），怎么会比直接写一遍数据更安全、还更快？

**先说"更安全"。** 崩溃随时可能在"改了一半"时降临。如果你直接原地改数据页，崩在中间，数据页就处于一个半新半旧的损坏状态，没人知道该信哪部分。有了 WAL，崩溃恢复时只要重放日志：日志里记着"事务 T 提交了、它的改动是 X"，就把 X 重做（redo）一遍；日志里只记了一半、没记到"提交"的事务，就当它没发生（或按 undo 信息回滚）。**日志成了"什么算数"的唯一权威**——一笔事务只有当它的提交记录 fsync 进了日志，才算真的提交了（这正是第 7 问"exactly-once"和数据库 durability 的交汇点）。原子性和持久性，都挂在这条日志上。

**再说反直觉的"更快"，这才是精髓。** 关键在两种写的物理代价天差地别：

- **日志写是顺序追加**：永远往文件末尾续，磁头不用乱跑（HDD 上这是天与地的差别），一次 commit 往往只需**一次顺序 fsync**。
- **数据页写是随机散布**：你改的那些行可能分布在盘上四面八方，挨个去原地改是**随机写**——HDD 上每次都要寻道，慢得令人发指；SSD 上也触发写放大（第 10 问）。

WAL 的魔法就是**把代价重新分配**：commit 时，只付"一次顺序追加 + 一次 fsync"这个便宜账（用户等的就是这一下）；那些昂贵的随机数据页改写，**推迟到后台慢慢做**——可以攒一批一起刷（合并多次改动）、可以挑空闲时刷、可以让操作系统顺手优化。于是"同步的随机写"（慢）被换成了"此刻的顺序写 + 将来的、批量的、懒惰的随机写"（快）。**写两次，但把那次贵的从关键路径上挪走了**，所以总体更快。

打个比方：厨房用一条顺序的"点菜导轨"记下每一单（写得飞快、严格有序、一次落定），厨师再不慌不忙地按单备菜、装盘（懒惰、可批量）。万一厨房中途失火（崩溃），那条导轨告诉你哪些单子是已确认的，照着重做就行；没上导轨的，就当没点过。

**判断的落点**：理解了 WAL，你就懂了一串现象——为什么数据库 commit 的瓶颈常在"日志盘的 fsync 能力"（所以日志盘要快、要单独放）；为什么"组提交（group commit）"能提吞吐（攒多个事务的日志一次 fsync，把那次贵的 fsync 摊薄）；为什么 `innodb_flush_log_at_trx_commit` / `synchronous_commit` 这些参数是在"每次 commit 都 fsync（最安全最慢）"和"攒一会儿再 fsync（快但崩溃可能丢最后几毫秒的已提交事务）"之间让你**亲手选一致性和性能的兑换比**。

- **可验证**：把 MySQL 的 `innodb_flush_log_at_trx_commit` 在 1 和 2 之间切换，压测看 TPS 差几倍——那个差，就是"每次 commit 都 fsync"的代价，也是组提交存在的理由。

## 3 · B+ 树为什么"矮胖"——它在迁就谁

数据库索引几十年来的霸主是 B+ 树。它长得很怪：不是我们写算法题时熟悉的"瘦高"二叉树，而是**矮胖**的——一个节点里塞着成百上千个 key，整棵树却只有三四层高。为什么？因为它的每一个设计，都在迁就**一个事实**：磁盘按"页/块"读写，且随机寻道极慢。

把这个事实摊开：磁盘不是按字节读的，是按**页**（典型 4KB～16KB）一次一整页地读；而读不同位置的页，HDD 要移动磁头寻道（毫秒级，慢得像地质年代），SSD 也有不可忽略的随机访问开销。所以对存储引擎来说，**性能几乎只由一个量决定：一次查询要读多少个页（= 多少次随机 IO）。** 一切设计都为压低这个数服务。

于是 B+ 树的每个怪相都有了解释：

- **为什么节点那么"胖"（扇出几百上千）**：一个节点 = 一个页。既然读一页和读一个字节代价差不多（都得付一次 IO），那就把这一页塞满 key——一页能放下几百个 key，每个 key 带一个指向下层的指针，于是一个节点能岔出几百个孩子（高扇出）。
- **为什么树那么"矮"**：扇出几百，意味着每下一层，能覆盖的数据量乘以几百。三四层就能索引几亿、几十亿行。**树高 = 一次查询的随机 IO 次数**，矮，就是快。对比一下：同样几十亿行，二叉树要 30 多层，就是 30 多次随机 IO——慢一个数量级还不止。
- **为什么叶子节点串成链表**：所有真实数据/指针都在最底层的叶子上，叶子之间用指针首尾相连。这样做范围查询（`WHERE age BETWEEN 20 AND 30`）时，定位到起点后，**顺着链表横扫**就行，不用每读一条都从树根重新往下找。范围扫描因此变成顺序的，又快又省。

**这里藏着一个反直觉、也最能体现"第一性原理"的拷问：把 B+ 树搬进全是内存、随机访问免费的世界，它还是最优解吗？** 不是。B+ 树的全部精妙都建立在"随机 IO 极贵、所以要按页批量读、要压低树高"之上。这个前提一旦消失（纯内存数据库，随机访问和顺序访问几乎一样快），高扇出、按页组织带来的好处就大打折扣，甚至那些用来填满页的额外 key 反而成了缓存不友好的负担。所以纯内存的系统（Redis、各种 in-memory 引擎）压根不用磁盘式 B+ 树，转而用哈希表、跳表、字典树这些更贴合"内存访问模型"的结构。**B+ 树不是绝对最优，是"针对磁盘存储层级"的最优**——它优化的对象不是"比较次数"，是"随机 IO 次数"。看懂一个数据结构在为哪种硬件代价做优化，比记住它的形状重要一百倍。

- **可验证**：自己算一遍——页 16KB、每个 key+指针约 16 字节，扇出约 1000；那么 3 层能覆盖 10 亿条（1000³）。再对比二叉树 log₂(10⁹) ≈ 30 层。两个数字一摆，"矮胖"的理由不言自明。

## 4 · LSM 凭什么挑战 B+ 树，compaction 为什么是双刃

B+ 树统治了读密集的世界，但写密集场景（日志、时序、海量 KV 写入）杀出了 LSM-tree（Log-Structured Merge-tree，RocksDB / LevelDB / Cassandra / 你日常的很多 NoSQL 都用它）。它凭什么？凭一句话：**把随机写，变成顺序写。**

B+ 树的痛处在写：要改一行，得找到那一行所在的叶子页，**原地改**——这是随机写（第 3 问说过随机写贵）。写得越多、越分散，随机 IO 越多。LSM 换了个思路：

- 新写来了，先进**内存里的有序表（memtable）**（同时追加 WAL 保命），根本不碰磁盘上的旧数据。
- memtable 满了，整个**顺序刷成一个磁盘上的有序、不可变文件（SSTable）**——一次大块顺序写，飞快。
- 读的时候，可能要从新到旧查好几个 SSTable（因为同一个 key 的新值在新文件、旧值在旧文件），直到找到。
- 后台有个进程不断把多个 SSTable **归并、排序、丢弃被覆盖/被删除的旧值**，合成更大更整齐的文件——这就是 **compaction（合并）**。

LSM 的本质，是在**三种"放大"**之间重新下注：

- **写放大**：同一份数据，在 compaction 中被反复读出来、合并、再写回去，物理上写了好多遍。
- **读放大**：一次读可能要查多个层级的多个文件（靠布隆过滤器和分层来缓解，但仍比 B+ 树一次定位多）。
- **空间放大**：旧版本、墓碑（第 8 问）在被 compaction 清掉之前，占着额外空间。

这里有个深刻的"不可能三角"，叫 **RUM 猜想**：读开销（Read）、写开销（Update）、内存/空间开销（Memory），你**最多同时优化两个**，第三个必然被牺牲。B+ 树押注读优（读放大小、空间紧凑），代价是写放大（随机写）；LSM 押注写优（顺序写、写吞吐高），代价是读放大和空间放大。**所以根本没有"更好的引擎"，只有"针对你的读写比，把赌注押对了的引擎"**——写多读少（埋点、日志、IoT），LSM 赢；读多写少且要复杂查询（典型 OLTP），B+ 树赢。一个工程师的判断力，就体现在能不能看穿"这个选型在拿什么换什么"。

**而 compaction 是 LSM 的灵魂，也是它的命门——典型的双刃：**

- **是优势来源**：正是 compaction 在后台默默把读放大压住（文件别堆太多）、把空间放大收回（清掉旧值墓碑）、把数据排整齐。没有它，LSM 读会越来越慢、盘会越撑越满。
- **是尾延迟杀手**：compaction 是个吃 IO、吃 CPU 的后台重活。它一发力，就和前台的读写抢资源，造成**周期性的延迟尖峰**（p99 突然飙高，对应可观测性主题的尾延迟）。更糟的是"写停顿（write stall）"：如果写入速度长期超过 compaction 的消化速度，文件堆积失控，引擎会**主动限速甚至暂停写入**逼你慢下来——一次设计不当的批量灌数据，能把 LSM 引擎逼进写停顿，整个服务卡死。

- **可验证**：跑 RocksDB 自带的 `db_bench`，开 compaction 统计，看写放大系数（常常是 10 倍以上）和 compaction 期间的延迟毛刺；把写入速率调到超过 compaction 能力，亲手制造一次 write stall。

## 5 · 隔离级别，和内存模型的乱序自由为什么同构

"数据库帮我保证了 ACID，并发我不用操心"——这是个会让你在并发场景翻车的误解。事务隔离级别（读未提交 → 读已提交 → 可重复读 → 串行化）这一档档放松，本质上和[并发原理](../../并发原理/)主题里"内存模型暴露多少乱序自由"是**同一个结构**：**都在用"放弃一部分正确性保证"换取"更高的并发/性能"，并把放弃掉的那部分风险，悄悄甩回给你。**

先把对应关系挑明：

- **内存模型**：CPU 和编译器有权重排你的读写，给你"看起来乱序"的世界。你想要某个写对某个读保证可见，就得用同步原语建立 happens-before（付出同步开销）。默认是弱的，强一致要你显式去买。
- **隔离级别**：并发事务之间有权"看见彼此的中间状态、以你想不到的顺序交错"，给你各种"异常（anomaly）"。你想杜绝某种异常，就得调高隔离级别（付出加锁/重试开销）。默认也是弱的，串行化要你显式去买。

**每一档隔离级别，精确对应"你愿意容忍哪些异常"**：

- **读已提交（RC）**：杜绝脏读（不会读到别人没提交的数据），但允许**不可重复读**（你在一个事务里读同一行两次，中间别人改了并提交，两次值不同）。
- **可重复读（RR）**：同一行你读多少次都一样，但（在标准定义下）允许**幻读**（你按条件查一批行，别人插了一行也满足条件，你再查范围就多出一行"幻影"）。
- **串行化（Serializable）**：表现得像所有事务一个接一个排队跑，杜绝一切异常。最强、最贵。

**为什么默认几乎从不是串行化？** 因为串行化要么靠大量加锁（读也加锁、范围也锁，并发被压垮），要么靠"乐观执行 + 冲突就让一方失败重试"（SSI，可串行化快照隔离）——两条路都付出可观的吞吐代价。所以 MySQL 默认 RR、PostgreSQL 默认 RC，数据库**默认就在拿正确性换性能**，把残留的风险留给你。

那个最该被你记住的残留风险，叫**写偏序（write skew）**——它正是"两个对的局部操作，组合出全局错误"的数据库版，和并发主题里"两个对的局部重排组合出错"是同一个幽灵。经典例子：医院规定"任意时刻至少留一名医生值班"。两名值班医生 Alice 和 Bob 同时想请假，各自开个事务：读到"当前值班人数 = 2，≥ 1，没问题"，于是各自把自己改成休息。两个事务**单独看都遵守了规则**（都检查了"还有别人在"），但一起提交后，值班人数变成 0，规则被破坏。在 RR 下这能发生（两个事务读的是各自快照，谁也没看见对方的修改），只有串行化（或显式 `SELECT ... FOR UPDATE` 把那次检查加锁）才挡得住。

**判断的落点**：和内存模型一模一样——**默认是弱保证，强一致要你显式去买**。你写并发事务时，必须主动问："我这段逻辑依赖了'读到的值在我写之前不会被别人改'吗？" 如果依赖，而隔离级别又没强到能保证，你就埋了一个写偏序的雷。`SELECT ... FOR UPDATE`、唯一约束、显式提升隔离级别，就是数据库世界的"内存屏障"。

- **可验证**：开两个 `psql` 会话，都设 `REPEATABLE READ`，手动复现一次写偏序（各自读同一个计数、各自基于它写）——亲眼看见两个"都对"的事务合谋破坏了不变量；再加 `FOR UPDATE` 看它怎么被挡住。

## 6 · MVCC 为什么读写不互锁，长事务为什么是诅咒

老式的读写锁有个让人难受的地方：读要加读锁、写要加写锁，读写互斥——一个大查询在跑，写就得等；一个写在改，读就得等。高并发下这是灾难。现代数据库（PostgreSQL、MySQL InnoDB、Oracle）几乎都用 **MVCC（多版本并发控制）** 绕开了它，做到"**读不阻塞写，写不阻塞读**"。它靠的什么魔法？

魔法就一句：**不要原地覆盖，给每行保留多个带版本戳的副本；每个事务只看属于自己那个"快照"的版本。**

具体说：每行数据带着"哪个事务创建的、哪个事务删除的"这种版本信息。当一个写事务要改某行，它**不抹掉旧版本，而是造一个新版本**，旧版本还留着。这时：

- **读事务**按自己开始时的快照，去读那个"在我这个时间点该看到的版本"——它读到的是旧版本，根本不在乎有没有人正在写新版本。**读不需要等写。**
- **写事务**造新版本，不影响别人读旧版本。**写不需要等读。**

读写就这样在"不同版本"上各行其是，互不阻塞。这也顺带实现了上一问的快照隔离——你整个事务看到的是一个一致的、定格在某一刻的世界。

**但天下没有白吃的魔法，代价是版本会堆积。** 旧版本不能马上删——因为可能还有别的、开得早的事务的快照需要看它。于是数据库需要一个后台清理工（PostgreSQL 叫 **VACUUM**，InnoDB 叫 purge）去回收那些"已经没有任何活跃快照需要的旧版本"。正常情况下清理工跟得上，版本不会失控。

**长事务为什么是诅咒？** 这就是 MVCC 最深的坑。清理工能删一个旧版本的前提是"没有任何活跃事务的快照还需要它"。而一个**迟迟不提交的长事务**（比如一个跑了一小时的大报表，或者更阴险的——一个忘了提交、卡在 `idle in transaction` 的会话），它持有一个**很老的快照**，等于在宣布："从我开始那一刻之后产生的所有旧版本，都可能被我用到，谁也不许删！" 于是清理工被它**死死摁住**——哪怕这一小时里别的事务疯狂地增删改、产生了海量旧版本，一个都回收不了。结果：表和索引疯狂**膨胀（bloat）**，盘越撑越大，查询要在一堆死版本里翻找、越来越慢。**一个忘了 commit 的会话，能把整个 PostgreSQL 拖垮**——这是 PG 运维的头号经典事故。

打个比方：图书馆允许"借出旧版、同时上架新版"（多版本，读写不互锁）。但有个读者借了一本旧版说"我还在看，别销毁"，然后**人间蒸发了一小时**。于是这一小时里所有被替换下来的旧版书，图书馆一本都不敢销毁（万一那个失踪读者要对照呢），仓库迅速被废书塞爆——这就是长事务 + MVCC 的膨胀。

- **可验证**：PostgreSQL 里开一个事务执行 `SELECT 1` 然后**不提交**晾着，另一个会话疯狂 update 同一张表，观察 `pg_stat_user_tables` 里 dead tuples 暴涨、`VACUUM` 却回收不掉；`SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction'` 就是抓这种诅咒的探照灯。

## 7 · 索引为什么在写密集是负优化，最左前缀是物理推论

"查询慢？加个索引。"——这条本能在读场景几乎总对，但它藏着两个必须想透的反面，否则你会在写密集场景给自己埋坑，也会对"为什么这个索引没生效"百思不解。

**反面一：每个索引都是一棵要同步维护的独立 B+ 树，所以索引在写密集场景是负优化。**

想清楚索引的物理本质：一个 `(age)` 索引，是一棵**独立的 B+ 树**，按 age 排好序、叶子指回真实行。你建了 5 个索引，就是 5 棵独立的树。现在你 `INSERT` 一行——主表要写，**那 5 棵索引树每一棵都得插入一个新条目、可能触发节点分裂**。一次写，变成了 1 + 5 次结构维护（这又是一种写放大）。所以：

- 读密集的表，索引多多益善（查询挑着用）。
- **写密集的表，每多一个索引，每次写都更慢一点。** 一张高频写入的表挂了十几个"以防万一"的索引，写入性能会被悄悄拖垮。索引不是免费的查询加速器，是"读变快、写变慢"的兑换——这个兑换比，要按这张表的读写比来判断（呼应第 4 问 LSM 的同一种思维）。

**反面二：覆盖索引、最左前缀不是数据库的随意规定，是 B+ 树物理结构的直接推论。**

- **覆盖索引（covering index）**：如果一个查询要的列，**全在索引里**（索引的 key + 它顺带存的列），数据库读完索引就能交差，**不用再回主表捞那一行**（省掉一次"回表"的随机 IO）。这不是什么高级特性，就是"叶子节点里已经有你要的全部数据了，何必再跑一趟"的朴素推论。
- **最左前缀（leftmost prefix）**：一个联合索引 `(a, b, c)`，它在物理上是**先按 a 排序，a 相同的再按 b 排序，b 也相同的再按 c 排序**——像电话簿先按姓、同姓按名排。于是：
  - `WHERE a = 1`：能用（直接定位到 a=1 那段）。
  - `WHERE a = 1 AND b = 2`：能用（a=1 段里 b 又是有序的）。
  - `WHERE b = 2`（不带 a）：**用不了**——因为 b 只在"相同 a 内部"有序，全局是乱的，就像你想在电话簿里只按"名"找人，整本都得翻。
  
  这条规则不是 DBA 拍脑袋定的，是排序的物理事实逼出来的：**没排序的维度，索引帮不上忙。**

最后那个经典考题—— `WHERE a = 1 ORDER BY b` 能不能免去排序？取决于索引列顺序：用 `(a, b)`，定位到 a=1 那段后，里面的行**本来就按 b 排好了**，直接顺序读出即满足 `ORDER BY b`，**零排序开销**；用 `(b, a)` 就不行，得先捞出 a=1 的行再额外排一次序（`EXPLAIN` 里会出现 "Using filesort"）。**索引能不能省掉排序，是它物理有序性的直接结果。**

- **可验证**：`EXPLAIN`（MySQL）/ `EXPLAIN ANALYZE`（PG）你的查询，看 `key`/`Index Scan` 是否命中、有没有 `Using filesort` / `Sort` 节点；把联合索引列顺序调一下，看执行计划怎么变——一手验证"最左前缀"和"索引消序"。

## 8 · 删除为什么是写墓碑，删完为什么更慢

"我删了几百万行，为什么磁盘没释放、查询反而更慢了？"——这是个让无数人懵掉的现象。根因是：**在很多存储引擎里，"删除"压根不是真的把数据抹掉，而是写一个"已删除"的标记，叫墓碑（tombstone）。**

为什么不能当场抹掉？两个场景，两种原因，但都指向"数据在物理上不方便/不允许立刻消失"：

- **LSM 引擎里**（第 4 问）：数据存在**不可变**的 SSTable 文件里——不可变意味着你根本不能去文件里把某条抠掉。于是"删除 key K"这个操作，本身也只能作为一条新记录**追加**进去：一条写着"K 已删除"的墓碑。读 K 时，引擎从新到旧找，先撞上墓碑，就知道"它删了"，返回不存在。真正的物理清除，要等到 **compaction** 时，归并过程中发现"K 有墓碑且没有更新的写"，才把 K 的所有旧版本和墓碑一起丢弃。
- **MVCC 引擎里**（第 6 问）：删除一行 = 给它的当前版本打上"被某事务删除"的戳，旧版本还得留着——因为别的、开得早的事务的快照里，这行可能还"活着"。真正的空间回收，要等 **VACUUM/purge** 确认没有任何快照需要它。

**于是"删完更慢、空间不降"就顺理成章了：**

- **空间没降**：数据（和新增的墓碑）都还在盘上，要等后台合并/清理才回收。PostgreSQL 里普通 `DELETE` 之后，空间甚至不会还给操作系统（只是标记为可复用），要 `VACUUM FULL`（锁表重写）才真正缩盘。
- **查询更慢**：你以为删空了的范围，物理上**塞满了墓碑/死版本**。一个范围扫描得吭哧吭哧扫过这一大片"已删除但还没清理"的垃圾，才能凑齐真正存活的行。Cassandra 有个臭名昭著的"墓碑问题"：对一个被大量删除的分区做范围查询，要扫过成千上万个墓碑，慢到超时、甚至直接把节点 OOM——因为它得把这些墓碑都读进内存来判断"这些都删了"。

打个比方：图书馆"下架"一本书，不是马上从书架抽走拉去销毁（太费事，还可能有人正借着旧版），而是在书的位置插一张"此书已下架"的卡片。书架上于是堆着越来越多的下架卡片，你找一本在架的书，得拨开一堆卡片才够得着——直到管理员某天集中清架（compaction/vacuum），卡片和废书才真被搬走、空位才腾出来。

**判断的落点**：这条认知直接改变你的运维判断——大批量删除不是"删了就完事"，而是制造了一大批待清理的垃圾，要么紧跟一次手动 compaction/VACUUM，要么用更聪明的方式（按时间分区然后**直接 DROP 整个分区**，那是真删、瞬间释放，绕开墓碑机制）。"删除很便宜"是直觉，"删除其实是延迟昂贵"才是真相。

- **可验证**：PostgreSQL 里 `DELETE` 掉一张大表的大部分行，看 `\dt+` 表大小**纹丝不动**，`pg_stat_user_tables` 里 dead tuples 暴涨；再 `VACUUM FULL`，看空间这才回收。Cassandra 里可观察 `tombstone_warn_threshold` 的告警。

## 9 · 信任 OS page cache vs 自建 buffer pool，O_DIRECT 为什么存在

数据库要反复读热数据，总得缓存。这里有个有趣的"内战"：**到底该信任操作系统的 page cache，还是自己在进程里再建一层缓存？** PostgreSQL 大体选了前者（只留一小块 shared_buffers，主要靠 OS 缓存），MySQL InnoDB 选了后者（自建一大块 buffer pool）。两条路都活得好好的，这说明背后是个真实的权衡，不是谁蠢。

先理解那个"浪费"：操作系统本来就会把读过的文件页缓存在 page cache 里。如果数据库**又**在自己进程里建一层 buffer pool 缓存同样的数据页，那同一份数据就在内存里**存了两遍**——一遍在 OS page cache，一遍在 buffer pool。这叫**双重缓存（double caching）**，白白浪费内存。

那为什么 InnoDB 还要自建、宁可冒双重缓存的浪费？因为**自己管，能做 OS 做不到的事**：

- **更懂自己的访问模式**：数据库知道"这是个索引页、那是个会被全表扫一次就不再用的数据页"，能据此做比 OS 通用 LRU 更聪明的淘汰（比如防止一次大全表扫描把热点页全冲掉——这正好接到[缓存](../../缓存/)主题第 8 问的"扫描污染 LRU"）。OS 不懂这些语义，只能一视同仁。
- **更可控的刷盘/检查点**：buffer pool 里的脏页什么时候刷、怎么和 WAL 检查点配合，数据库要精确掌控（关系到崩溃恢复时间），交给 OS 它说了不算。
- **配合 `O_DIRECT` 消除双重缓存**：如果自建了 buffer pool，那 OS 那层缓存就纯属多余了。**`O_DIRECT` 就是为此存在的**——它告诉内核"我这个文件的 IO 绕过 page cache，直接在我的用户态 buffer 和磁盘之间走"。于是数据只缓存在 buffer pool 一处，双重缓存消除，IO 行为也更可预测（不会被 OS 的回写时机搞出意外延迟）。代价是：你放弃了 OS 免费的预读（readahead）和缓存，这些得自己实现——所以 `O_DIRECT` 只对"我比 OS 更懂自己访问模式"的系统（成熟数据库）划算，对普通应用反而是负担。

而 PostgreSQL 反方向押注：**信任 OS**。理由也成立——OS 站在全局视角，知道整台机器的内存压力，能在数据库和别的进程之间动态平衡缓存；自己重造一套缓存管理是大量复杂且容易出 bug 的工作，不如复用久经考验的内核 page cache。代价就是前面说的：对缓存的控制力弱一些，且 shared_buffers 和 page cache 之间存在一定双重缓存。

**所以谁对？没有普适答案**——这正是该刻进判断力的地方：**当"我比操作系统更懂我的数据访问模式"成立时，自建 buffer pool + O_DIRECT 划算；当不成立、或不值得那个复杂度时，信任 OS 更明智。** 成熟数据库（InnoDB、Oracle）属于前者，它们对自己的页访问了如指掌；绝大多数普通应用属于后者，自作聪明地绕过 OS 缓存几乎总是亏。

- **可验证**：`free -m` 看 `buff/cache` 那一列有多大——那就是 OS page cache 替你缓存的量；对比 InnoDB 的 `innodb_buffer_pool_size` 配置，体会"两层缓存"是怎么并存又怎么可能重复的；读 PostgreSQL 文档为什么建议 shared_buffers 别设太大（正是怕和 OS page cache 重复）。

## 10 · SSD 没磁头了，顺序写为什么还更快

"顺序写比随机写快"，在机械硬盘上是物理常识——磁头要移动寻道，随机访问就是慢。可到了 SSD，没有磁头、没有旋转盘片、没有寻道了，为什么**顺序写依然明显快过随机写**？答案是：物理原因**整个换了一套**，而看懂这套，会改变你设计存储格式的判断。

SSD 的闪存有三条铁律，是一切怪相的源头：

1. **读写按"页"（page，典型 4KB～16KB）**，但**擦除按"块"（block，一个块含几十到几百个页）**——擦除的粒度比写大得多。
2. **不能原地覆盖**。一个已经写过数据的页，**必须先把它所在的整个块擦干净，才能再写**。闪存只能"从 1 写成 0"，要变回去得整块擦。
3. 中间隔着一层 **FTL（Flash Translation Layer，闪存转换层）**：它把操作系统看到的"逻辑地址"映射到实际的物理闪存位置，并负责垃圾回收（GC）和磨损均衡。

把这三条合起来，随机写的灾难就浮现了。你要"原地"改一个逻辑页，FTL 不会真去擦那个块（太贵），而是**把新数据写到别处一个空闲页，把旧页标记为废**。于是随机小写会把数据**撒得到处都是**，制造大量"块里有几页有效、几页是废"的半满块。等空闲页不够了，GC 就得登场：**把半满块里仅存的有效页搬到别处，再把整块擦掉回收**——这一搬一擦，就是**写放大**：你以为写了 4KB，FTL 背后可能搬运、擦写了好几倍的量。写放大既拖慢速度，又**磨损闪存寿命**（闪存的擦写次数有限）。

而顺序写（或大块对齐写）天生友好：数据**整整齐齐填满一个个擦除块**，要回收时一个块要么全有效要么全废，GC 几乎不用搬运、直接擦——写放大趋近于 1，又快又不伤盘。

于是那句精辟的总结浮出水面：**SSD 本质上是一个"伪装成块设备"的日志结构系统。** FTL 在内部干的事——把随机写重映射成顺序写、攒一批一起落、后台 GC 清理回收——和第 4 问的 LSM-tree 几乎一模一样！这不是巧合，是同一个物理约束（"原地覆盖昂贵、顺序追加便宜"）逼出的同一种解法。

**这为什么改变你的判断？** 因为它告诉你：**为 SSD 设计数据格式时，要顺着它的脾气——多用追加、用大块对齐 IO，避开零碎的随机小写。** 这也解释了一连串现象：为什么 **LSM 和 SSD 是天作之合**（LSM 的顺序写正好喂 SSD 最爱吃的）；为什么 SSD **预留空间（over-provisioning）**能提速（给 GC 更多腾挪余地，减少写放大）；为什么 **TRIM 命令**重要（让 SSD 知道哪些页是文件系统层面已删的、可以直接当废页，省去 GC 搬运它们）。把 SSD 当成"快一点的 HDD"，你会在随机写密集的场景被写放大和寿命问题反噬；把它当成"内部跑着 LSM 的日志设备"，你的存储设计才对得上它的物理真相。

- **可验证**：用 `fio` 在同一块 SSD 上分别跑 4KB 随机写和 1MB 顺序写，对比吞吐和延迟——差距就是写放大和 GC 的代价；`smartctl -a` 看 SSD 的写入量统计和磨损指标，长期随机写密集的盘磨损会明显更快。
