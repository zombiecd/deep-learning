# 缓存 · 深讲十问

> 脊梁：缓存是持有一份可能过时的副本来换速度。一切难题都是同一个问题的变体——这份副本什么时候、凭什么、由谁判定它过期了？

---

## 1 · 为什么"缓存失效"难到成了两大难事之一

Phil Karlton 那句名言——"计算机科学里只有两件难事：缓存失效和给东西起名字"——常被当玩笑讲。但"缓存失效"为什么真能跻身"两大难事"？把它拆开，你会发现它难得有道理。

缓存失效要回答的核心问题是：**"我手里这份副本，和源数据现在还一致吗？" 而这个问题，把三件本来就各自很难的事，纠缠在了一起：**

- **分布式**：源数据往往在另一台机器（数据库），副本在缓存（甚至在 N 个进程内）。"源变了没有"是一个跨网络的问题——而跨网络你连"对方此刻状态"都不知道（[分布式系统](../../分布式系统/)主题的脊梁）。
- **时间**：源是在过去某一刻变的，你的副本是过去某一刻取的，两个时刻之间发生了什么，你不在场。
- **一致性**："一致"到底要多强？你能容忍副本过时几秒吗？还是一秒都不行？（[分布式系统](../../分布式系统/)第 4 问的一致性谱系，在缓存这里换了张脸。）

而最要命的一点是：**你无法廉价地知道"副本还一致吗"的答案。** 想确切知道，唯一办法是去问源数据——可你一旦每次都去问源，缓存就失去了意义（缓存的全部价值就是"不用每次都去问源"）。**这是一个自我矛盾的死结：缓存为了快而不去问源，却又因为不问源而无法确知副本是否过期。**

于是你被逼到只有两条路，每条都不完美：

- **猜**（TTL，第 5 问）：给副本设个过期时间，赌"这段时间内源大概不会变，或者变了我也忍得了"。简单，但必然有一段"源已变、副本还没过期"的不一致窗口。
- **被通知**（主动失效）：源一变就发个"失效"消息让缓存丢弃副本。听起来精确，但这个消息要跨网络传——可能丢、可能延迟、可能乱序（又是分布式问题），消息没到的那一刻，副本就是脏的。

**所以缓存失效的难，是结构性的、不是偶然的**——它本质上是"在不付出'每次问源'的代价的前提下，维持副本与源的一致"，而这件事在分布式 + 时间 + 一致性的纠缠下，根本没有免费的完美解，只有一堆各有取舍的缓解。理解了这个死结，后面九问就都是它的不同侧面了。

- **可验证**：拿你系统里任何一处缓存，问自己三个问题——它怎么知道源变了？源变到它更新之间的窗口有多长？这个窗口里读到旧值会出什么事？多半你会发现答案是"靠 TTL 猜"或"发消息但可能丢"，没有第三种轻松答案。

## 2 · 穿透/击穿/雪崩：三个完全不同的失效机制

"缓存穿透、缓存击穿、缓存雪崩"——这三个词听起来像近义词，是面试高频背诵题。但它们其实是**三个完全不同的故障机制**，触发条件、危害路径、解法**各不相同、互不替代**。把它们混为一谈，就会用错药。

**穿透（penetration）：查根本不存在的 key。** 攻击者（或脏数据）反复查询一个**数据库里压根没有**的 key（比如 `user_id = -999`）。缓存里当然也没有 → 每次都缓存未命中 → 每次都穿过缓存、打到数据库 → 数据库查完还是"没有" → 不会写缓存（因为没东西可缓存）→ 下次同样的查询又穿透。缓存形同虚设，数据库被反复打。**解法**：①把"查无此物"这个**空结果也缓存**起来（缓存 `user_id=-999 → null`，设个短 TTL），下次直接命中空值挡回去；②用**布隆过滤器**在缓存前面挡一道——它能极快地判断"这个 key 肯定不存在"，对不存在的 key 直接拒绝、不让它碰数据库。

**击穿（breakdown）：一个热点 key 在过期瞬间被并发洪流击穿。** 某个**极热**的 key（比如首页配置、爆款商品）一直被高频读、缓存命中率极高。但它**一旦过期**的那个瞬间——成千上万个并发请求**同时**发现它没了，**同时**冲去数据库重建这同一个 key。数据库被这一波"重建同一个值"的并发洪峰打垮。注意它和穿透的区别：穿透是"key 不存在"，击穿是"key 存在且很热，只是恰好过期了那一下"。**解法**：①**互斥重建**——只让**一个**请求去重建，其余的等它建好直接用结果（这正是作者的 **singleflight** demo 干的事！`WaitGroup.Done` happens-before `Wait` 返回，所以等待者读结果不用再加锁）；②热点 key **逻辑过期 / 永不过期 + 后台异步刷新**，避免"过期瞬间"这个真空。

**雪崩（avalanche）：大量 key 同时失效，或缓存整个挂掉。** 不是一个 key，而是**海量 key 在同一时刻一起过期**（最常见的原因：它们被设了**相同的 TTL**，于是同生共死），或者**缓存集群本身宕了**——瞬间海量请求全部未命中、全部涌向数据库，数据库被这股海啸冲垮，进而整个系统崩溃。**解法**：①给 TTL **加随机抖动**（jitter，又见[可靠性工程](../../可靠性工程/)第 1 问的同一招——打散同步！）让 key 错峰过期，别同生共死；②缓存做高可用（别让它整个挂）；③对数据库加**熔断/限流**（[可靠性工程](../../可靠性工程/)第 3、4 问），缓存挂了也别让海啸直接拍死数据库。

**判断的落点**：三者是三种病——穿透是"问不存在的东西"，击穿是"一个热点恰好过期那一下"，雪崩是"一大批同时过期/缓存全挂"。**药也是三副，不能混用**：布隆过滤器治不了击穿，singleflight 治不了雪崩，TTL 打散治不了穿透。能一眼分清你遇到的是哪一种、开对应的药，就是把这道"背诵题"真正学透了。

- **可验证**：本地起 Redis + 一个 DB，分别构造三种场景——狂查不存在的 key（穿透）、让一个热 key 过期时并发打（击穿）、给一批 key 设相同 TTL 然后等它们一起过期（雪崩）——观察数据库 QPS 的三种不同尖峰形态，再分别上对应的解法看它怎么被压平。

## 3 · Cache-aside 的经典竞态为什么没有完美解

缓存有几种经典用法模式，它们不是"风格偏好"，而是在**一致性、延迟、丢数据风险**上踩了不同的点：

- **Cache-aside（旁路缓存，最常用）**：应用自己管。读：先查缓存，命中就返回；未命中就查数据库、回填缓存。写：更新数据库，然后**让缓存失效**（删掉）。缓存只是"旁路"，应用全程做主。
- **Read-through / Write-through（穿透读写）**：把读写数据库的活儿交给缓存层同步代理——读未命中时缓存自己去加载，写时缓存自己同步写库。对应用透明，但一致性更好维护、延迟略高。
- **Write-back（写回 / write-behind）**：写只写缓存、立刻返回，**异步**地稍后批量刷回数据库。写极快，但缓存若在刷回前挂了，**那批数据就丢了**——拿丢数据风险换写入延迟。

最常用的 Cache-aside，恰恰藏着一个**经典的并发竞态，而且它至今没有完美解、只有缓解**。竞态是这样发生的（两个线程交错）：

1. 线程 A 读缓存，**未命中**，于是去查数据库，读到旧值 `v1`。（此刻 A 还没来得及把 v1 写回缓存。）
2. 线程 B 此时**更新数据库**，把值改成 `v2`，并**删除缓存**（Cache-aside 的写流程）。但缓存本来就是空的，删了个寂寞。
3. 线程 A 这才**慢悠悠地把它读到的旧值 v1 写回缓存**。

结果：数据库里是新值 `v2`，缓存里却被 A 写进了**旧值 `v1`**——而且会一直脏到 TTL 过期或下次写触发失效。**一次正常的读、一次正常的写，交错出了一个持久的脏缓存。** 这正是[并发原理](../../并发原理/)主题里"read-then-act 不原子就有竞态"的缓存版——A 的"读库 → 写缓存"不是原子的，中间被 B 的写插了进来。

**为什么说没有完美解？** 因为要彻底堵死，你得让"读库 + 回填缓存"和"写库 + 删缓存"之间有严格的串行化保证——而这又把你拖回[分布式系统](../../分布式系统/)的强一致协调，代价高到失去了用缓存的意义。所以工程上只有**缓解**：

- **延迟双删**：写库 + 删缓存之后，**过一会儿再删一次**——赌"第二次删"能清掉 A 在间隙里写进去的脏值。能大幅降低概率，但不能 100% 保证（第二次删的时机也是猜的）。
- **订阅 binlog（如 Canal）**：不靠应用主动删缓存，而是**监听数据库的变更日志**，库一变就据此失效缓存——更可靠、更解耦，但要搭一套订阅链路。
- **兜底 TTL**：给缓存配一个不太长的 TTL，**就算某次失效漏了/脏了，最多脏 TTL 这么久就自愈**——这是最朴素也最该有的安全网（接第 5 问）。

**判断的落点**：别追求"缓存和数据库永远强一致"——那是个昂贵且常常不必要的目标（[分布式系统](../../分布式系统/)第 4 问）。承认 Cache-aside 有这个竞态、用延迟双删/binlog 订阅压低概率、再用 TTL 兜底自愈，是务实且成熟的工程姿态。

- **可验证**：用两个 goroutine 精确编排上面的交错时序（A 读库后 sleep 一下，期间让 B 完成写库+删缓存，A 再写回），稳定复现脏缓存；再加 TTL，验证它最终自愈。

## 4 · "先更库再删缓存"与"更新缓存为何总更糟"

接上一问，写操作时缓存和数据库的更新**顺序**，是个看似抠字眼、实则真会翻车的并发问题。两个维度要想清楚：**先动谁**，以及**对缓存是"删"还是"更新"**。

**维度一：先删缓存再更库，还是先更库再删缓存？**

- **先删缓存，再更新数据库**：删完缓存、还没更完库的**间隙**里，若有个读请求进来——它缓存未命中，去读数据库，读到的是**还没更新的旧值**，然后把这个旧值**回填进缓存**。等你的写终于更完库，缓存里却是刚被回填的旧值，脏掉了。
- **先更新数据库，再删缓存**（Cache-aside 标准做法，通常更优）：先把库改对，再删缓存。它的间隙问题更小（更新库到删缓存之间很短），但仍有上一问那个 Cache-aside 竞态。所以它是"更好但不完美"。

两个顺序都有竞态窗口，但"先更库再删缓存"的窗口通常更窄、更可控，所以是主流推荐——再配延迟双删和 TTL 兜底（第 3 问）。

**维度二：对缓存该"删除（delete）"还是"更新（update，写入新值）"？答案几乎总是删除，而"更新缓存"几乎总更糟。** 三个原因：

- **写-写竞态**：两个并发写 A（把值改成 a）和 B（改成 b）。如果是"更新缓存"：可能数据库的最终值是 b（B 后提交），但缓存的更新却因为调度乱序变成了 a 后写——**缓存里留下 a，和库里的 b 不一致**。两个"写缓存"动作的相对顺序，和两个"写数据库"动作的相对顺序可能不一致，于是缓存定格在错误的值上。而"删除缓存"没有这个问题——删除是幂等的，两个并发删除，结果都是"缓存为空"，下次读时从库里拉到的一定是最新值。
- **白算一场**：如果你"更新缓存"，但这个值**写进去后、下次被读之前，又被改了好几次**——那你每次更新缓存都是白算（写了没人读就又被覆盖）。"删除 + 下次读时再懒加载"则只在**真有人读**时才计算一次，不浪费。
- **派生值更贵**：如果缓存里存的是一个**计算/聚合出来的派生值**（比如某个复杂查询的结果），"更新缓存"意味着每次写都要重新跑那个昂贵的计算；"删除 + 懒加载"则把计算推迟到真正需要时。

**所以经验法则是："写数据库 + 删除缓存（而非更新缓存）"，再用 TTL 兜底。** 而终极的判断，回到[分布式系统](../../分布式系统/)第 4 问的精神：**别为缓存和数据库的强一致较劲**——给它配个合理的 TTL，接受"最多脏一小段时间"，绝大多数业务这完全够用，且省掉了一大堆为强一致自找的复杂度和竞态。

- **可验证**：构造两个并发写，分别用"更新缓存"和"删除缓存"两种策略，看"更新缓存"怎么因为写顺序乱序而留下脏值、而"删除缓存"怎么靠幂等避免了它。

## 5 · TTL 为什么是"用陈旧换掉全部复杂度"

TTL（过期时间）是最朴素的失效手段——给缓存的每个 key 设个寿命，到点自动失效、下次读时重新加载。朴素到很多人没意识到：**TTL 其实是一笔极其划算的交易——它用"接受数据可以陈旧最多 TTL 这么久"，换掉了主动失效的全部复杂度。**

把这笔交易看清楚。第 1 问说过，缓存失效的死结在于"既要不付出每次问源的代价，又要知道副本是否过期"。主动失效（源一变就通知缓存丢弃）想精确解决它，代价是要搭一套"变更 → 通知 → 失效"的链路，还要面对消息丢失/延迟/乱序的分布式难题（第 3 问那些缓解措施全是为它擦屁股）。**而 TTL 直接绕开整个死结：它不问"源变了没"，只说"反正过了 N 秒我就当它可能旧了，重新拉一份"。** 一句话，把一个棘手的"分布式一致性 + 主动失效"问题，降维成一个"有界陈旧（bounded staleness）"的参数。所有那些 binlog 订阅、延迟双删的复杂度，TTL 一笔勾销——代价仅仅是"承认数据可以旧一会儿"。

**正因如此，"TTL 设多长"是一个业务判断，不是技术判断。** 它直接等价于一个业务问题：**"你的业务能容忍这个数据陈旧多久？"**

- 商品库存：陈旧几秒可能就超卖，TTL 要极短或干脆别只靠 TTL。
- 用户昵称、头像：陈旧几分钟没人受伤，TTL 可以很长。
- 首页推荐、热榜：陈旧十几分钟甚至一小时都行，TTL 可以很长，省大量回源。

没有"正确的 TTL"，只有"匹配这份数据的业务容忍度的 TTL"。把这个判断当技术参数随手拍，要么 TTL 太短白白增加回源（失去缓存意义），要么太长导致业务无法接受的陈旧。

**而最后一个坑，前面已埋过伏笔：给所有 key 设同一个 TTL，是在亲手制造雪崩（第 2 问）。** 如果一大批 key 同时被写入、又用了同一个 TTL，它们会在同一时刻**集体过期、集体回源**，把数据库一波打垮。所以 TTL 必须**加随机抖动**——基础 TTL ± 一个随机量，让 key 们错峰过期。这又是[可靠性工程](../../可靠性工程/)第 1 问那条元教训的第三次出现：**大量个体在同一信号下同步行动 = 毁灭性尖峰，解药是主动引入随机性打破同步。**（重试、TTL、退避，同一招。底层是连通的。）

- **可验证**：给一批 key 设完全相同的 TTL，监控它们过期时刻数据库 QPS 的尖峰；改成 `TTL + rand(0, jitter)`，看尖峰怎么被抹平成平缓曲线。

## 6 · 多级缓存与 CDN：为什么"从不失效、只换名字"

真实系统里，一个数据从源到用户眼前，往往要穿过**一长串缓存**：浏览器缓存 → CDN 边缘节点 → 接入层网关缓存 → 应用进程内本地缓存 → Redis → 数据库。多级缓存能层层挡住请求、极大减轻源压力。但它有个绕不开的代价：**每多一级缓存，就多一处"可能各自持有不同版本"的不一致源。** 你改了源，要让这一串里的每一级都更新到最新——而它们各有各的失效机制、各有各的 TTL，**协同失效几乎是噩梦**（第 1 问的死结，乘以层数）。

这个噩梦在 **CDN 这一级尤其尖锐**，因为 **CDN 的主动失效（purge / 刷新缓存）是出了名的慢和不可靠**：CDN 把内容缓存在全球成千上万个边缘节点上，你发一个"purge 这个 URL"的指令，要传播到全世界每一个节点、让它们都丢弃旧副本——这要花几分钟，而且偶尔有节点没收到/没执行，留下零星的脏副本。你急着上线一个新版本的 JS/CSS/图片，却要祈祷全球 CDN 都及时刷新了——这是 CDN 运维的经典痛点（作者的 CDN 背景对此应该不陌生）。

**于是工业界发明了一招釜底抽薪的打法——版本化 URL / 内容指纹（content hashing）：从不失效，只换名字。**

思路是：**不要试图让 CDN"失效"一个 URL，而是给文件名里嵌入它内容的指纹（哈希）**——比如把 `app.js` 改成 `app.a3f9b2c1.js`，那串 `a3f9b2c1` 是文件内容算出来的哈希。于是：

- 内容**没变**时，哈希不变，URL 不变，CDN 上的副本**永远有效、可以缓存到天荒地老**（TTL 设一年都行）——因为这个 URL 对应的内容**永不改变**。
- 内容**变了**时，哈希就变了，URL 也跟着变成 `app.b7e4d9f2.js`——对 CDN 来说这是一个**全新的、从没见过的资源**，它会去源站拉最新的；而旧的 `app.a3f9b2c1.js` 没人再引用了，自然冷却淘汰，**根本不需要去"失效"它**。

**这一招的精髓是：把"可变的 URL + 头疼的失效"，换成"不可变的 URL + 改内容就换 URL"——彻底绕开了缓存失效这个死结。** 因为只要 URL（缓存的 key）和内容是绑定的、不可变的，"这个副本还一致吗"这个问题就**永远是 yes**，失效问题不复存在。HTML 入口文件（它得用短缓存，因为它要引用最新的带指纹的资源名）+ 带指纹的静态资源（长缓存、不可变）的组合，是现代前端构建（webpack/vite 的 hash 文件名）和 CDN 配合的标准范式。

这背后是一个能迁移到很多地方的深刻思想：**不可变性消灭了一致性问题。** 一个永不改变的东西，不存在"副本和源不一致"的可能——这和[并发原理](../../并发原理/)主题里"配置热加载的最优解是'不可变 + 换指针'而非加锁"是**同一个思想**（不可变数据天然无竞态），也和[网络](../../网络/)第 10 问 DNS 缓存、[分布式系统](../../分布式系统/)的最终一致一脉相承。底层，又一次连通了。

- **可验证**：看任何现代网站的静态资源 URL，几乎都带一串哈希（`main.4f8a2b.js`）——那就是这一招；看它的 Cache-Control，带哈希的资源往往是 `max-age=31536000, immutable`（缓存一年、且声明不可变），而 HTML 入口是 `no-cache`。一个长一个短，正是这套范式的指纹。

## 7 · 本地缓存最快，为什么又把你拽回分布式

进程内的本地缓存（直接在应用内存里存一个 map / Caffeine / Guava Cache / Go 的 sync.Map 之类）是**最快**的缓存——没有网络往返、没有序列化，纳秒级命中，比 Redis（要走网络，微秒到毫秒级）快几个数量级。既然这么快，为什么不全用本地缓存？因为它引入了一个**集中式缓存（Redis）根本没有的难题：N 个应用实例，各自有一份独立的副本，怎么让它们同时失效？**

集中式缓存只有"一份"——Redis 里某个 key 就一个，你删它，所有应用实例下次读都未命中、都去拉最新值，天然一致。但本地缓存是**每个实例各存各的**：你有 10 个应用实例，同一个 key 就有 **10 份独立副本**散在 10 个进程的内存里。现在源数据变了，你怎么通知这 10 个进程**同时**丢弃它们各自的那份旧副本？

- 你没法像删 Redis 那样"删一个就完事"——你得**广播**："喂，所有实例，把 key X 失效掉！"
- 而广播是个分布式问题：靠 Redis pub/sub？消息可能丢、某个实例可能刚好在重启没收到。靠定时拉取版本号？那又有延迟。靠……

**看见没有——本地缓存的"快"，是用"重新掉进分布式一致性"换来的。** 你为了省掉网络往返的那点延迟，换来了"N 份副本如何协同失效"这个分布式难题（广播失效、版本号比对、最终一致）。第 1 问那个死结，在本地缓存这里**乘以了实例数**。

**那什么时候本地缓存的"快"补偿不了它的"各执一词"？** 判断标准是数据的**变更频率**和**一致性要求**：

- **适合本地缓存**：很少变、且短暂不一致无所谓的数据——比如配置字典、地区编码表、几乎不变的元数据。变得少，失效就少，"各执一词"的窗口和概率都低，本地缓存的速度优势净赚。
- **不适合本地缓存**：变得频繁、或一致性要求高的数据。最危险的例子是**权限/功能开关**——如果你把"用户 X 的权限"缓存在本地，管理员刚把他的权限收回了，但某个实例的本地缓存还留着旧的"有权限"，于是这个实例**继续放行一个本该被禁止的操作**——这就从"性能问题"升级成了"安全问题"（[安全思维](../../安全思维/)主题）。这种场景，宁可慢一点用集中式缓存（甚至不缓存），也不能让"各执一词"造成正确性/安全事故。

**判断的落点**：本地缓存是把双刃剑——它最快，但它把"一份副本"变成了"N 份要协同的副本"，把缓存一致性问题升级成了分布式一致性问题。用它的前提是"这份数据变得足够少、且短暂不一致无害"。常见的成熟做法是**两级缓存（本地 + Redis）**：本地挡住绝大多数读、Redis 作为相对一致的次级，再加 pub/sub 广播失效本地副本——但要清楚，这套组合的复杂度，正是你为"那点本地速度"付的分布式税。

- **可验证**：起多个应用实例都用本地缓存同一个 key，改一次源数据、只通过 Redis pub/sub 广播失效，故意让一个实例"漏收"广播（重启它），观察它怎么继续返回脏值——亲手制造一次"本地缓存各执一词"的不一致。

## 8 · 命中率越高越好吗，LRU 怎么被扫描污染

"缓存命中率（hit rate）越高越好"——这又是个需要打问号的直觉。盲目追求高命中率，会让你掉进两个坑。

**坑一：为了高命中率，缓存了大量"占着地方、却很少被再读"的冷数据。** 命中率高，可能只是因为你把什么都往缓存里塞——但缓存空间有限，塞进一堆"读一次就再也不读"的冷数据（one-hit wonders），就会把真正的热数据**挤出去**。表面命中率好看，实际是在用宝贵的缓存空间养一堆没价值的副本，还增加了一致性维护负担（第 1 问）。**缓存该装的是"会被反复读的热数据"，不是"读过一次的所有数据"。** 命中率要看，但要结合"缓存了什么"一起看，别为了刷命中率而缓存一切。

**坑二（更深）：LRU 在扫描型负载下会被污染到形同虚设。** LRU（最近最少使用）是最常见的淘汰策略——淘汰最久没被访问的。它在"有稳定热点"的负载下很好用。但遇到**扫描型负载**（一次性顺序遍历大量数据，比如一个批处理任务、一次全表扫描、一次大范围导出），LRU 会**灾难性地失效**：

- 扫描会**依次访问大量"只读这一次、之后再也不碰"的数据**。
- LRU 看到这些数据"刚刚被访问"，就把它们当成"最近使用的"留在缓存里，**反而把真正的热点数据当成"较久没访问的"淘汰掉**。
- 于是一次大扫描过后，缓存里塞满了**扫描时读过、却永远不会再读**的冷数据，真正的热数据全被冲走——**缓存被"污染"了，命中率暴跌，扫描结束后还要很久才能"养"回热点。**

这就是为什么"一个半夜的批处理任务，把白天的缓存全冲坏了，早上高峰期缓存命中率暴跌"是个真实事故。**LRU 的弱点是它只看"最近"，分不清"最近被访问"是因为它真热、还是因为一次性扫描碰到了它。**

针对不同的访问模式，演化出了一系列更聪明的算法，它们各自在和某种模式作斗争：

- **LRU-K**：要求一个数据被访问 **K 次**才有资格进入"受保护"区——一次性扫描的数据只被碰一次，进不来，从而**抗扫描污染**。
- **LFU（最不经常使用）**：按访问**频率**淘汰，热点（高频）天然受保护，但对"曾经热、现在凉了"的数据反应迟钝（需配合衰减）。
- **ARC（自适应替换缓存）**：动态平衡"最近性（recency）"和"频率（frequency）"两个维度，**自带抗扫描**能力，是很多存储系统（如 ZFS）的选择。

这直接接到[存储引擎](../../存储引擎/)第 9 问——数据库自建 buffer pool 的一大理由，正是它要做这种"抗扫描污染"的智能淘汰（一次全表扫描不该把整个 buffer pool 冲烂），而通用 OS page cache 的 LRU 做不到。**底层又连通了：应用层缓存和数据库 buffer pool，面对的是同一个"LRU 被扫描污染"的敌人。**

- **可验证**：模拟一个访问序列——先是稳定的热点访问，中间插入一段"顺序扫描一大批不重复 key"，再回到热点访问；用 LRU 跑，看扫描段怎么把命中率打到谷底、且恢复缓慢；换 LRU-K 或 ARC，看它怎么扛住扫描、保护住热点。

## 9 · 为什么"先别加缓存"常常才是对的判断

遇到慢查询，本能反应是"加个缓存"。但很多时候，**正确的工程判断恰恰是"先别加缓存"**——因为加缓存常常是**把一个性能问题，换成了两个一致性问题**（第 1 问那个死结、加上多副本协同），而原来的性能问题可能根本不需要靠缓存解决。

先认清加缓存的真实代价：你以为加了缓存就是"变快了"，实际上你同时引进了一整套新麻烦——缓存怎么失效（第 1 问）、并发竞态（第 3、4 问）、雪崩击穿穿透（第 2 问）、多副本一致性（第 7 问）、以及"缓存和数据库不一致时排查起来格外烧脑"的运维负担。**缓存不是免费的加速器，它是用一致性复杂度换速度的交易。** 所以加之前要先问：这笔交易划算吗？这个慢，是不是缓存该解决的那种慢？

**关键的判断，是区分"读放大"和"烂查询"：**

- **读放大（read amplification）**：同一份数据被**大量请求反复读**（首页配置被每个用户读、热门商品被无数人看）。源（数据库）被同样的读重复轰炸。**这才是缓存的主场**——缓存就是用来"把对同一份数据的重复读，挡在源前面"的。这种慢，加缓存对症。
- **烂查询（bad query）**：查询本身慢——缺索引、全表扫描、O(n²) 的逻辑、N+1 查询（[存储引擎](../../存储引擎/)、[性能工程](../../性能工程/)主题）。这种慢，加缓存只是**把烂查询的结果存起来，掩盖了问题、还附赠了一致性风险**——查询本身的烂没修，第一次查（缓存未命中）还是慢，缓存一过期/被穿透又暴露原形，而你还多背了一身缓存一致性的债。**这种慢，该去优化查询本身（加索引、改写 SQL、消除 N+1），而不是用缓存盖住它。**

**"缓存是用来扛读放大的，不是用来补烂查询的"**——记住这个区分，能帮你省掉一大类自找的麻烦。一个缺索引的查询，正确动作是加索引（一次性、无一致性代价、且彻底）；给它套个缓存，则是用持续的一致性复杂度，去掩盖一个本可一劳永逸修掉的问题。前者是治本，后者是花钱买债。

**判断的落点**：加缓存前过一遍这个 checklist——①这个慢是读放大还是查询本身烂？②如果是查询烂，能不能先优化查询（往往加个索引就够了）？③如果确实是读放大、决定加缓存，我想清楚它的失效策略、竞态、和兜底 TTL 了吗？能诚实地"先别急着加缓存、先看看能不能优化源头"，是比"一慢就缓存"更成熟的判断。

- **可验证**：找一个你系统里"加了缓存"的地方，回头查它当初是为了扛读放大、还是为了盖一个慢查询；如果是后者，试试去掉缓存、给查询加索引/改写，看是不是又快又省去了缓存那套复杂度。

## 10 · Redis 不只是哈希表：持久化与单线程的硬约束

很多人对 Redis 的心智模型停在"一个跑在内存里的大哈希表，特别快"。这个模型会让你在两个地方栽跟头——它的**持久化**其实面对着和数据库一样的难题，它的**单线程**则给你的用法划了一条硬约束。

**其一：Redis 的持久化，面对的是和数据库 WAL 一模一样的"崩溃一致性"难题。** Redis 数据在内存里，进程一挂、机器一断电就没了。所以它提供两种持久化，而这两种恰恰对应[存储引擎](../../存储引擎/)主题里讲过的两种思路：

- **RDB（快照）**：定期把整个内存数据 dump 成一个快照文件。优点是文件紧凑、恢复快；缺点是**两次快照之间的数据，崩溃就丢了**（你 5 分钟存一次，崩在第 4 分钟，这 4 分钟的写全没）。这就是"周期性快照"的固有取舍。
- **AOF（追加日志）**：把每一条写命令**追加**到一个日志文件——这**几乎就是数据库的 WAL**（[存储引擎](../../存储引擎/)第 2 问）！恢复时重放这些命令即可。而它同样要面对 WAL 那个核心权衡：**多久 fsync 一次？** 每条命令都 fsync（`appendfsync always`，最安全最慢）、每秒 fsync（`everysec`，崩溃最多丢 1 秒）、还是交给操作系统（`no`，最快最不安全）——这和 MySQL 的 `innodb_flush_log_at_trx_commit` 是**同一个旋钮、同一个一致性 vs 性能的兑换**。**看懂 Redis 持久化 = 复用你在存储引擎主题学的崩溃一致性知识**，底层再次连通。

**其二：单线程的 Redis 反而快——但一条慢命令能卡死所有人。** Redis 处理命令的核心是**单线程**的（网络 IO 在新版本里多线程了，但命令执行仍是单线程）。反直觉的是，单线程**反而是它快的原因之一**：所有命令排队顺序执行，**没有锁、没有线程切换、没有并发竞态**——它把[并发原理](../../并发原理/)主题里那些让人头疼的同步问题**整个绕开了**（不需要锁，因为压根没有并发执行）。每个命令都是原子的，因为它们本来就一个接一个跑。这是"用单线程换掉并发复杂度"的极致。

但这条单线程，也是一根**致命的软肋**：**因为所有命令排一个队顺序执行，只要有一条命令很慢，它就会把整个队列卡住，后面所有请求全部干等**——这是命令级的队头阻塞（[网络](../../网络/)第 5 问的队头阻塞，换了个场景）。哪些命令会闯这个祸？

- **`KEYS *`**：遍历**所有** key，O(n)。生产库有几百万 key，这一条能让 Redis **卡死好几秒**，期间所有其他请求全部超时——这是新手最容易犯、后果最严重的事故。正确做法是用 `SCAN`（游标分批、不阻塞）。
- **删除/读取一个大 key**：删一个有几百万元素的大 Hash/Set/List，或 `SMEMBERS` 一个巨大的集合——都是 O(n)，都会长时间占住单线程。大 key 是 Redis 的隐形炸弹（要用 `UNLINK` 异步删、`lazy-free`，并从设计上避免大 key）。

**所以单线程给你的硬约束是：Redis 上绝不能跑 O(n)/O(大) 的命令。** 这条约束直接来自"单线程顺序执行"这个架构事实——理解了它，你就懂了为什么 Redis 规范里反复强调"禁用 KEYS、警惕大 key、用 SCAN 代替遍历"。这不是规矩，是单线程模型的物理推论。

- **可验证**：往 Redis 灌几百万 key，然后跑一条 `KEYS *`，同时用另一个客户端发普通请求——看普通请求怎么在 `KEYS *` 执行期间全部卡住（`SLOWLOG GET` 能看到那条慢命令）；换成 `SCAN` 分批，看其他请求怎么不再被阻塞。
